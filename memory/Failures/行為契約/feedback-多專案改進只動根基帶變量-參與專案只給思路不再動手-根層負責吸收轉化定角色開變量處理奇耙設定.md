## 知識

- [臨] 使用者原話（根層總控三方討論第二波）：改進「僅限在根基，而且是根層、專案層、公司層全域都可以應用的帶變量規則，並預設本次參與的專案不做任何進一步的調整」；根層「負責吸收、理解、轉化」，想清楚根層與專案層未來各扮演什麼角色、根層要調什麼、開什麼變量給專案層用、怎麼處理多專案的奇耙設定；兩個專案 session 是專案層視角，程式人員教育不同思路會不同，那是輸入的價值不是要統一的。
- [臨] 我犯的錯：在這段話之後仍派專案 session 去擴自己的表、寫 _tools 原型——總控台派工前要對照使用者最新的範圍聲明；範圍是「只動根基」時，專案 session 只回思路（角色哪裡不對、會覆蓋哪些變量成什麼值、根層不知道就會做錯的設定、哪些主張是自家習慣），不動手；已做的當樣本不回退也不擴。
- [臨] 根層處理多專案差異的原則（三邊 Codex 共同核過）：差異靠變量吸收、不在 hook 裡寫專案分支；每個變量要有預設可用、覆蓋有理由、歧義報錯；吸收不了的（跨 repo 版本、公司作用域、執行環境）定契約而不是丟給使用者配置；根層負責「產生與更新」的流程（骨架、路由、健檢、回路），專案只提供領域事實，否則機制缺口會被專案補卡補表遮住。

## 行動

- 收到範圍聲明後，先改派工再改文件：專案端停手、改成回思路四題
- 多專案差異出現時先問「這能做成變量嗎」→ 能：預設＋覆蓋理由＋歧義報錯；不能：定契約
- 根層 session 不派專案工；日常看 scorecard 與回路、調預設、修閘

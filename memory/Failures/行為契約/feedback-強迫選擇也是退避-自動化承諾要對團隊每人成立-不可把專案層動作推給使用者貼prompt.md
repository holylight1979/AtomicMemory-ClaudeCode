## 知識

- [臨] 使用者原話（2026-09-03）：「先不選，繼續討論，避免重要決策缺漏（強迫選擇也是一種退避）」。從討論中推出 A/B 二選一要人拍板，若他的質疑還沒逐點回完、或我自己的前提還有錯（例：「B 多一個 commit」其實不成立），那個選擇題是把我該做的分析推給他。正確做法：逐點回答、認錯就認、把選項間真正的差異縮到一句，再讓他決定。
- [臨] 使用者原話：「專案層也要我去貼 prompt？這不也應該是自動辦到好的嗎？」。完工後的操作必須對團隊每一個人、每台機器全自動；「根層的事在根層、專案的事在專案 session」是改程式時的權限邊界，不是把專案層的機械動作推給使用者手動執行的理由；專案層的自動化要換點換成既有的專案內觸發點（如 atom 寫入漏斗尾端、專案內的 git 指令前）。同理，「升級後手動跑一次 X」若可以在需求發生時自動補上，就不要寫成必做步驟。

## 行動

- 要出選擇題前自問：他的每個質疑我都答了嗎？我的前提有沒有錯？選項差異能不能一句話說清？三者任一否 → 先回答，不出題
- 收尾若出現「請使用者到 X 貼這段 prompt」，先問能不能換成專案內既有觸發點自動執行；只有真的需要人拍板或不可逆才留給人

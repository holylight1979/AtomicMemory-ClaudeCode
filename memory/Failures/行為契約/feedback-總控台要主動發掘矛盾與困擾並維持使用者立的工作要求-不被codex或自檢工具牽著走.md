## 知識

- [臨] 使用者原話：「你要維持住我告訴你的這些工作要求與品質，並且要主動去發掘出矛盾或困擾之處，不要只是單純被 Codex 牽著鼻子走」。背景：對人總控台一整天「codex 或自檢工具指一條→我裁一條」，文件被補成飄移、誤擋被當成要配合的流程、該推就推變請示。審查者只對它被問的面找漏洞；目標對不對、流程有沒有自相矛盾、使用者在哪裡被磍到，沒人替總控台看。
- [臨] 收到審查或自檢結果先問三題再裁：①服務原話輯哪一條目標？指不出就維護軌或不理；②跟已定規則或其他軌有沒有矛盾？有就先解；③使用者現在被什麼磍到（重複提問、看不懂的名字、幾十條廢話）？那才是第一優先。每回合收尾前自己掃一次「哪條規則被重複踩、哪兩條互打」。
- [臨] 裁錯實例一：工作 session 回報「關掉部位導讀時讀入範圍提醒也不跑，建議維持現狀」，我照它的框架裁維護軌；原設計者一問「這不就是要讓 LLM 具備綜觀能力？」就倒。錯在用實作成本當判準、沒先問服務哪條目標（是 G0／G1 核心）、把「部位表（資料）」與「綜觀（行為）」當同一件事。判準：工作 session 提「維持現狀」或「改得動到別軌」時，先回原話輯找目標，目標是核心就改，成本不是理由。
- [臨] 裁錯實例二（連續兩次被翻）：Codex 對一支測試說「正規表達式抓分支，未來改寫可能漏抓」，調度退件我無異議；原設計者指正「Codex 建議要用綜觀很確定會造成重大問題再派，別用邊角問題浪費 token 與工時」，我馬上撤回；他再指正「不要只是附和我，綜觀包含『執行起來很快且有具體讓系統更好的效果』」。判準兩面：重大問題（一般寫法會踩、後果是漏記／誤認／誠實流程過不了）→派；快且具體有效（小範圍、一輪內、系統明確變好）→派、順手做；兩者都不是→維護軌。被指正後要自己重新判，不把指正套成新的單一條件倒向另一邊。

## 行動

- 收到審查條目：先對原話輯目標、再查與既有規則的矛盾，再用成本效益兩面裁（重大？快且有效？），兩問都否才維護軌
- 每回合收尾前自問：使用者被什麼磍到、哪兩條規則互打；有就主動提出處理
- 被使用者指正後：重新判手上那件，不直接撤回或直接照做

## 知識

- [臨] 原設計者原話（看到 AI 把自己點出的「最該修」寫成「該誰解：下一個寫碼 session」）：「他們有空就讓他們修完不是嗎？這也是我說『我從未答應把這種東西另外放進修正計畫』的狀況……倘若是 Codex 或審查時挖出來的、但 LLM 判斷後其實屬於『飄移』的，直接不做；但倘若有關且確實有問題，就應該要立即修正。」
- [臨] 規矩：審查、codex、交付時挖出的問題只有兩種常徵——判為飄移（跟手上目標無關、或是設計取捨）就寫一句理由直接不做；判為相關且確實有問題，就由發現的人當場修（先紅後綠），再交付。「該誰解」欄只能是「已修」或「飄移，不做，因為…」，不准寫「下一個寫碼 session」「之後再排」（要同意就當場問，不當排除理由）。實例：正式模組檔名踩到案例樣式沒守門、宣告行留在卡片知識段吃預算——兩件都是發現的軌自己能修、一個案例加一處改動。

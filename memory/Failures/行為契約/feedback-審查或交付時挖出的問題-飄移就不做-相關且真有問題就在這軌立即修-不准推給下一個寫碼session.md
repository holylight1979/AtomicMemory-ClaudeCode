## 知識

- [臨] 原設計者原話（看到兩條工作軌把自己點出的「最該修」寫成「該誰解：下一個寫碼 session」）：「他們有空就讓他們修完不是嗎？這也是我說『我從未答應把這種東西另外放進修正計畫』的狀況……倘若是 Codex 或審查時挖出來的、但 LLM 判斷後其實屬於『飄移』的，直接不做；但倘若有關且確實有問題，就應該要立即修正。」
- [臨] 規矩：審查、codex、交付時挖出的問題只有兩種常徵——判為飄移（跟手上目標無關、或是設計取捨）就寫一句理由直接不做；判為相關且確實有問題，就由發現的那條軌在同一分支立即修（先紅後綠），再交付。「該誰解」欄只能是「已修」或「飄移，不做，因為…」，不准寫「下一個寫碼 session」「合併後由總控台排」「要總控台同意」（要同意就當場問，不當排除理由）。實例：正式模組檔名踩到案例樣式沒守門、宣告行留在卡片知識段吃預算——兩件都是發現的軌自己能修、一個案例加一處改動。
- [臨] 總控台端：收到交付信先掃「該誰解」與「已知限制」，裡面有被推遲的相關問題就派回原軌的下一封補件，不記成追蹤項。追蹤項只留給真的跨軌、要原設計者拍板、或會撫到別軌正在改的檔的事。

## 行動

- 寫交付信的「該誰解」前先判：飄移？不做寫理由。相關且真有問題？現在修，欄位寫「已修」
- 總控台收件：「該誰解」出現下一個 session／之後／合併後排 → 當場派回原軌補件

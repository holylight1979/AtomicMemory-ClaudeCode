## 知識

- [臨] 原設計者在多軌合併收尾時立下總控台流程規則（以後所有多軌開發適用）：①啟動後先檢討「目前流程耗時長的核心原因」向原設計者回報並優先改流程；②同權但不同面向的兩個總控台並行——一個「對人」（回答原設計者、裁定、追蹤表），一個「調度」（派工、對帳、快照、合併、與各 session 通訊），用 SendMessage 同步；③原設計者的提問是最高優先，同一回合先答再做事；④所有寫碼工作一律拆去其他工作 session（Opus）執行，總控台連一行碼都不改、也不開子代理寫碼；⑤每個工作 session 自己跑 codex 審查、交付附審查報告，最終判斷由總控台做。
- [臨] 為什麼要分兩個 session 而不是一個 session 開子代理：子代理收不到跨 session 的 SendMessage、也不能直接對原設計者說話；只有主 session 能做這兩件事。
- [臨] 原設計者同時裁定：獨立實跑驗證不再單獨開一個 session，併進各工作 session 的交付（自己跑探針附結果）；總控台只在閘本體合併前抽查一次。
- [臨] 模型配置（原設計者 Fable 額度吃到 95% 後定）：調度總控台只做對帳、合併、推送、收材料，用 Opus 就夠；小修類工作軌也用 Opus；對人總控台在只剩轉達與收尾時也可換 Opus。Fable 只留給裁定密集、要回錨原話輯的階段。換模型不丟對話脈絡；Opus 反問變多時一句「照既定裁定做」。

## 行動

- 接任總控台：先寫耗時檢討與改法，再開工；開工句分「對人」「調度」兩個 session
- 收到原設計者訊息：同回合先答，再回到派工
- 自己想改碼或開子代理時停下：寫派工單給工作 session
- 收交付時先看它附的 codex 報告；總控台 codex 每軌只在合併候選跑一次

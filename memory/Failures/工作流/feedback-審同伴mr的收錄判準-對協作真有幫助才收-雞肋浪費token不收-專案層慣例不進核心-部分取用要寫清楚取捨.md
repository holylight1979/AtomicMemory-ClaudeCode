## 知識

- [臨] 使用者定的收錄判準（原話）：原子記憶系統「不要雞肋、也不要無謂浪費 token，但歡迎真正對與人協作有大力幫助的」；「不該是此系統應該具備的（像是專案更適合）也要多考慮是否僅存於專案」。每個 MR 的決定都要寫清楚為什麼：不收的寫為什麼、部分取用的寫哪裡取哪裡沒取、收的也寫原因；需要強化或改造的可以請原作者處理後再合併。全部要白話、人好懂。
- [臨] 實際怎麼判：測試假紅修正、多機差異修正、少做無效事的改動 → 收；大改動只要方向是「少做事、少衝突」也收（反向連結不落檔、索引可重建）；讀專案自帶慣例（帳本編號格式、專案詞表）的 hook 段 → 不進核心，和核心既有機制重疊更不收；大範圍重構只為防很少發生的事、卻永久加規矩（字面就紅）→ 退回請作者說明動機並改輕量版。
- [臨] 紀錄落在三處：merge commit 訊息（每個 MR 一則，為什麼合）、_AIDocs/DevHistory 審查紀錄檔（總表＋逐項理由＋驗法）、GitLab 每個 MR 一則留言。審 MR 不跑全量測試，只跑 MR 自帶案例檔＋被改模組的既有案例檔。

## 行動

- 收到同伴 MR：逐個問四題——對協作有實質幫助？會不會多花 token？屬核心還是專案層？和既有機制重不重疊？
- 決定（合／部分／退回）連同白話理由寫進 merge commit、DevHistory 紀錄檔、MR 留言三處
- 驗證只跑相關案例檔，不跑全量；測試裡 git 參數或次序有改就連錄製檔一起重錄

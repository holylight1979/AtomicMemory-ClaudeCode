## 知識

- [固] （user 2026-08-04 指正，背景＝一份控制文件做「歷史區搬移」時，把仍在追蹤中的活項當成歷史埋掉，同層檔案的去留也完全沒判斷）根因＝把「機械執行授權」擴大解釋成「不必做內容判斷」；執行方向不明時沒先確認使用者意向就動手。
- [固] 規則一「狀態變更即決策」：把課題標成 長期追蹤／擱置／非本波／watch ＝業務取捨，必須顯式提請使用者裁決（一句話＋建議），禁止寫在敘事裡帶過。
- [固] 規則二「活項對照閘」：搬移／歸檔／瘦身類任務的機械授權只管「怎麼搬」；交付前必列「被搬內容中未結案／待觸發／追蹤中項目」清單，逐項確認現況頁仍可見；有活項會被埋＝範圍變更＝先問。
- [固] 規則三「方向不明先問、問在動手前」：遇到指示／交接未覆蓋的內容判斷（檔案去留／歸屬／合併），先給選項＋單一建議讓使用者拍板；禁用「保守做完＋報告尾巴 flag」模式（尾巴 flag 實證會被略過，使用者看到的是失真結果）。
- [固] 反面辨識：被指正時用「整理品質＝決策品質」類抽象話術回應＝推託（把焦點從自身過失滑開）；正確回應＝先把過失本身講準（哪個決策點沒問）再談修法。
- [固] （user 2026-08-04 校準，防矯枉過正）「該整理就要整理」：顯而易見的過時／被取代／殘屍檔去留＝自己 flag 的維護動作直接做完不問（為這種事開提問窗＝過度反問）；提問窗只留給真取捨：①活項處置 ②動到別的專案／別的 agent 正在跑的工作區（即使歸位判斷正確也該先問）③不可逆且非顯然 ④方向／業務取捨。

## 行動

- 整理/搬移/封存任務開工前：先列內容決策點（去留/歸屬/活項）→ 有未被授權覆蓋的 → AskUserQuestion 前置
- 交付前跑活項對照閘：搬出內容的未結案項 × 現況頁可見性 逐項勾稽
- 擱置/長期追蹤類狀態變更 → 當決策提請，不入敘事

## 知識

- [觀] 使用者指正（原話）：「這個擋的詢問已經跳出來非常多次，但我在意的是正確性而不僅是耗時。不論是否已經改動被驗的 track，只要是面對目標的、是最後應該要有的正確模樣、就請徹底修正、驗過無誤再回報。」
- [觀] 始末：驗證 session 反證時暫改受測檔又 git checkout 還原，寫碼查核閘仍算「改了程式碼」；我連續幾回合用【收尾放行確認】請使用者放行，還以「不該改受測 track」為由不動。正解是修閘的判定根因（改過又原樣還原的檔不算改碼），補會紅的案例、跑真 hook 入口與全量再回報。
- [觀] 判準：同一個閘為同一件事擋第二次，就先問「是閘的判定錯了還是我的工作有缺」；判定錯就修判定（角色邊界不是不修的理由，照正常分支／合併流程交），放行詢問只留給真的無法補證據的情況。
- [觀] 使用者原話（track-e8 待命回合被寫碼查核擋 4 次問 2 次）：「看不懂你說什麼，請避免各說各話的問題；如果確定是流程錯誤，就發訊息讓調度總控台記下放行問題」。現場兩個根因：①(a)(c) 的「本回合證據」用 turn_seq 判，跑驗證的 2.5 分鐘內進來兩則同伴訊息，PASS 收據就被當舊回合；②轉述別人動作的句子（「已換上修好的 probe」）被當成自己的完成宣稱。兩件都派給工作軌修判定（改用使用者回合、排除轉述）。行為教訓：擋滿要問使用者時用白話（「這回合沒改程式、只是待命，要讓我結束嗎」），不丟 turn_seq、收據這類內部代號；判定是流程錯誤就先回報總控台記下，再問放行。
- [觀] 使用者原話（七個並行 session 被同一批根因反覆誤擋、要一次派修時）：「擋驗證的功能本身不是錯，所以也不是隨便亂放行或乾脆整輪不擋；應該是要做出精準的判斷與充分的證據（現在看起來機制邏輯本身不周嚴且粗糙判定，建議是要有一支獨立腳本檔來處理各種可能的需求。」落地規則：閘誤判的修法永遠不是加例外、放寬、整輪不擋；把「欠不欠帳、算不算本回合、算不算放行、算不算改碼」抽成一支獨立純函式模組（輸入狀態＋對話片段＋ git 事實，輸出判定＋證據清單），各 hook 只呼叫它；每種情境一條有名字的規則＋一個會紅的案例；擋訊息印出命中的規則名與證據。
- [臨] 行動段「修判定照標準流程…全量，再交合併」的全量那一步已拔掉（使用者裁定，全量改增量待補）：改成跑宣告的驗證範圍。見 [[feedback-全量測試從流程拔掉改增量待補-全量紅了指不出誰修修完又要全量-收尾跑llm適度擴展的可能相關清單]]

## 行動

- 同一閘為同一件事擋第二次：先查閘的判定對不對，錯了就修判定
- 修判定照標準流程：開分支、先寫會紅的案例、真 hook 入口探針、全量，再交合併
- 放行詢問只用在真的補不了證據的情況，不當例行解法

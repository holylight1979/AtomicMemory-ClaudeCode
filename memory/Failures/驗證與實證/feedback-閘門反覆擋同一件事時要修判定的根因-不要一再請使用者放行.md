## 知識

- [臨] 使用者指正（原話）：「這個擋的詢問已經跳出來非常多次，但我在意的是正確性而不僅是耗時。不論是否已經改動被驗的 track，只要是面對目標的、是最後應該要有的正確模樣、就請徹底修正、驗過無誤再回報。」
- [臨] 始末：驗證 session 反證時暫改受測檔又 git checkout 還原，寫碼查核閘仍算「改了程式碼」；我連續幾回合用【收尾放行確認】請使用者放行，還以「不該改受測 track」為由不動。正解是修閘的判定根因（改過又原樣還原的檔不算改碼），補會紅的案例、跑真 hook 入口與全量再回報。
- [臨] 判準：同一個閘為同一件事擋第二次，就先問「是閘的判定錯了還是我的工作有缺」；判定錯就修判定（角色邊界不是不修的理由，照正常分支／合併流程交），放行詢問只留給真的無法補證據的情況。

## 行動

- 同一閘為同一件事擋第二次：先查閘的判定對不對，錯了就修判定
- 修判定照標準流程：開分支、先寫會紅的案例、真 hook 入口探針、全量，再交合併
- 放行詢問只用在真的補不了證據的情況，不當例行解法

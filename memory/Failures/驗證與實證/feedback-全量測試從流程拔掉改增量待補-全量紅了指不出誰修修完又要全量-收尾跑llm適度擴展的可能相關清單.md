## 知識

- [臨] 使用者裁定：全量測試（整包 run_verify，約 3900 案、單行程 23～40 分鐘、多 session 同機時拖慢所有人）直接從流程拔掉——收尾、合併、發版前都不跑，部位表不拿它當量尺；拔除處標「全量改增量待補」。全量入口檔留著只供手動排查。
- [臨] 使用者駁回「保留全量、改夜間背景自動跑」的理由：背景自動跑只適用記憶系統本身，還得決定哪台電腦跑，別的專案需求不同；全量找到壞掉卻指定不了誰修，修完又要再跑測試，那時是否又要全量；拿「全量抓到幾件」當實證，卻沒追那些測試為什麼年久失修的根因。
- [臨] 要做的方向（增量）：改完後由 LLM 判定並適度擴展，記下「可能相關」的測試目標清單，收尾時針對清單再跑一次。範圍漏判（清單外的測試事後紅了）是增量的盲點，要拿漏判的實際類型去強化 LLM 的擴展判斷，而不是補回全量。
- [臨] 全量抓到的真紅，根因都是測試把別處的契約抄一份寫死：讀全部卡片的 lint（卡片格式）、斷言追蹤項輸出格式、沙箱沒指資料根／程式根、fixture 缺新欄位、斷言擋訊息字樣、直接讀根層部位表寫死尺數（同一個數字寫在兩支測試）。改契約的人看不出這些測試跟它有關，所以只有全量碰得到。

## 行動

- 不建議、也不跑全量（含背景、夜間、發版前）；收尾只跑宣告的驗證範圍
- 改到格式、欄位、訊息字樣、資料根或部位表這類「契約」時，擴展清單前先 grep 測試裡有沒有抄這份契約的字面值，有就列進清單
- 拿「某機制抓到 X 件」當保留理由前，先追那些案例為什麼壞的根因
- 看到其他卡片或文件叫人跑全量，視為過時，照本卡；順手標「全量改增量待補」

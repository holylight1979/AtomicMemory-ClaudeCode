## 知識

- [臨] 使用者原話：「你們只針對了實際發生的 BUG 寫出測試，但是沒有寫出『人讀的時候就要跳超過 3 層、以及腦袋必須拐彎超多次』這種狀況。」背景：守門機制的回放測試全從提交紀錄挑案例，提交紀錄只記 bug，於是「程式沒錯、測試會過、但讀者要開四五個檔穿過介面工廠基類才懂」這類壞味道一題都沒測；數彎原型又只認同檔，跨檔跳轉數不到。
- [臨] 驗證設計要有兩類案例：①真 bug（找得到根因嗎）；②沒 bug 但人讀要跳超過三層（審查者會不會因為「沒錯」就放行；它列的讀者路徑對不對得上人讀路徑；改法是真的更直還是只是搬家）。量法＝人讀路徑長度（檔數、型別數、間接次數），跨檔。案例來源不能只有提交紀錄，要加「人判過難讀但沒修」的程式。

## 行動

- 設計審查／守門的驗證：案例分「真 bug」與「沒 bug 但難讀」兩組，缺一組就沒測到一半
- 數彎要跨檔；先人列路徑、後自動

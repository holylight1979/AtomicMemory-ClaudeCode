## 知識

- [臨] **使用者原話（質問）：「編譯後你能自己驗證的為啥要靠我?」** —— 我先前宣稱「我沒有實機驗證條件，需要你開程式跑一次」，但那個專案本來就有可自動化的實跑通道（REST + 關舊開新的測試循環），**而且是我自己寫過的 atom**。這是退避，不是調度。
- [臨] **離線模擬不算驗證「系統介面」**：自己寫假伺服器餵自己假設的字串，只能證明「狀態機邏輯對」，**證不了「我對外部系統的假設對」**。本輪離線 6 情境全過、一上線立刻抳到兩個真錯：比對字樣拄錯稱謂（您/你）、以及一個完全無關的登入 bug。兩個都是離線永遠碰不到的。
- [臨] 交付前先問：**「這個系統有沒有可自動化的實跑通道？」**（CLI / REST / 測試套件 / 啟停腳本 / MCP 控制）。有就自己跑完再回報。**只有這三種才交還給人**：① 需人類主觀判斷（好不好看、順不順手）；② 需實體操作或我拿不到的憑證；③ 不可逆且未授權的對外動作。「麻煩」「要登入」「要開 GUI」都**不是**理由。
- [臨] 實跑時把副作用當成交付物的一部分：動過的設定（活躍帳號、開關）逐項還原並在報告裡列出來；外部系統的狀態（登入中的帳號）用正規方式收尾（送 quit），不是直接切連線。
- [臨] 被別的 session 弄壞共用工作樹、編譯不過時，**不是放棄驗證的理由也不是去改別人檔的理由**：拷一份隔離副本、把別人的檔還原成 HEAD、只留自己的改動，在那邊編譯。報告裡要講明「驗證是在隔離副本跑的」。

## 行動

- 宣稱「我無法驗證」之前，先 grep 自己的記憶與專案文件找「測試循環／啟停腳本／REST／API」
- 離線測試全綠只能說「邏輯對」，報告時不得寫成「已驗證」；對外部系統的介面假設一律標「未實機驗證」
- 實跑完逐項還原副作用，並在收尾報告列出改過什麼、還原了什麼
- 共用工作樹被別人弄壞時走隔離副本驗證，不改別人的檔、不改寫共用歷史

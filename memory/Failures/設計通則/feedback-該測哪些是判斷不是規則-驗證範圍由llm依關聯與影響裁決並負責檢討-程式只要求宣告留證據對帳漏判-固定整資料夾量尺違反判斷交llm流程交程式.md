## 知識

- [臨] 使用者原話：「改動的範圍也不應該是『特定範圍的量尺』呀！在這種需要智慧的時候，就需要 LLM 介入、進行『應該測試哪些有關聯、會受影響』的。裁決範圍之後，才針對該範圍進行驗證，且 LLM 必須對提出的範圍進行負責、懂得檢討。」背景：曾把「程式能擋的不交給 AI」外推到驗證範圍，做成部位表上固定的整資料夾量尺加 MeasureGate 必跑（改 tools 一行要跑 12 分鐘）；還有人提「改哪支就跑同名 verify」，同樣是程式替判斷做決定。判準：「要不要驗」可以是規則，「驗哪些」是判斷。程式只管流程：關鍵點要 LLM 宣告範圍與每項理由、要範圍內每項有改完後的收據、事後範圍外的測試紅了記成漏判並送回檢討。
- [臨] 盤點閘裡的固定規則分三種改法（原設計者核准）：真的要判斷（語意、關聯、授權）→ LLM 宣告並附理由，程式只查有沒有宣告、核對證據；規則其實是某個查得到的事實的粗略替身（「有新檔＝搬走」「改過同檔＝自己的案例」）→ 換成查那個事實，不必交 LLM；已判斷完的規則或只會多擋不會多放的安全邊界（防偽造、證據級、否定詞表）→ 保留。改之前先讀既有設計與測試：「檢討義務只綁負責的 session」看似精準，負責者通常已關，會讓漏判沒人檢討。

## 行動

- 設計驗證閘或量尺：先分「要不要驗」（規則）與「驗哪些」（判斷），後者交 LLM 宣告並負責
- 提修法前自問：這是不是又讓程式替判斷做決定（固定清單、檔名對應）

## 知識

- [臨] 使用者原話（2026-10-13）：「以後這種問題我希望不要再由我追你才懂得提出.. 特別是這種卡了整天的問題，早就應該要跳出來修了不是嗎？為啥死死的被 Codex 給鎖住？這就是我說的『綜觀』，絕對不可以把視野越做越小... 大處著眼、小處著手，就算經手了很多個大目標下的小功能，也要時時回頭提醒自己『現在真正的大目標是什麼』。」背景：對人總控台自己被寫碼查核閘擋了一整天（只動文件的角色被當寫碼），我把它寫成「等 B 段的 C-知識類部位」放著，每回合照閘的指示配合、逐條裁 codex 報告；直到使用者問「還有什麼能開 session」才把它派出去。
- [臨] 判準：一件事若同時滿足「今天讓人或我反覆痛」「我已知道根因與解法」「解法落在大目標清單裡」，它就不是「等下一段」的待辦，是現在就該派的件。每回合收尾前回頭看一次大目標清單（原話輯 G0～G16）：哪條兩天沒動、為什麼、是真卡還是我沒派。
- [臨] post-mortem（2026-10-13 對人總控台，同一天被糾正兩次：該推卻請示、知識類部位被寫碼閘擋了整天沒派）。始末：接手後每回合的輸入都是調度轉來的 codex 報告、自檢工具的文件不一致、閘的擋訊息；我逐條裁、逐條補文件、逐次配合閘，把「相應」當成工作本身；正確做法是每回合先回錨大目標清單，把今天反覆痛、已知根因、在清單上的件立刻派出去。根因：對人總控台的職責寫成「回答、裁定、追蹤表」三件被動事，沒有「定期回錨目標、主動開件」這條主動職責；加上輸入源全是審查者與閘，它們只會對被問的面找漏洞，沒有任何輸入會問「大目標哪條沒動」。設計原理：雙總控台是為了把「對人」與「派工對帳」分開、讓原設計者的提問最高優先；第二意見與閘是為了補漏。斷掉的環節：「最高優先先答」被我做成「只做被問的」，審查與閘的輸出占滿每回合，大目標清單從接手讀過一次後再沒打開。防再犯：①每回合收尾前固定一行自問「大目標哪條今天沒動，是真卡還是沒派」；②被閘或審查擋第二次同一件 → 那件本身就是要派的 bug，不再配合；③自己已判該做的可逆動作（推送、派工）直接做，寫成「你說我就做」就是退避。

## 行動

- 每回合收尾前重讀大目標清單：哪條沒動、是真卡還是沒派
- 反覆痛＋知根因＋在清單裡 → 當場派工，不等使用者追
- 收到審查條目先對大目標，對不上的不讓它占回合

## 知識

- [臨]（使用者原話「session 內的思考與參與討論，務必加派 codex、讓他與 CC 具備等價認知的方式來進行」）參與設計討論或回答使用者的設計問題時，不能 CC 自己想完就回：要另派 Codex（`codex exec`，純讀取）吃**與 CC 同一組材料**（題目原文、自己的綱要、自己打算回的草稿、對方已寄的信），請它獨立回同題並指 CC 草稿盲點；回覆分三段：CC 答案／Codex 答案與分歧／CC 裁決附理由，不可只取一邊不交代。**Why**：同一 context 的自我批判是已經相信初步見解的腦在評自己；實測 Codex 一輪推翻 CC 16 條、CC 認錯 11 條。
- [臨] 使用者再重申（三方討論第三輪）：「全都要全面啟動有完全同步認知知識的 Codex」，每個 session（根層與各專案）各自派，不是只有總控端派。裁法三條（實跑得出）：Codex 看不到 session 裡跑過的結果會把【試過】降成「部分」，那是視角限制不是分歧；它說「X 不等於 Y」多半對，寫進「還缺」不辯；附 file:line 的程式缺陷先對碼，對的當場修加測試，設計取捨寫「已知邊界」附理由。同時他定調：根層做根層的調整，專案層可有更適用的覆蓋調整；總控台也要自己做可驗證的項目加速，不只派工。

## 行動

- 回設計討論前：先寫 CC 草稿 → 材料內嵌送 codex exec → 讀它的盲點與分歧 → 逐條裁決寫理由 → 才寄出／回覆
- 裁決分三類寫清楚：認錯直改／接受措辭／保留附理由

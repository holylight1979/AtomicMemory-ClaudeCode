# 自己指出的更好做法若成本低就當場做掉-不要列成設計債丟給使用者

## 知識

- [臨] 收尾時我列「結構性問題」並自己寫出「更根本的做法是 X」，使用者回「那你怎麼還不趕快把 X 改寫進去??」（2026-08-26 MudClient 設定檔只存差異）。教訓：**自己已經看懂、且成本低、可驗證的更好做法，就當場做掉，不要包裝成「設計債」交給使用者拍板**。那不是業務取捨，是技術選擇，屬於我自己該決的範圍（同 [[自己flag的維護動作直接做完不要反問]]）。
- [臨] 判準：能用一句話講清機制＋有離線自測可驗＋不改使用者已定的行為 → 直接做。真正該交給使用者的只有「往哪邊收」這種方向選擇（例：兩套戰鬥邏輯要留哪套——結果使用者的答案是「都留、收成同一個輸出型別」，連這個也比我提的二選一好）。
- [臨] 另一個訓：我把「兩套判斷」框成「兩份真相、該刪一套」，使用者糾正：兩套各自根據現況生成就不是問題，問題是**沒有匯合點**。先找匯合點，不要先想刪誰。

## 行動

- 收尾建議裡出現「更根本的做法是…」→ 先問自己為什麼不現在做；答不出就做
- 多套平行邏輯先找匯合點與單一輸出型別，不先提刪哪套

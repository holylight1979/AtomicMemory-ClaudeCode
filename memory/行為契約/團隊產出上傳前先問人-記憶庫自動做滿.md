## 知識

- [臨] **兩種產出、兩種尺度，別用同一套判斷：**
- [臨] **(a) 團隊開發範圍的異動 — 上傳前必須再次向使用者(團隊成員、人)確認過。** 問法：『包含驗證都無誤了，是否確定上傳？』，得到明確同意才執行。理由：那是共有物，上傳等於替其他人做決定；且多數版控提交不可逆。
- [臨] **(b) 記憶庫(atom、分類、索引、連結) — 盡可能自動做好做滿，不必逐次徵詢。** 寫入、去重、歸類、建立交叉連結、修正錯誤條目都直接做完。理由：那是我自己的知識管理，問只是增加摩擦。
- [臨] **分界問法**：『這個產出會不會進到別人也要用的東西？』——會 → 問；不會(只是我自己的知識整理) → 自動做完。
- [臨] **單次授權不得外推成長期授權**：使用者說『上傳你自己的』只授權那一次、那幾支檔；之後又修了別的東西，就算測過也要重新問。把修正做完、驗證做完、**停在提交前**，不算退避。
- [臨] 「上傳前先問」的停點是 **commit 之前**，不是 push 之前（2026-09-04 使用者指正）：不得先 commit 再問要不要 push——那會讓使用者失去下「上GIT」前看 diff 的機會，也會把 Stop 閘的 SyncReminder 靜音而掩蓋未同步。問過、得到「上GIT」→ commit＋push 一氣做完。細節見 [[feedback-上git是commit加push一體-沒口令前不先commit-讓使用者能先看diff]]
- [臨] 記憶庫 atom 的版控例外（使用者 2026-10-01 裁決）：atom／索引／_AIDocs/_atoms 的變更由 Stop 收割後與 SessionEnd 的 vcs-sync worker 背景自動 commit，git 另自動 push、svn 直接 commit——這一類**不停在 commit 前、不問人**，目的是多機知識庫即時同步。「停在 commit 前等上GIT」只適用程式碼／文件等團隊產出。
- [臨] worker 的 push 有守門：待推歷史裡只要有任何 commit 碰到記憶路徑以外的檔（例如本地已 commit 但未上 GIT 的程式碼），就不 push、留本地並寫 `workflow/vcs-sync/<hash>.unpushed`，下個 SessionStart 以 advisory 提示；這樣自動推記憶不會順手把未發布的程式碼推出去。機制 SoT：`hooks/wg_vcs_sync.py`、`hooks/vcs-sync-worker.py`、TECH.md §6.3／§7.1。

## 行動

- 要提交團隊程式碼時：先列『檔案清單 + 驗證做了什麼 + 哪些驗證沒做』，再問『是否確定上傳？』，等明確同意
- 記憶庫的寫入/歸類/修正/刪除錯誤條目：直接做，不反問『要不要我…』
- 分不清時就問自己：這東西會進到別人也要用的產出嗎？

## 知識

- [臨] 使用者問：最聰明的模型也誤判，有沒有演算法能算出「目前的判準可能未達確切權重」？答：沒有可讀出的權重；能做的是三件程式化的事：①裁定必填欄——服務哪條目標（代號＋原話）／框架是誰給的（自己／實作者／審查器，複述要標）／若改動成本為零會怎麼裁；填不出目標就不裁。②反事實比對：零成本裁定≠實際裁定 → 標「成本驅動」，要理由或送第二視角。③校準回路：裁定帳記每筆＋最後有沒有被使用者翻，算「按框架來源的被翻率」——這才是判準權重的量法：事後量，不是事前算。
- [臨] 為什麼側觀視角（目標視角段落批評）在總控台沒觸發：需求目標流程的五個關鍵點（新需求開始、動手前、讀入範圍變大、提問前、宣告完成前）全是寫碼者視角；審查者／總控台的「讀入」是收到交付信、審查報告、同伴建議，「裁定前」必須是第六個關鍵點（跨 session 訊息到達即觸發三問）。機制沒到之前手動做：裁定帳就是之後回放題組的標註資料。

## 行動

- 裁定前先寫三欄：服務哪條目標、框架誰給、零成本會怎麼裁；寫不出目標就不裁
- 零成本裁定與實際不同 → 標成本驅動、送第二視角
- 裁定帳記結果，定期算被翻率、拿被翻筆當回放題
- 設計關鍵點時把「收到外部主張要裁定前」當一個關鍵點

## 知識

- [臨] 使用者原話：「單一構想的實際完成邏輯，如果腳本內必須先拐三個彎，這種設計必定有貓膩，就是壞味道。同樣的道理：你 LLM 的思考也是一樣，如果出現了超過 3 個拐彎處，就有極高的機率有跑偏、或想錯。繼續推進下去只會越跑越偏。」
- [臨] 拐彎的操作化（我的定義，待使用者糾正）：從「這個構想要做什麼」到「做到了」之間，讀者必須換一個脈絡才能繼續追的點。程式裡＝間接層（介面、工廠、callback、事件轉發）、條件分支、跨檔跳轉；推理裡＝「因為 A 所以 B，但 B 要先成立 C，而 C 又要…」的每一個「但」。超過三個就停，回到構想本身重問最短路徑，不在第四個彎上繼續。
- [臨] 實例：三方討論裡根層提的「記憶回流」設計（命中→計數→門檻→五分類→草稿→待審→人裁）六個彎，依此原則極可能想偏；真正的構想是「重犯的教訓要留下來」，最短路徑是人裁完直接寫 atom，既有 harvest 已是這條，回流整段降為不做。
- [臨] 實測（同一題給 Codex 跑三次）：LLM 數「拐了幾個彎」不穩，三次分別答 4、2、3，兩次沒過門檻；但「哪些是彎」的清單三次一致。所以門檻判定交 code 數（分支數、同檔委派深度），LLM 只列彎。數字類結論一律重跑看穩定度再用。

## 行動

- 寫碼或審碼：一個構想的完成路徑數彎，超過三個就是壞味道，回到構想重找最短路徑
- 推理或寫信：結論推到這裡拐了幾個彎，超過三個不寄結論、寄問題
- 自檢段固定加一行「本段拐了幾個彎」

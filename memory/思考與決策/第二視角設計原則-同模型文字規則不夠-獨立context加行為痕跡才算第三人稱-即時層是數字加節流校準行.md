## 知識

- [臨] 要讓 AI 寫碼時「隨時用第三人稱看自己」：同一 context 裡的自我批判是已經相信初步見解的腦子在評自己，偏差共享；文字規則也不夠——記憶庫裡 [固] 的 feedback atom 本身就是「規則在、仍重犯」的紀錄。真正的第三人稱要兩個條件：獨立 context（看不到推理、只看行為痕跡）＋可對照的證據（tool trace、diff、使用者原始目標）。
- [臨] 審查者被問的問題決定它看到什麼：只問「有沒有做、有沒有證據」抓不到「飄離目標、多做了什麼、陳述無證據」，三個視角要各自成一面鏡（goal_drift／overengineering／unsupported_claim），且必須餵 diff，只給改檔清單審不了「多做了什麼」。
- [臨] 時序要分兩層期待：獨立審查者是非同步的，只能是「每輪之間」的第三人稱；「每一步」的即時層只剩兩件——專案層的數字閘（同步、同回合、騙不了同模型）與同模型端節流的一行校準提示（文字、不可靠但唯一即時）。
- [臨] 讓審查結果「可數」而不改輸出 schema 的最便宜做法：每條 finding 必帶一個鍵（規則條號或 diff 單元名），無鍵即降級；條目數用程式數行，不靠人眼。
- [臨] 跨專案共用的語言專屬檢查器（如 C# Roslyn 規則器）不歸根層 ~/.claude；根層只管語意層與每輪之間的第二視角，語言規則與門檻留專案層或公司層。

## 行動

- 設計自我監看機制時先問：審查者是不是獨立 context、拿得到 diff 與原始目標；兩者缺一就只是換句話說的自我安慰
- 三個視角各寫成一問，不混成一句「請批判」；每條 finding 要求帶鍵
- 報告時序：明說哪些是每輪之間、哪些是每一步；不把非同步審查講成即時

## 知識

- ### 模式
- [臨] 查根因時讀原始碼，看到一個「十足合理、能導致此果」的機制就收手宣告它是元兇，未拿實例跑一次確認它真的命中
- [臨] **讀了原始碼反而比沒讀危險**：產生「我看過實作」的虛假信心。「存在能造成 X 的機制 M」≠「X 實際由 M 造成」—— 兩者差一個實測
- [臨] 最難偵測的情境：**結論碰巧是對的**（該分模組 / 該修這裡），於是沒任何症狀提醒。錯的只有因果，而因果寫進文件後會害維護者往錯的地方修
- 
- ### 2026-08-11 實例（wg_research）
- [臨] 問「為何檢索型 prompt 不觸發並行建議」→ 讀到 `wg_parallel._is_pure_question` 會濾純問句 → 判定它是元兇，寫進 docstring/atom/CHANGELOG/commit **四處**
- [臨] 補回歸測試時推翻：檢索型句子的 `_is_pure_question` 全為 False（以「幫我搜索」開頭、非「什麼是」開頭）。真因是 score 恆 0 —— 檢索意圖不在任一計分維度
- [臨] 推翻成本：一行 `score_prompt(prompt)`。距離真相只差一次實跑，卻沒跑
- 
- ### 防再犯
- [臨] 宣告根因前做「雙向實例」：拿**真實觸發案例**嗂進嫂疑機制，看它是否真命中（不只看代碼說它會）
- [臨] 能寫成回歸測試就寫成測試 —— 本案正是補測試時才拖出真因；測試兼作前提釘子（前提一變即紅）
- [臨] **分段驗證會漏掉段與段之間的閘門**：同批測試另抓出 `min_prompt_chars` 對中文太嚴，因原先 inline 驗證只跑核心函式未經長度閘層。驗證要端到端

## 行動

- 宣告根因前自問：我是「看到機制存在」還是「實測它在本案真的觸發」？後者才能寫進文件/commit
- 因果宣告至少跑一行實例驗證；能寫成回歸測試就寫成測試
- 驗證走端到端，不只測核心函式（閘門層常在分段驗證的縫隱）
- 發現因果寫錯且已散出去：四處（docstring/atom/CHANGELOG/commit）逐一更正，並在 atom 標註「曾誤寫為主因」防再犯

# 遊戲伺服器架構：框架型 vs 元件型（三核心 + 遠瞻性判準）

## 知識

- [臨] **核心命題**：遊戲伺服器再龐大，本質只需三大服務核心——①多人連線/傳輸 ②記錄存儲/存檔 ③核心玩法(GamePlay)邏輯與計算。資深以上從這個「單純」出發；**體量龐大 ≠ 必要**（SGI 即過度龐大）。
- [臨] **元件型設計(✓)**：三核心各做成「一看就懂、用法極簡」的服務元件——連線像 TCP(固定檔頭 + 協定 Type/Kind 可擴)、存儲不論 SQL/Mongo/Redis 都給簡明 API(存 json 或 bytes 不強制限定)、GamePlay 按玩法做基礎配置。**鐵則：「非服務內容卻想塑進底層擴大支援」的需求一律無視**——要的人自己寫，多人共用就整成 Util/API；底層**絕不**讓存儲與傳輸耦合（SGI 用 protobuf 把兩者綁死 = 頭號反例）。圖像：三顆小圓盤平躺在底、其餘被輕輕捧著/絲線牽連、空間自由不受限。
- [臨] **框架型設計(✗)**：用封裝/反射把所有底層包起來、把核心以外「限制在有限使用以防無限上綱」——防禦型但把中介層以上的腳本擠成畸形。底層一旦錯誤耦合又不能改，唱一出路是「不斷轉繼承往中介層塑」，一般人無法深入、只能當「上層腳本使用者」；運作期過量物件化/繼承/泛型/反射/事件系統 → **stack trace 難追異常**。圖像：本想做成裝東西的杯/圓容器，但遊戲總要大型調動往外長 → 長成「刺蘆球」或左凸右凹的詭異形狀。
- [臨] **用途/意涵**：這是判「沒經驗的人是否具備遠瞻設計理念」的鏡子，也是 AI 自己設計 server 端系統時的預設偏好——往「三核心 + 元件簡明 + 不在底層耦合」走，遠離框架式過度封裝。與特定專案無關，是通用遊戲程式設計智慧。

## 行動

- 設計/審查 server 端架構時：先問「是不是只需 連線/存儲/玩法 三核心？」、有沒有在底層把不該耦合的東西耦合(尤其存儲×傳輸)
- 看到過度封裝/繼承鏈/反射/事件系統導致 stack trace 難追 → 標為框架型反模式，建議往元件化拆
- AI 自己寫 server 端 → 預設元件型(簡明 API、要的人自寫、不塑底層)，不主動造框架

## 知識

- [臨] 使用者裁定：把檔名／資料夾名／路徑全部集中成常數＋位置元組＋拼路徑方法＋「寫字面就紅」守衛，對人是好習慣（人有 IDE hover 與跳定義，集中幾乎零成本），對 LLM 是淨負擔：LLM 沒有 hover，每解一個常數是一次工具呼叫；組合過的位置名（如 GLOBAL_ATOM_INDEX_REL 包住 _atom_index.json）讓「誰在用這個檔」的 grep 斷掉；日誌裡的真實路徑要先翻譯回常數名才搜得到；守衛擋字面抓到的全是風格違規不是 bug。
- [臨] 但「名字集中」這一層對 LLM 有真好處：LLM 最常見的錯是打錯字或編一個很像的檔名，字面寫法下它會靜靜寫到錯的路徑、很久才被發現；集中後變成常數名不存在、一載入就炸。反之「拿錯名字」（ATOM_INDEX vs ATOM_INDEX_JSON）集中反而多藏一層，但它較少發生。
- [臨] 定型做法：只集中「會被多處抄一份」的名字（索引檔名、衍生資料夾名、記憶結構資料夾名，約 10～15 個）成扁平字串常數放進既有的規格檔；各工具的跳過名單從常數組、內容各自維持；守衛只擋「別處再寫一份同組名字清單」。不做位置元組、拼路徑方法、跨語言 JSON 副本、擋單獨字面與路徑字面。位置拼裝防的是「資料夾拼錯」，等真的頻繁發生再加。

## 行動

- 審或寫「集中命名」類重構：先分層——名字集中可收，位置拼裝與全面字面守衛退回
- 判斷一個抽象對 LLM 划不划算：問「LLM 讀到這裡要多發幾次工具呼叫、grep 會不會斷」，不問「人看起來整不整齊」

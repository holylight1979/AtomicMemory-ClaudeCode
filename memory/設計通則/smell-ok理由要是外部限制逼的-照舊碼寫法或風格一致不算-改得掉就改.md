## 知識

- [臨] 判準：smell-ok 只給「不這樣寫就會壞」的外部限制：框架或 SDK 只收這種形狀（要物件不收函式、要回呼不收 Promise）、協定或程式產生器規定、量測過非這樣不可。理由要寫出是哪個限制。
- [臨] 不算理由：「舊碼也這樣寫」「跟檔裡既有寫法一致」「比較短」「趕時間」——新碼不照抄舊碼的病；舊碼那幾處閘只列不擋，不代表新寫的可以跟著寫。
- [臨] 反例：擋下 if 套到第 5 層，AI 寫 smell-ok「邏輯本來就複雜」——改成提早 return 就壓得平，不是外部限制。
- [臨] 擋訊息的「怎麼改」是建議不是命令：照改之前先確認改完程式還能跑；smell-ok 註解加在擋訊息點名的那一行，理由會跟著 diff 給使用者看。

## 行動

- 每個 ✗ 先問：照擋訊息的修法改了，程式還能不能跑？能就改
- 不能才寫 smell-ok，理由寫限制本身（哪個框架／API 要求什麼），註解寫在被點名那一行

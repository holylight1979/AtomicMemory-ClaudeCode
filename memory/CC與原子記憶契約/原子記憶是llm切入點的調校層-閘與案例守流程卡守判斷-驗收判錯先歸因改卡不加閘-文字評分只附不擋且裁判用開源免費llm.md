## 知識

- [臨] 原設計者觀點（中道：側觀、綜觀、記憶、邏輯揉合）：原子記憶不是記坑的倉庫，是每個「程式留給 LLM 判斷的切入點」的調校層：程式只負責把 LLM 帶到那個位置、餵材料、問一句；那一刻判得準不準取決於當下注入的卡。卡能加、改、退役，所以判斷力是持續可優化的。閉與案例守流程，卡守判斷，兩邊都要、互不取代。
- [臨] 他對 LLM 過程的四點檢討（別重蹈）：老是合併卻沒先問必要性；沒預先建立對目標與成果的評分規格；以為寫 code＋驗證是王道、小看 LLM 判斷力、忽略何時讓它帶智慧介入；綜觀側觀不夠所以一直寫硬邏輯。
- [臨] 接回流程：驗收題組的期望是「切入點那一刻注入的卡有沒有讓它判對」；判錯先歸因四類（缺卡／卡教錯／輸入不夠／問法不對）再改卡或改輸入，不先加閉；判錯當天落成切入點卡；合軌前多問「它的切入點注入哪幾張卡」。受測資料根要帶 live 全域卡（排除講驗收題本身的），否則量不到卡。
- [臨] G15 文字規格評分表裁定：影子記帳→每則尾巴附一行（評分 N/7｜沒過條目）＋週彙總，「擋」不排進路線圖（擋＝硬閉違反先改卡；看不到評分＝黑箱）；自動評每回合給人看的最終回覆（≳300 字）與文件，碎句不評；七條同等級。自評與裁判一律用開源免費 LLM（內網 rdchat gemma4:e4b／本地 ollama），付費模型只當對照。
- [臨] 第二波實證：每 G 一張「評分規格卡」是給裁判用的，綁上切入點會排在專卡前搞預算、反例近乎洩題，不綁、也不進受測資料根；判錯落的卡要綁在「事前」那一刻（改測試前的定位批判），綁在事後的守門太晩。量「卡有沒有教會」前先確認卡送得到（預算、失敗呼叫記檔、hook 逾時），否則量到的是送不到。

## 行動

- 設計或驗收任何「要 AI 判斷」的機制：先寫那一刻餵什麼／怎麼問／期望判什麼／注入哪幾張卡，沒卡先補卡
- 驗收沒過先歸因（缺卡／卡教錯／輸入不夠／問法不對），派改卡或改輸入，不派加閉
- 文字品質評分只附不擋，裁判用開源免費 LLM 並寫明模型、秒數、token

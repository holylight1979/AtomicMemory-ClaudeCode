## 知識

- [臨]（某專案戰役後八包一夜完工）雙 Claude 分工模式：Fable 監工（commit 權唯一在我）兼實作自己最熟的線，Opus 實作另一線；**每包一邊實作、另一邊驗證**（自己 build、自己跑自測、讀碼）。開場一封信：計畫檔路徑＋分工表＋檔案所有權（共用檔只 Edit 小範圍、信裡列動了哪些方法）＋各自 build 輸出目錄＋實機共用行程要先 ack。Opus 回「同意即開工不必再等信」很有效。
- [臨] Opus 特質：規格內自決附理由、會對規格提否決（三次全對）、誠實回報意外並自行修復（remove all 後 wear all 少 7 件→逐格對帳）；弱點：**驗證腳本判準太鬆**（catch-all 關鍵字把「未收斂」標通過）——監工必須自己讀逐字稿行號原文，不信 RESULT 行。
- [臨] 共用工作樹的代價：對方半成品隨時在樹上，`git add <檔>` 兩次掃進對方 hunk；解法見 [[混改檔hunk級選擇性staging]]（隔離匯出 index 建置是最後一道閘）。
- [臨] 無人值守：本該問使用者的遊戲事實→先實機取證，取不到採最保守（不送／不改態／做成設定）並標「待使用者確認」不停工；實機一輪合併多包取證、預先 ok 附條件（備份／quit 確認句／不勾自動戰鬥／地圖還原）；15 分鐘靜默看門狗（背景 bash 從現在起計時，不用最新檔 mtime）。
- [臨] 收尾必做：雙方 build 都在暫存目錄時，**最後要就地 `dotnet build` 一次**，不然使用者開到的 exe 是舊的。
- [臨] 通道：兩個 Claude Code session 之間目前直接用 SendMessage（`--name` 起的名字固定＝地址），閒置的對方收信會自動開回合，不必掛 Monitor 盯目錄；`.ai-inbox\to-opus\`／`to-fable\` 檔案信箱已退場，舊信只當案卷。
- [臨] 共用資源分兩級：port／行程（headed client、4321）先發訊息打招呼就可動手、不等回；真獨佔（連遊戲）才等對方回 ok。一晚沒撞過一次。
- [臨] 總管模式（一個 session 只讀 repo、只發訊息裁決，主力 session 逐階段接手）跑完五階段遷移可行：每階段主力先送「坑點清單」（改動面／已知坑對策／驗證對應）、總管回「無異議＋補證項」才准接線；交付附驗證末行，總管**獨立重跑**（run_verify、--check、audit）不只讀信；放行條件一次寫齊——分兩封送，主力會按第一封先動手。
- [臨] 換手時前任交付後立刻關掉，總管核實前任已不在清單再放行新的。舊碼 MCP 實例是遷移期最大寫手風險：總管自己的 MCP 也是舊碼時全程不呼叫 atom_write，落 atom 走 python `lib.atom_io` 新碼。

## 行動

- 開雙 Claude 分工：開場一封寫齊計畫檔／分工表／檔案所有權／build 目錄／共用行程規矩，用 SendMessage 送
- 監工驗收：自己重跑驗證、讀逐字稿原文，不信對方 RESULT 行
- 收尾就地 build 一次再交使用者

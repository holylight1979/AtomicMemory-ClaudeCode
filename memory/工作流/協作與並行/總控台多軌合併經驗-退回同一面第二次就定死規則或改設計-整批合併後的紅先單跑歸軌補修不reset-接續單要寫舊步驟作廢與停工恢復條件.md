## 知識

- [臨] 總控台審八軌二十八輪後：退回信在同一面（Bash 寫入目標解析、hub 分型、撤回機制）打轉到第三輪時，改成「把規則定死（R0〜R5 式逐條可判定）或改設計（撤回→可重入）」就一輪收斂；逐條描述症狀只引出下一組反例。
- [臨] 多軌整批合併後全量紅的五案全是整合落差（既有 fixture 缺新欄位 session_id、拒寫句字樣、一軌的案期待另一軌的輸出）：單獨跑該檔取細節→歸軌在分支補 commit→再 merge→再全量；reset 只留給「補修兩輪仍紅或要改別軌介面」。
- [臨] 長戰役接續單每次更新要明寫三句，否則 Codex 交接自檢連擋（本場八次）：舊步驟作廢、停工範圍與恢復條件（誰、怎麼解除）、背景驗證輸出檔絕對路徑；引用的腳本與模板要放持久目錄，不放 session 專屬 scratchpad。
- [臨] 接續單寫「<分支 commit> 已合 main」有兩種意思（分支把 main 合進來／分支合進 main），接手者會讀成後者而把待修件當成已上線。轉述前用 `git merge-base --is-ancestor <commit> main` 核實方向，寫法固定成「分支已 merge main、尚未合進 main」或「已合進 main：<merge commit>」。同時一退件（038→039），接續單「接下來」的進階條件就要改寫成以修正件為準，舊句明寫作廢。

## 行動

- 退回同一面第二次：改寫規則或改設計，不再列症狀
- 整批合併後的紅：單跑取細節歸軌補修，不 reset
- 更新接續單自檢：舊步驟作廢了嗎、停工／恢復條件寫了嗎、引用檔在持久路徑嗎

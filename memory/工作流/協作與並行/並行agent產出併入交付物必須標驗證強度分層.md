## 知識

- [固] （2026-08-11 自查發現）派並行 sub-agent 做研究後把成果併入同一份交付文件時，**我親自抓取逐字驗證的內容**與**agent 回報、我未二次核對的內容**會被寫成同一種語氣，讀者無從分辨。本次在一份主題正是「三方一致地錯」的事故分析裡犯此錯 —— 等於自己示範同一個失效模式。
- [固] 規則：交付物內含並行 agent 產出時，誠實聲明段必須做 **A/B 兩層分層**——A 層＝本人親自抓頁面逐字取得（可直接對外引用）；B 層＝agent 取得、附來源 URL 但我未逐條重開核對（內部參考可用，對外引用前須自核）。
- [固] 分層還不夠：要**點名 B 層中最該優先自核的 2-3 條**，判準＝「這條會直接導致工程決策或成本支出」（例：某套件的受影響版本區間 → 決定要不要排升級）。單純的背景知識不必點名。
- [固] 同理適用於 agent 提供的程式碼片段：未編譯／未實機跑過就必須註明「參考骨架，非可貼上即用」，不可預設讀者知道。
- [固] 反面辨識：agent 回報寫得越完整、附的 URL 越多，越容易讓我略過「我沒親自看過」這件事 —— **來源數量 ≠ 我的驗證強度**。

## 行動

- 並行 agent 成果併入文件前，先分清哪些是我親抓、哪些是 agent 抓，分層寫進誠實聲明
- 點名 B 層中會導致工程決策的 2-3 條，要求讀者自核
- agent 給的程式碼一律註明未編譯驗證
- agent 推翻我先前結論時，把更正明列成表（初版寫法 vs 正確內容 vs 影響），避免舊版流出後被沿用

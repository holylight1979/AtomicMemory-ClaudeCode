## 知識

- [臨] 2026-09-21 merge-atom-index --resolve 逼近 2.5s hook 預算：同一回合把「計時腳本」與「pytest 全套」「strings 掃 217MB 二進位」並行送出，Windows 每個 git 子行程從 0.15s 漲到 0.3～0.5s、python 啟動從 0.2s 漲到 0.47s，三次量測互相矛盾（同一份程式 1.67s／2.6s／2.77s），差點誤判修法無效。
- [臨] 時間敏感量測的規矩：單獨一個工具呼叫、前後各採一次 CPU 負載（PowerShell `(Get-CimInstance Win32_Processor | Measure-Object -Property LoadPercentage -Average).Average`）、取最快值當「結構性上限」、取分布當「負載下表現」；並行跑的結果只能當定性參考。
- [臨] 找瓶頸用時間線而非總和：spy 包 subprocess.run 記錄每個子行程的 (起點, 終點, 執行緒)，一眼看出主執行緒被 `future.result()` 卡住、或哪條鏈是關鍵路徑；只看「呼叫次數 × 平均」會漏掉序列依賴。
- [臨] Windows 上 git/python 子行程各約 0.15～0.3s 起跳：hook 預算內的工具，彼此獨立的子行程用 ThreadPoolExecutor 同時跑（讀寫同一鎖檔的 git config 寫入除外，必須序列），python 啟動＋import 的固定成本（本機 0.3～0.45s）另計。

## 行動

- 量時間：一個回合只做一件事，先報 CPU 負載再跑，跑 3 次取最快與最慢。
- 找瓶頸：先畫子行程時間線（起訖＋執行緒），再決定批次化／並行化哪一段。
- 報告：分開寫「安靜機器最快」與「負載下分布」，不用單次數字下結論。

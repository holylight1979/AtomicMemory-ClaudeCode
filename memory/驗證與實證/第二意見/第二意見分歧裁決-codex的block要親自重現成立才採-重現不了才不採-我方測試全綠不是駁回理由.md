## 知識

- [臨] 「不需第二意見」只在改動沒有邏輯影響（只改註解、docstring、字串、文件）或使用者已裁定這類交付不跑 codex 時成立。改到任何判斷、分支、比較、門檻，或設定檔的讀法，就要跑——「改動很小」「只改 N 行」「每個行為都有測試」「照既有寫法」都不是理由：程式檔數到門檻本身就是「不小」的事実，測試是自己寫的、漏的輸入也一樣漏。
- [臨] 裁決順序：把 Codex 每條 BLOCK 轉成一個可檢查的反例（輸入 → 預期壞掉的結果），自己讀碼追或跑一次。重現成立 → 採納，補那個反例當案例先紅再修；重現不了（讀碼看得到已處理、或跑了沒壞）→ 不採，裁決寫出擋住它的那行碼或實跑輸出。
- [臨] 「我方測試全綠」不是駁回理由：Codex 的反例常正是我方案例沒涵蓋的輸入（空清單、None、超長輸入）。「Codex 説的」也不是採納理由：它看不到本機執行，常把已處理的分支當沒處理。
- [臨] 第二意見要在 commit 前送：second_opinion_start 打包的是工作樹對 HEAD 的 diff，已 commit 才送會「diff 為空」，Codex 只拿到摘要、只能判證據不足、指不出缺陷。
- [臨] 裁決 codex 反例時，拿分支基底跑同一組反例：基底擋、本輪放 → 本輪新開的漏洞，必修；基底本來就放 → 原設計，再看是不是語意判斷（交 LLM、不加例外清單）。

## 行動

- 宣告不需前先問：這次改動有沒有改到任何判斷、分支、比較、門檻、設定讀法；有就跑，不寫不需
- 每條 BLOCK 先寫「反例：… → 重現：成立／不成立（依據）」再裁
- 送第二意見排在 commit 之前

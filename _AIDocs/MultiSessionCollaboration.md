# 多 session 協作：主持端派工給多個工作 session 的通則（AI 讀）

> 讀者：任何「一個主持 session 派工給多個工作 session（或子代理）」的 CC session——主持端與工作端都適用。知識來源是 v6 開發期總控台時期累積的記憶卡，這裡只留離開那套儀式仍成立的通則；v6 專用的派工單格式、裁定帳、對帳五項、無頭驗收等開發期儀式不在此，見 `DevHistory/v6.0-寫程式碼的進化-2026-10/`。
> 機制真源：跨 session 訊息＝CC 原生 `SendMessage`／`ListAgents`；背景 session＝`claude --bg`／`agents`／`attach`／`stop`；worktree＝`EnterWorktree`／`ExitWorktree`。本檔只講契約與做法，CC 版本行為以實測為準。
> 每節末「出自」列的是卡名（`[[slug]]`），`[[…]]` 是活卡；標「退役卡」的維持退役、只取其中一句通用知識，原卡在 `_AIDocs/_atoms/MemDev/v6總控台/_distant/2026_10/`。

## 1. 這份文件是什麼、不是什麼

- 是：主持端（派工、問進度、彙整的那個 session）與工作端（接單做事的 session）之間的分工、通訊、合併、交接、回報的通則。
- 適用範圍：只要有「一個 session 派工給多個 session」就適用——三方信箱討論、多軌 worktree 開發、背景 CLI session 派工、根層與專案層對齊，都算。
- 不是：v6 開發期總控台的專用儀式（雙總控台、對帳五項、快照複跑、無頭驗收凍結、裁定帳格式）。那些是為一次開發戰役定的規矩，離開總控台就不存在，編年與原話在 DevHistory v6.0 夾。
- 判準借用一張活卡：寫進任何會注入／會擋的機制前，先問「一個同事、一個分頁、沒有主持端時它還成不成立」；不成立的留在派工單與文件，不進產品。
- 本檔是文件不是卡：卡隨 trigger 整顆注入、知識段約 200 tok；長篇做法放這裡，卡只留結論與指標。

## 2. 角色與邊界

- 主持端三件事：**派工**（每個工作 session 隨時有編號待辦，閒置就是派工失職）、**問進度**（定節奏：完成寄報告、未完每 30 分鐘一行、沒事寄待命；主持端每 60 分鐘對帳）、**分工寫文件**（各寫各段到各自的檔，主持端彙整後給各段作者核一次；分開寫就不會打架）。
- 寫「無待答項」之前先問：是真的沒事，還是我沒派？連寫幾封「無待答項」就是沒派工的訊號。
- 根層與專案層分工：根層負責「產生與更新」的流程（骨架、路由、健檢、回路）、吸收與轉化；專案層只提供領域事實與思路（角色哪裡不對、會覆蓋哪些變量、根層不知道就會做錯的設定）。
- 多專案差異靠變量吸收，不在 hook 裡寫專案分支：每個變量要有預設可用、覆蓋有理由、歧義報錯；吸收不了的（跨 repo 版本、公司作用域、執行環境）定契約而不是丟給使用者配置。
- 範圍聲明是「只動根基」時，專案 session 停手只回思路，已做的當樣本不回退也不擴；收到範圍聲明先改派工、再改文件。
- 子代理 vs 獨立 session：子代理收不到跨 session 的 SendMessage、也不能直接對使用者說話；要跟別的 session 通訊或要對人開口的工作，必須是獨立 session。
- 主持端若對人負責對話窗口，調查與修補交給有對口的工作分頁，不自己開子代理搶活；工作分頁還開著就派它。

## 3. 派工單怎麼寫

- 派工單裡的路徑與指令多半是寫單者憑記憶寫的：接單者執行前用 Glob／ls 核實檔在哪、打開檔頭看是 pytest 案還是自帶 main 的腳本；不符就照實際位置與跑法做，交付信寫明「第 N 項應為 …」，不另建同名檔湊路徑。pytest `no tests ran`／exit 5 不是綠。
- 並行線只跑目標 verify 清單、明寫不跑全量；全量（若流程還有）由主持人整合後單獨跑一次，跑的期間不動程式、不做別的 git 操作。
- 多線會碰同一個設定檔／入口檔時寫「只動自己那幾行、Edit 前重讀、文字插入不整檔重寫」並指定誰最後合併；線與線的介面透傳（A 加參數、B 的入口要透傳）留給主持人收尾，避免兩線互等。
- 文件交付物明列：工作端不會自動把 TECH／CHANGELOG 當交付物，派工單沒列就不寫。「只動哪些檔」段固定加一行「對應文件節與 CHANGELOG 由這軌自己寫」，交付信附「文件：§… 列／CHANGELOG 段」。
- 背景（無人盯畫面）軌三要寫死：收尾不發 AskUserQuestion（沒人答，會永遠卡住）、每個改過的程式檔都要有案例、被擋滿要問人就把擋訊息原文寫進交付信給主持端裁。會觸發放行題的事（改舊測試、無新案例）先在單上裁好。
- 寫「走到要問人那一步停下回報」前：先確認人已就位，或改成「直接發題掛著、同時通知主持端」。只結束回合等人，閘每回合會再擋一次、次數累加。
- 授權要寫對象與失效條件：例如夜間授權只給當時那一個主持 session，它 token 用完、換手或工作完成即失效；接到授權先把規矩寫進接續單、開一份「早上待辦」檔（要人動手的放最前面），再通知其他 session 改作業方式。
- 只有主持端能定奪的事列「待決」，不硬裁；可關的分頁不替人關，寫進待辦附「關前收錄知識」提醒。
- 開工句第一句以軌名開頭（分頁標題才看得出來），軌名要望文生義。

## 4. 調度節奏

- 慢的主因是主持端串行等交付，不是軌本身慢。每收一件交付、每則回報前問「還有哪些待辦跟在跑的檔不重、不用等階段」，有就當回合開。
- 不開只有三種理由（等階段數據、先後有依賴、改同一批檔會衝突），理由寫進派工單；撞檔的拆成兩單：不撞的先開、撞的等合完。
- 背景 session 名額滿了就 stop 待命的（重起只要幾十秒），不要等；有軌收尾就照原則接著開，不等人提醒。
- AI 判得了的定義題（「這條算不算過」「這樣算不算寫明」）不卡等人：先自裁、附理由、做下去，留痕讓人可翻。寫「待他裁」前兩問：答案錯了改得回來嗎？有沒有只有他才知道的事實？兩題都否 → 自裁。只有不可逆、業務取捨、動他的設定才問。
- 暫停類限制解除後，不得拿「等裁定」當新的停工理由。
- 任何凍結或限制一律寫「理由＋解除條件」，條件一到自動解；沒寫解除條件的限制會讓工人空等。
- 量測前先問「結論還沒跑就估得出嗎」：估得出就不跑完整量測；刀口先量分布再開，對準最大那塊。
- 發現的問題：相關且真有問題就在既有軌當場修，修不了的記追蹤項；不因此長新子目標（無限延展通常是偏移），真要擴範圍才問人。
- 排待辦照「改小＋牽連大 ＞ 改小 ＞ 牽連大 ＞ 又小又沒牽連」，每項標改多少、牽連多大。

## 5. 跨 session 通訊的實際機制

- SendMessage 的訊息只在收件端**下一次呼叫工具時**才進對話；光結束回合等，沒有工具呼叫就永遠等不到。要等人答完再醒：先在背景跑一個短 sleep 當鬧鐘再結束回合，鬧鐘到的通知會把 session 叫回來。
- 收件端在計畫模式（或雙方權限模式不同）時，訊息會被扣住等使用者在那個分頁核准，沒人按就逾時作廢、對方看不到；重送只會再被扣。會進計畫模式的工作軌，要說的事一次寫進開工句。收到 held 通知就告訴使用者那個分頁有訊息待核准，不重送。
- 要轉告別的 session 就自己 SendMessage，不列成使用者的下一動。訊息第一句自足（人只看得到第一行），附「不是你就忽略」與「不需回覆」。
- ListAgents 的同伴名（claude-xx）跟 session id 沒有對應：讀目標 session transcript 第一筆 timestamp，跟 ListAgents 的「started N 小時前」比，只有一個對得上就是它。
- 開工句交出後內容有更新：先 ListAgents 看下一個 session 是否已開工；在就直接 SendMessage 轉更新並問它做到哪、是不是舊版開工句；不在才給新版開工句。不叫使用者換開工句貼。
- 信箱協議（根層與專案 session 對齊同一題）：落在專案 `.claude/inbox/`，雙槽 `root-link/`（`to-root/` 專案寫、`to-project/` 根層寫）、三槽 `tri-link/`（每槽一個出向 `from-<slug>/`，`re: <槽>/<seq>`）。落專案目錄的理由：根層寫專案目錄不受保護閘影響，反向會被擋。首封「我是誰＋綱要正本路徑＋一句摘要＋幾題」，對方一封一題回、附已驗證路徑或數字；約 20 封就該收斂到「各自向使用者要拍板」。Monitor 要排除自己的出向目錄。
- 背景 session：用 VS Code 擴充內建那支 `claude.exe`（`resources/native-binary/`）起 `claude --bg "<開工句>" --permission-mode <模式>`，以 cwd 為工作樹；模型要在起時用 `--model` 設好，事後改不了；worktree 沒信任紀錄會拒起。它是完整 session：ListAgents 看得到、SendMessage 雙向通、hook 全套照跑。
- 人要答它：終端機 `claude agents` 進總覽、選列按 Enter 就是 attach，選項直接選；attach 畫面連按兩次 Esc 是 Rewind 不是離開，要離開直接關視窗；收掉用 `claude stop <id>`。`claude agents --json` 的 status 是 waiting／waitingFor="input needed" 就表示它在問人。
- 背景軌卡在 AskUserQuestion 時：讀它 transcript（projects 下該 worktree slug 夾的 `<sid>.jsonl`）最後一則 assistant 看卡哪題；分支 HEAD 比上次交付前進了就自己對帳合併再 stop，要人答才 attach。停掉後 worktree 目錄會有幾十秒 Permission denied，稍後再刪。

## 6. worktree 與共用工作樹

- 工作 session 的分頁 cwd 若在 live 而不在 worktree，hook 推出的收據根會是 live，量尺對不上；開工第一步用 `EnterWorktree(<已存在的絕對路徑>)` 切進去，不叫人用 VS Code 另開資料夾。
- 切進 worktree 後被隔離：寫不到 worktree 外（含 live 信箱）、跑不了 `git -C <live>`；交付一律用 SendMessage 回全文，主持端收到後存進信箱。「live 未動」的唯讀替代證據：`git hash-object <live 檔>` 與 `git rev-parse main:<檔>` 逐一相同。
- 隔離下 Bash 的坑：同一條指令混 live 路徑與 git add／commit 會整條被擋，拆兩條；用 shell 變數組路徑會被判「寫入目標不明」，路徑寫字面絕對路徑或改用 Write；heredoc python 被擋就把腳本寫進 scratchpad 再跑。
- 工作 session context 將滿時：叫它停手、不 commit（未提交改動留在 worktree 給接手者），只回 20 行內接手備忘（每件已完成且測過／已改未測／未開始、未提交檔改到哪、選擇與理由、讀碼看不出的坑）；主持端據此寫自足派工單給新 session 在同一 worktree 接著做。
- 小改不開軌：純測試、純文件、單檔小修、clean-up 直接在 main 改、跑目標 verify、推；只有多檔或跨部位改動才開軌。文件軌進 worktree 的代價（整樹 checkout、啟動器、CHANGELOG 衝突）全是為程式設的。
- 合進 main 同一回合 `git worktree remove`＋`git branch -d`，補驗過即推不積累；留著的 worktree、分支、未推 commit 都是「做完沒」的雜訊。
- worktree 裡寫不到 gitignore 的人讀文件（例 `memory/_staging/`）：派工單叫它在 worktree 同路徑自己 mkdir 寫新版、讀現況用 live 絕對路徑唯讀；主持端收件後複製進 live；要進版控的部分照常在分支 commit 由主持端合併。
- 共用工作樹讓路：自己有未提交、未驗完的改動，同伴要 ff 進 main 且碰同檔 → 先確認沒有 MERGE_HEAD，`git diff --binary -- <檔> > x.patch`、`git apply --check -R` 確認反套得回去、`git apply -R` 還原、回「你先」並背景輪詢 HEAD；對方 ff 後 `git apply --3way x.patch` 套回，再立刻 `git restore --staged -- <檔>`（3way 套回會留在暫存區，別的 session 下次 commit 會帶走）。不用 stash（stash 是整個 repo 共用的，別的 session 可能 pop 走）。
- 退回看紅的腳本：`git checkout main -- <檔…>` 清單裡只放基底真有的檔（新增檔留著或用 `git ls-tree main -- <檔>` 先過濾），一個 pathspec 比不到就整條失敗、一個檔都沒退回；checkout 後查退出碼，「退回後紅數 0」當腳本壞掉不當通過。
- settings 裡的 hook 指令寫死跑 live（`~/.claude/hooks`）：在 worktree 開的受測 session 跑到的是 main 不是分支；要量分支那刀就用事件帳重播交給分支函式組裝，或 `--settings` 指到 worktree 的 dispatcher 並在交付寫明。

## 7. 合併與驗收

- 退回信在同一面打轉到第二次，就改成「把規則定死（逐條可判定）或改設計（例：撤回→可重入）」，不再逐條描述症狀——描述症狀只會引出下一組反例。
- 整批合併後的紅多半是整合落差（fixture 缺新欄位、一軌的案期待另一軌的輸出）：單獨跑該檔取細節 → 歸軌在分支補 commit → 再 merge；reset 只留給「補修兩輪仍紅或要改別軌介面」。
- 背景工作 session 不自己 merge；要把 main 合進工作分支由主持端合，工人只交衝突解法（哪支檔取哪邊、合完重跑的範圍）。
- merge 方向寫法固定：「<分支> 已 merge main、尚未合進 main」或「已合進 main：<merge commit>」。「X 已合 main」有兩種讀法，接手者會讀成已上線；轉述前用 `git merge-base --is-ancestor <commit> main` 核實。
- 接驗收條件時先對照使用者自己的裁決，超過的就是前任加的（例：他裁「只抽查閘本體」被落成每件都快照，一天十幾件就被驗證段吃掉）。
- 案例綠≠真實任務會動：工作軌照自己的用法寫測試，沒照使用者的用法跑一次，單元測試越多越容易以為沒事；洞要到驗收才浮出，完工時程就算不準。
- 合併前每軌先用無頭 `claude -p`（乾淨資料根）跑一個真實小任務，用使用者實際的工具與寫法（例 Windows 上 PowerShell 多行訊息），看它在真實交付裡有沒有動；抓到的洞當場開小軌修，不累積到驗收結論。
- 驗收判分不自己做：開乾淨 context 的 agent（跟主持者不同模型）與第二意見工具各判一次，只比對分歧——自己讀太多材料視野會縮小。

## 8. 交接文件

- 人看 checklist 與原話輯，AI 看接續單；兩者對同一件事的說法要一致，對不上以人認得的那份（checklist）為準更新接續單。
- 要人看懂或決定的東西（下一步、編號對照、待決、範圍限定）寫進 checklist，對話裡引用也指 checklist 的段落，不叫人去讀接續單。
- 接續單每次更新三句必寫：舊步驟作廢、停工範圍與恢復條件（誰、怎麼解除）、背景驗證輸出檔絕對路徑；引用的腳本與模板放持久目錄，不放 session 專屬 scratchpad。
- 裁定把某件事做完或改向，當場回頭改派工單／接續單上提到它的舊句，改成「已產出：<路徑>、<commit>」；接手者只讀單不對 git log，讀到舊句會重開已做完的工作。
- 接手收到「開新軌」請求，先用 git log 與信箱查是否已有產物。
- 交出開工句、計畫、清單前自審三問：對得上最新的計畫與接續單嗎？每條指示在這件事上真的需要嗎（不是沿用範本）？剛改的東西影響哪些已給出去的內容——有就當場重發修正版。
- 被問到一處毛病：順查同一份東西還有沒有同類問題，一次改完，不等人連問兩次。
- 一退件，接續單「接下來」的進階條件就改寫成以修正件為準，舊句明寫作廢。

## 9. 對人回報

- 指稱 session 一律用分頁標題看得到的軌名＋分支；`claude-xx` 是 session 間通訊的地址，人看不見。開工句第一句放軌名，分頁標題才看得出來。
- 要人決定的事當場白話列內容、附建議；只寫「待你裁 N 條」或把內容推到檔裡，人視為推卸責任。
- 每條回報用「他會體驗到的事」說：一句現象＋一句現在到哪＋一句差什麼；把代號（G、E、軌名、commit）全拿掉後還讀得通才算，代號只留在裁定帳與文件。最後一定有「一句話版」。細節見活卡 [[feedback-收尾報告使用者視角四要素-白話綜觀非片段細節]]（`memory/行為契約/`）。
- 成本數字的形狀：token 寫「原本大概多少、後來多少」與倍率，不用美金；耗時條列「項目 × 對照哪條目標 × 多耗幾秒」，從帳本算不用估。
- 引用驗收腳本代打的句子（例「先不用管它」）要標明是題目腳本，否則人會以為自己的語意被扭曲。
- 收尾檢核（HUD）報告的讀者是看 HUD 的人，不是派工的主持端：第一行固定「<軌名>，在做 <哪條目標> 的 <哪一件>；這則給 <誰> 看」；要主持端做的事寫「給主持端：…」，對人沒事就寫「你不需動作」；代號首次出現附一句白話。
- 派子代理或背景工作人看不到就是黑箱：回報要讓他知道現在在做什麼、做完他會體驗到什麼。

## 10. 裁定者的自我校準

- 兩把尺：這件事耦合使用者要的目標嗎？增加耗重（token、耗時這些實際體感）嗎？任一不過就降級或拿掉。先分三類：代價高＋不是他要的（補丁）→ 直接拿掉；代價低 → 留；代價高＋是他要的 → 才問他「值不值得、或改成更便宜的形狀」，附建議。
- 目標來自他不代表做法形狀經過他：擋還是記錄、幾處送、門檻，都要分開檢。
- 裁定前三欄必填：服務哪條目標（代號＋原話）／框架是誰給的（自己／實作者／審查器，複述要標）／若改動成本為零會怎麼裁。填不出目標就不裁；零成本裁定≠實際裁定 → 標「成本驅動」、送第二視角。
- 判準權重沒有事前可讀的數字；能量的是事後「按框架來源的被翻率」——裁定帳記每筆＋最後有沒有被使用者翻，被翻的筆當回放題。
- 收到審查或自檢結果先三問再裁：①服務原話裡哪條目標？指不出就不理；②跟已定規則或其他軌有沒有矛盾？有就先解；③使用者現在被什麼磍到（重複提問、看不懂的名字、幾十條廢話）？那才是第一優先。審查者只對它被問的面找漏洞，目標對不對沒人替你看。
- 審查建議派不派兩面判：重大問題（一般寫法會踩、後果是漏記／誤認／流程過不了）→ 派；快且具體有效（小範圍、一輪內、系統明確變好）→ 派、順手做；兩者都不是 → 維護軌。被指正後要自己重新判，不把指正套成新的單一條件倒向另一邊。
- 工作端提「維持現狀」或「改得動到別軌」時，先回原話找目標；目標是核心就改，實作成本不是理由。
- 閘誤擋自己就是現場重現的 bug：第一時間讀碼定位到函式與行號（為什麼記錯、為什麼不重查），單獨開件派工修根因，派工單寫根因與重現證據而不只寫「定死規則」。放行題的選項只有放行／繼續擋，不提關分頁、換角色、繞閘。
- 被糾正時先寫卡（融會貫通的載體），要加關卡前問「單人單分頁、非該情境回合時它還該跑嗎」；多加的關卡多半是程式替自己防重犯。
- 「離開主持端還存在嗎」分兩層：存在 → 屬產品，證明要是產品自帶的案例、形狀對照原話；不存在 → 屬開發期規矩，不落全域卡、不進 hook／注入／settings，也不拿它的儀式去證產品。

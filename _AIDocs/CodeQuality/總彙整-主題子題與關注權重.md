# 總彙整：主題、子題、嚴重性與關注權重

> 把五份危險／壞味道／正面準則彙整與兩份本機證據，收成「14 個主題 × 子題 × 權重」的單層索引。機器版見同資料夾 `總彙整.json`。

## 0. 怎麼用
1. LLM 寫碼或審碼時，先看第 1 節入口索引，拿「一句可數認法」對照手上的程式碼或 diff。
2. 命中某主題，再看第 2 節該主題的子題表；先看權重高的子題（權重 ≥5 的先處理）。
3. 要全文照「指向」欄去讀來源檔；缺口以來源 1（Research/code-smells）的條目為定義、來源 2～5 為可數認法與危險清單。
4. 權重只是關注順序，不是判決；命中後仍要讀來源條目的「何時不算」再報（README §0）。
5. 效能類子題沒有量測數據只能報「疑似」；並行正確性類看程式形狀就能報。

## 1. 給 LLM 的入口索引（14 主題；每行：主題｜一句可數認法｜最高權重子題；Tnn-m ＝第 2 節 Tnn 表第 m 列）
- T01 空層與拐彎（讀路徑）｜從入口追到第一行實質計算要「跳到定義」≥4 次；一個構想的資料形狀鏈箭頭 >3；巢狀 ≥4｜最高 T01-6(隱式流程找不到) 權重 5
- T02 繼承與抽象每層都要有作用｜繼承 ≥3 層且有一層「新增成員=0、override=0、獨立呼叫端=0」；interface 只有 1 個實作且無替換計畫｜最高 T02-6(近複製平行類與樣板) 權重 4
- T03 資料攤成表、不綁格式｜資料能整份貼進試算表卻寫成巢狀容器；核心資料型別帶 [ProtoMember]/[JsonProperty]；新增一筆內容要改 .cs｜最高 T03-2(手寫映射漏接新欄位)、T03-5(同一數值多來源) 權重 5
- T04 狀態單一出入口｜同一容器/欄位的寫入點 ≥3 檔或 ≥6 處；同一事實存 2 份（hp 與 isDead）；≥4 個互斥 bool｜最高 T04-2(同一事實存兩份) 權重 5
- T05 存檔、載入與遷移（載入不是變動）｜Load 呼叫鏈內出現 OnChanged/發事件/發獎勵；存檔無版本欄位；直接覆寫原檔｜最高 T05-2(讀檔失敗回預設並覆寫) 權重 6
- T06 Unity 物件的 null 與生命週期｜對 UnityEngine.Object 用 `?.` `??` `is null`；Awake/Start 互相依賴；`+=` 數 > `-=` 數｜最高 T06-2(初始化順序依賴)、T06-3(事件不退訂) 權重 4
- T07 執行緒歸屬與每幀配置｜Update/tick/封包處理內出現 new、LINQ、字串串接、GetComponent/Find；非主執行緒碰 Unity API；tick 內 .Result｜最高 T07-1(熱路徑配置) 權重 4
- T08 熱更邊界｜跨界 API >100 或一次流程跨界 >2 次；用字串反射找熱更型別；適配器註冊手改｜最高 T08-2(字串反射與手動推棧)、T08-3(適配器與鏡像手改) 權重 4
- T09 網路權威、原子性與決定性｜伺服器採用客戶端回報的結果；「查條件」與「改狀態」分兩步；有副作用的請求重送會再執行；協定兩端各手寫一份｜最高 T09-6(協定兩端各手寫一份) 權重 5
- T10 數值與捨入｜金額/機率用 float；金幣用 int 累積；Math.Round 未指定 MidpointRounding；`new Random()` 以時間為種子｜最高 T10-2(整數溢位與除法)、T10-6(保底計數) 權重 3
- T11 時間與時區｜冷卻/到期/每日重置取客戶端時間；DateTime.Now 與 UtcNow 混用；+24 小時當「明天」｜最高 T11-1(客戶端時鐘為準) 權重 3
- T12 靜默失敗與邊界 fail-fast｜空 catch；catch 後只 return default；非事件處理器的 async void；`?? default` 旁沒有 log/計數｜最高 T12-1(空 catch)、T12-2(靜默降級) 權重 5
- T13 LLM 產碼慣病｜新增函式前沒搜既有 helper；改/刪/skip 測試；在報錯行加防護；一個 diff 混重構與功能｜最高 T13-2(幻覺 API 與未讀就假設)、T13-3(只修症狀) 權重 5
- T14 驗證與等值證明｜預期值由新程式產生；案例全取自 bug 修復提交；結論沒有「我跑了什麼」；零測試專案｜最高 T14-1(重構無等值證明)、T14-3(未實證就斷言) 權重 5

## 2. 子題表

**權重算法（固定）**：權重 ＝ 嚴重性（致命 3／嚴重 2／中 1／低 0）＋ 本機踩過（有 +2，無 0）＋ LLM 常犯（是 +1，否 0），範圍 0～6。權重欄寫成「總分 ＝ 嚴重+本機+LLM」。

- 嚴重性刻度：致命＝直接造成金錢損失、資料損毀、外掛、不可逆；嚴重＝靜默錯誤、洩漏、卡死、跨版本壞，通常條件到才爆；中＝維護成本、效能、可讀；低＝風格與偏好。來源 2～4 未分級，此為本檔判定（依 04 事故優先序與 Client 後續步驟的風險排序）。
- 粒度：語言（C#/.NET 語意）／引擎（Unity）／架構（跨類別、跨層）／邏輯（單一流程的對錯）／可讀（人讀成本）／流程（寫碼與驗證的做法）。
- 本機踩過：只收 09 的案例條（A-nn、N-n）或 Failures 的卡；`F:` 縮寫見下；09 的 B-nn 原則只放指向欄。
- LLM 常犯：以 08 條目或來源 4 第 9、18 章編號為證；無對應條目者填「否」。
- 指向縮寫：`SV`＝Server 危險彙整、`CL`＝Client 危險彙整、`GN`＝遊戲開發通用危險彙整、`RD`＝可讀性與優良設計彙整（後接章節編號）；`01`～`09`＝Research/code-smells 分支檔（後接條號或英文條名，03 為 A01 類、04 為 A1 類、09 為 A-nn／B-nn）。
- Failures 卡（`memory/Failures/` 下）：F:跳層驗證＝驗證與實證/feedback-驗證不能只涵蓋真bug…；F:複雜起源＝思考與決策/feedback-complexity-origin-trace；F:綜觀＝思考與決策/feedback-處理眼前需求時要同時適度綜觀專案…；F:現況≠應然＝思考與決策/feedback-現有程式只證明現況不證明應然…；F:註解＝行為契約/feedback-程式註解與敘事-現況直覺白話…；F:live檔＝行為契約/feedback-live-檔與記憶不留版本操作脈絡…；F:未實證＝驗證與實證/feedback-未實證先別斷言…；F:共識非實證＝驗證與實證/feedback-討論共識不是實證…；F:自動化實跑＝驗證與實證/feedback-能自動化實跑的驗證不准推給使用者…；F:靜默失敗＝_reference/silent-failures。

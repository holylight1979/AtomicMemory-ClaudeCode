## 知識

- [臨] 規則（v6 總控台定死）：口令、糾正、豁免詞、使用者決策、不要記、停用、失敗萃取、Quote 的來源只吃一支函式 `lib/harness_text.user_typed_text`（hooks/wg_core 轉呼叫，不另存一份）：剔掉所有 harness 區塊（system-reminder、task-notification、cross-session-message、ide_*…）、自成一行的系統通知標記行之後的內容、hook 殘渣行；清理後還殘留任何 harness 標籤字樣就整則不認。
- [臨] 踩過的繞過與誤丟：① 只看開頭前綴 → 同伴訊息前面夾一段 system-reminder 就繞過；② 整則以通知開頭就整則丟 → 通知後面接的使用者原話被丟；③ 先截 500 字再清理 → 前置注入很長時口令被截掉（要先清理、再截長、再存 state）；④ 正則非貪婪配對遇同名巢狀會在內層閉合就停，外層內容漏出；交錯閉合不能清掉仍開著的內層；屬性值裡的 `>`、`/` 不算標籤結尾；⑤ UPS 入口先用另一條正則剔 IDE 區塊會破壞巢狀判斷，要用同一支掃描器的 only 模式；⑥ 萃取 worker 消費舊候選不重驗來源，舊版排進佇列的同伴訊息照樣寫成 atom。
- [臨] recent_user_prompts 寫入端不要過濾非使用者訊息（存清理後文字、不是使用者的話就存空字串）：CommitOrder 的「沒有任何紀錄就放行」看的是清單是否為空，寫入端一過濾，第一則就是同伴訊息的 session 會走進 fail-open。過濾放在讀取端（user_typed_prompts）。
- [臨] 細節規則的依據：同伴區塊邊界照 Claude Code 封裝認（見卡 cc同伴訊息封裝…）；系統通知標記只認自成一行的完整標記，標記行之後、沒閉合區塊之後的文字分不出來源，寧可不認；使用者自己打出標籤字樣而不被認是可接受的代價（CommitOrder 擋訊息請他單獨重打口令）。意圖分類不是權威判斷，照舊吃同伴派工訊息。

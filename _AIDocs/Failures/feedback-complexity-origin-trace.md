## 知識

- [臨] **使用者表達「回答/內文超出預期的複雜、看不懂、敘述太長」時，那是「設計矛盾/漏洞」的症狀，不是「需要更多解釋」的訊號**。錯誤反應＝補更多文字去圓說（把症狀放大、根因埋更深）。**正確反應：停手、先追蹤複雜的起源**——通常是「兩個本應正交的東西被實作綁死」，或「先前已出現的複雜敘述當時沒被精確反饋成『這是設計矛盾』」。用一句話講清矛盾本體，再行動。
- [臨] **Why**：複雜的回答會累積、稀釋使用者的理解與信任；複雜往往是設計問題的「味道」，不是該用更多語言填的空。使用者已明言：每次「內文超出預期的複雜」出現、看到反饋時，**都該先追蹤分析「會生成這種複雜回答的起源」**。
- [臨] **How to apply**：① 偵測訊號（user 說太複雜/看不懂/太長）→ ② 立刻停手、不再堆解釋 → ③ 回溯：哪兩個正交軸被綁死？哪段先前複雜敘述沒被即時點名為矛盾？→ ④ 一句話講矛盾本體 → ⑤ 提議「是否要解這個矛盾（列為設計議題）」或「先照 user 心智模型執行」。
- [臨] **實例（本 session 2026-06-18）**：realm「放哪裡」問題——`memory/`（使用者心智＝索引角色）vs `_AIDocs/_atoms`（知識儲存角色）的**儲存角色**，被現行實作**綁死了「注入範圍」**（core＝全專案 / local＝僅 ~/.claude）；`feedback-*` 是唯一解綁特例（住 _AIDocs/Failures 卻全專案注入）。我先前用一張複雜的 realm 表回應，正是「沒追蹤起源」的反例——該做的是一句話點出「儲存角色 與 注入範圍 被綁死」這個設計矛盾。

## 行動

- 偵測「太複雜/看不懂/敘述太長」訊號 → 停止堆疊解釋
- 追蹤起源：找被綁死的正交軸 / 找漏報的矛盾
- 一句話講矛盾本體 → 提議解或照 user 模型執行
- 複雜敘述出現當下即精確反饋「這是設計矛盾」，不拖到下次

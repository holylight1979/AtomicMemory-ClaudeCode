# 作業紀錄與工作日誌 — 伴隨焦點記重點，避開監視紅線
> 所屬：[JARVIS 企業 AI 平台發想](README.md) · 對應願景 #12

> **本檔立場**：屬 `_AIDocs/Vision/` 發想層，以「說不定某天會真的拿出來做」的可執行設計參考書寫，非空想。技術數字均附來源 URL（會過時，以原始出處為準）；前瞻判斷標 (推測)。
>
> **⚠ 隱私敏感檔**：本主題本質是「LLM 在你旁邊記你做了什麼」。它與「監視軟體」只有一線之隔，而那條線一旦踩過去就是法律、信任、勞動權的災難。**本檔的核心不是「怎麼記得更多」，而是「怎麼記得剛剛好、且讓被記的人完全掌控」。紅線章節（§5）不可跳過。**

## 1. 對應願景需求（為何屬此檔）

| # | 願景需求原文 | 與本檔的關係 |
|---|------------|------------|
| **#12** | 客戶端可啟用「作業紀錄」模式，透過 LLM 學會**伴隨焦點**，把每天的實作、條列重點記下來；每月的工作日誌就交給他產 | 本檔主軸。拆成兩層：**即時採集**（伴隨焦點，記今天做了什麼）+ **聚合產出**（月誌＝把日採集摘要成報告）。 |
| **#13**（關聯） | 請假 / 填單 / 會議召開 | 日誌是**工時佐證**的天然資料源：填工時單時，LLM 可從當日事件日誌反推「這天實際在哪些任務上花了多久」。連動見 [安全治理](08-security-governance-compliance.md)。 |

一句話定位：**願景要的是「貼身書記」，不是「監工」。** 「伴隨焦點」聽起來像 Microsoft Recall / Rewind 那種「全程錄影桌面」，但那條路在 2026 已被反覆證明是隱私地雷（§2）。本檔主張走一條**結構上就更安全**的路：記「事件」與「決策」，而不是錄「畫面」。

> 與現況的落差（README 評 🟡 40%）：現有 journal skill 已能產日誌，但它是**事後聚合**（從已存的 atom + git log + transcript 拼），不是即時「伴隨焦點」採集。缺的是 OS 焦點層的即時事件流——而這正好是隱私最敏感、最該慎選粒度的一塊。

## 3. 推薦設計取捨

### 優選組合：**事件日誌 + 結構化決策日誌（皆非截圖）＋ 明確同意 ＋ 本地優先 ＋ 自動刪除 ＋ 隱私三色分級**

```
採集：OS focus 事件（window title + 活動類型 + 時戳 + duration） + Claude Code 內既有 hook 事件
      ↓ 即時打隱私三色標（Red 直接丟棄 / Yellow 去識別後存 / Green 原樣存）
       ↓ 進結構化決策日誌（只留有知識價值的「決策/變更」事件）
落地：本地優先儲存 + 明確同意清單 + 自動刪除（預設 6 個月）+ 可隨時導出/刪除
聚合：日採集摘要 → 月誌（現有 journal skill 升級版）
```

| 取捨點 | 選項 | 建議 | 理由 |
|--------|------|------|------|
| **採集形態** | 連續截圖（Recall/Rewind 式） vs 事件日誌 | **事件日誌（非截圖）** | 隱私洩露面積小一個數量級；記憶體省；符合 GDPR 最少化；標題列敏感是可治理小面，整張畫面敏感是不可治理大面 |
| **記什麼粒度** | 全活動 vs 只記決策/變更 | **事件日誌打底 + 結構化決策日誌為知識主體** | 「全活動」噪音壓垮訊號且逼近監視；「只記決策」知識密度最高、最像人類工作日誌；兩者互補（事件提供工時佐證，決策提供知識） |
| **同意模型** | 預設開 / 概括同意 vs 明確告知具體記什麼 | **明確告知「記什麼」（非「可能記什麼」）+ off-by-default** | 抄 Recall 的 opt-in；但更進一步——同意書要列**具體欄位清單**，不是模糊的「我們可能收集使用資料」 |
| **儲存位置** | 雲端 vs 本地優先 | **本地優先**，上傳僅限去識別後的聚合摘要（且須再同意） | 本地優先＝洩露邊界最小；個人原始事件流不離開本機 |
| **保留期** | 無限保留 vs 自動刪除 | **自動刪除（預設 6 個月）+ 可調** | 無限保留＝合規與洩露風險隨時間累積；抄 Recall 的保留上限機制 |
| **敏感處理** | 全記再過濾 vs 採集點就分級丟棄 | **採集點隱私三色分級**（Red 根本不寫入） | 「先全記再遮罩」一旦遮罩漏一處就洩漏（Recall 的敏感過濾是「減少」不是「保證」）；Red 類在採集點就丟棄，從源頭斷風險 |

### 隱私三色分級（採集點即判定）

| 級別 | 內容範例 | 處理 |
|------|---------|------|
| 🔴 **Red** | 密碼 / 認證 token / 個人通話 / 私人訊息 / 標記為隱私的程式碼 / 醫療財務個資 | **採集點直接丟棄，根本不寫入**（非事後遮罩） |
| 🟡 **Yellow** | PR 評論 / 設計決策討論 / 會議摘要 / 含人名的協作紀錄 | 去識別（人名→角色代號）後存；上雲須額外同意 |
| 🟢 **Green** | 技術決策邏輯 / 專案進度 / commit 訊息 / 公開設計理由 | 原樣存，可進共享知識層 |

### 為什麼不走 Recall 式截圖（一句話總結）

> **截圖把「隱私風險」和「知識價值」綁死在同一張圖上——你為了記住「我改了登入流程的這個決策」，被迫連同畫面上的密碼欄、私訊、別人的螢幕一起截下來。事件日誌則把兩者解耦：只記「改了登入流程決策」這個結構化事實，密碼欄從來不進入採集範圍。** 這是結構性的隱私優勢，不是靠加密事後補救。

## 4. ★ 在現有原子記憶系統上的落地切入點（本檔最重要的一節）

> 原則：**誠實標「能用 vs 必新建」**，不誇大現況。
>
> **好消息（也是本檔最關鍵的洞察）**：原子記憶系統在 Claude Code 內，**本來就是「事件日誌」而非「截圖」的形態**——hook 追蹤的是「改了哪個檔、跑了哪個 bash、讀了哪些檔」這種結構化事件，天生偏隱私友善。所以願景 #12 的「伴隨焦點」，在 Claude Code 範圍內幾乎已經實現了；缺的是把採集範圍從「session 內」擴到「OS 焦點層」。

### 4.1 零件盤點：能用 vs 必新建

| 現有零件 | 現況能力 | 在「作業紀錄」裡的角色 | 判定 |
|---------|---------|----------------------|------|
| **journal skill**（從 atoms + git log + transcript 聚合產日誌） | 事後聚合產出日誌 | **月誌產出器的現成底座**；採集層補上後，它從「拼湊」升級為「有結構化日採集可聚合」 | ✅ **能用**（聚合層）／ 採集層需餵料 |
| **episodic atom**（每 session 結束生成摘要，含閱讀軌跡 / 版控查詢 / 關聯） | 每 session 一份結構化摘要 | **就是「事件日誌」的 session 級雛形**——已記「這段做了什麼」 | ✅ **能用**（session 粒度的事件日誌已存在） |
| **SessionEnd 全量萃取** | session 結束時把重點轉結構化 atom | 把「每天實作重點」轉結構化條目的現成管線 | ✅ **能用** |
| **PostToolUse file tracking**（記 modified / accessed / bash） | 即時追蹤檔案改動與指令 | **就是事件日誌的事件源**——只是範圍限 Claude Code 工具呼叫 | ✅ **能用**（事件源，限 session 內） |
| **萃取管線 quick / deep** | 把對話轉結構化條目 | 把「決策 / 變更」抽成結構化決策日誌條目 | ✅ **能用**（結構化決策日誌的抽取器） |
| **scope / realm 分層** | 控制 atom 注入範圍與 core/local | 可直接承載「隱私三色分級」與「個人 vs 共享」邊界 | ✅ **能用**（分級的承載層；但見 §5 注入過濾≠存取控制的限制） |

### 4.2 必須新建的硬骨頭（現況完全沒有）

| 必新建項 | 為什麼現況做不到 | 對應參考 |
|---------|----------------|----------|
| **OS 焦點層即時採集器** | 現有 PostToolUse 只看得到 Claude Code 內的工具呼叫，看不到「使用者切到 IDE / 瀏覽器 / 終端」這種 OS 層 focus 事件 | OS focus/window API（Win32 `GetForegroundWindow` 等）；**這是 #12「伴隨焦點」唯一真正缺的核心零件** |
| **隱私三色分級器（採集點）** | 現有 Write Gate 是品質閘，不是隱私分級；無「採集點丟棄 Red」機制 | §3 三色表 + 採集點過濾規則 |
| **明確同意 + 透明儀表板** | 現況無「告知使用者具體記什麼 / 可選擇性排除 / 隨時導出刪除」的 UI | 抄 Recall 的設定面板形態（off-by-default / 排除清單 / 刪除 / 暫停） |
| **自動刪除 / 保留期政策** | atom 預設長存，無到期自動刪 | retention 排程（預設 6 月）+ 可調 |
| **OS focus 事件 → 結構化決策日誌的對映** | 焦點事件是低階訊號，要升維成「這是一個決策」需要 LLM 判讀 | 萃取管線 quick/deep 可改造承接 |

### 4.3 演進切入順序（從最安全的一刀開始）

1. **先用既有零件做 session 內事件日誌的「日誌化」**：把 episodic + PostToolUse file tracking 的既有事件，餵進 journal skill 產「日報」——**完全不新增採集、零隱私增量**，先驗證「事件日誌→日誌」這條聚合鏈。
2. **加結構化決策日誌**：用 quick/deep 萃取把對話中的「決策/變更」抽成 `decision + context + rationale` 條目。仍在 Claude Code 範圍內，無 OS 採集。
3. **隱私三色分級器先上線（在擴採集之前）**：先把分級與「採集點丟棄 Red」機制做好，**絕不能反過來**——擴採集前必須先有護欄。
4. **同意 + 透明儀表板**：off-by-default 的開關 + 具體欄位清單 + 排除清單 + 導出/刪除/暫停。
5. **最後才接 OS 焦點層採集器**：且預設只記 focus window 標題 + 活動類型（事件日誌形態），**永不截圖**。
6. **月誌升級**：journal skill 從「事後拼湊」升級為「聚合結構化日採集」。

> 切入順序的鐵律：**護欄（步驟 3、4）必須先於擴大採集（步驟 5）。** 任何「先採集，隱私之後再補」的順序都是 Recall 式翻車的起點。

## 5. 已知風險 / 紅線 / 待驗證假設

### ⛔ 紅線表（任一項出現即停止，不可踩）

| 紅線 | 為何是紅線 | 對照 |
|------|-----------|------|
| **連續視訊 / 截圖採集** | 「一份檔案＝完整監視」，本地加密也救不了（被傳票調取、malware 外傳、洩露面積最大） | Recall / Rewind 翻車核心 |
| **無告知就記錄** | 違反 GDPR 透明原則；摧毀信任 | EDPB 透明義務 |
| **捕捉密碼 / 認證** | 安全災難 + 法律責任 | Recall 敏感過濾只是「減少」非「保證」，故本檔在採集點直接丟棄 Red |
| **跨裝置同步原始事件流** | 擴大洩露邊界、脫離本地可控範圍 | 本檔主張本地優先，僅去識別聚合摘要可上雲 |
| **管理員強制開啟（員工不可關）** | 工作場域「同意」在 GDPR 下幾乎無效（員工無法自由拒絕），強制監視觸動勞動法爭議 | 見下「同意」段 |
| **無限保留** | 風險隨時間累積；違反儲存限制原則 | 本檔預設 6 月自動刪 |
| **無審計、可否認** | 出事無法追責；治理不可信 | 需 append-only 審計 |

### 隱私 / 同意 / 勞動法 / 合規（本檔主軸風險）

- **「同意」在職場幾乎無效**：EDPB（及前身 Article 29 WP）一再強調，**僱傭情境下「同意」通常不是有效法律基礎**，因為員工無法在沒有後果的情況下自由拒絕。實務上多以 **legitimate interest（GDPR 6(1)(f)）** 為基礎，且須做書面三段平衡測試：**目的明確性、必要性、比例原則**。來源：[GDPR Local](https://gdprlocal.com/gdpr-employee-monitoring/)、[Worklytics 合規](https://www.worklytics.co/blog/key-compliance-laws-for-remote-employee-monitoring-data-protection)。
  - **設計推論 (推測)**：因此本檔的「明確同意」在企業部署時，不能只靠員工點同意，必須**搭配比例原則論證**（為何「記決策日誌」是達成目的的最少侵入手段？能否用更不侵入的方式達成？）。並優先把功能定位為**個人生產力工具（員工自用、員工可關）**，而非管理層下發的監工工具——這是合規與信任的關鍵分水嶺。
- **比例原則 / 資料最少化**：監視須「necessary and proportionate」，且須先問「能否用更不侵入的手段達成同一目的」。事件日誌（非截圖）正是「更不侵入手段」的具體答案。來源：[GDPR Local](https://gdprlocal.com/gdpr-employee-monitoring/)。
- **EU AI Act 透明義務 (推測影響)**：[Regulation 2024/1689](https://gdprlocal.com/gdpr-employee-monitoring/) 對「AI 驅動的監視」加上透明義務（搜尋來源指其 2026/08 相關條文生效，**具體適用範圍待回原文核對**）。若 JARVIS 用 LLM 判讀員工活動，可能落入此範疇，須揭露。

### 管理職可見範圍 與 scope / 權限的關係（呼應現況最大弱點）

- 願景 #6 的管理職特權目前是 **honor-system（君子協定）**（見 [README](README.md) 與 [記憶作為共享皮層 §4](01-memory-as-shared-cortex.md)）。**作業紀錄一旦進共享層，這個弱點會被放大成隱私災難**：
  - 現況「scope 是注入過濾、不是存取控制」意味著——**任何能讀檔案系統的人都能 `cat` 到別人的 personal 事件日誌**。把作業紀錄做成共享 atom 之前，**真 AuthZ（檢索期強制過濾，見 [01 §4.2](01-memory-as-shared-cortex.md)）是硬前提**，否則等於把每個人的工作日誌攤在全公司面前。
  - **設計紅線**：個人作業紀錄預設 `personal` scope 且**本地不離機**；除非員工主動匯出去識別摘要，管理職**不應**能讀到個人原始事件流。「管理職能看月誌聚合」與「管理職能看你每分鐘在做什麼」是兩件事，前者可接受、後者是監視。

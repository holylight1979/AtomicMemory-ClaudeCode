## 合併時補的一刀（!14）

原版 SessionStart 的「死人開關」：只要 last-run.json 逾 72h 沒更新就提醒「排程沒跑，去 --register」。問題在 last-run 是每次執行都寫，**手動查過一次**（例如這次審查實跑的那一次）、沒打算註冊排程的人，三天後每場 session 都會多一行叫他去註冊，永遠不停——這正是使用者問的「額外消耗 token」會發生的地方。

改法：last-run 多記 `scheduled`（排程的 watch 跑法帶 `--notify`，手動查詢不帶），逾期提醒只看 `scheduled=true`；查詢失敗、通知失敗的提醒不變（那些不分手動排程都該浮出）。`hooks/verify/verify_usage_watch.py` 補 1 案（手動逾期不提醒），40 案全綠。作者既有的排程不用重註冊（它本來就帶 `--notify`）。

## !16（!11 輕量版）怎麼審的

- **邊界對不對**：10-20 定的「做」全有（索引檔 5 個名、記憶資料夾名 16 個、衍生物與 scope 三子樹，全是扁平字串常數，每個一句說明，放既有 `lib/atom_spec.py`）；「不做」全沒做（沒有拼路徑方法、沒有 JSON、沒有 JS 側、守衛不擋單獨字面）。守衛是一支 pytest（`lib/verify/verify_name_lists_single_source.py`），不是 hook，平時零成本；`except ImportError` 備援區放行，合理。
- **等值**：自己寫 AST 腳本，把 main 的字面清單和 !16 的常數組清單逐一求值比對——87 組相同、0 組有差；改成 import 的 4 組（vcs_ignore 的 DERIVED_*、merge-atom-index 與 normalize-eol 的 INDEX_FILES）對到 atom_spec 的值也相同。atom_io 的 scope 檢查改用 `VALID_SCOPES`，前面 global 已先 return，行為等值。
- **測試**：對 main 零衝突、0 落後。16 支相關案例檔 333 過，8 分 39 秒（三組錄製型測試佔大頭）。
- **錄製檔**：MR 帶了 122 個重錄的錄製檔，差異只有時間戳與 hash；原因是錄製框架把「被 git 叫起來的程式」（merge-atom-index 現在 import atom_spec）算進過期判定。本機跑完又全部重錄一次，原因是 git 版本不同（作者 2.49.0、本機 2.50.1），框架把 git 版本也算進去——所以錄製檔本來就每台機器各錄各的，本機重錄的不進版控，照收 MR 的。

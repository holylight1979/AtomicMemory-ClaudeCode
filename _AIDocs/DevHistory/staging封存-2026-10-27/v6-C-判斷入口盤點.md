# C-判斷入口盤點：哪些閘把需要判斷的事寫成了固定規則（待原設計者審）

> 讀者：原設計者。用途：審這份清單，核准後才動手改。本次只讀不改（0a 那一件除外，已修，列為第 0 項實例）。
> 判準：原話輯 G6 重點條列（程式管「已判斷完的規則」，需要判斷的地方留 LLM 宣告＋理由＋證據、事後對帳；擋要精準）、G1 10-15 條與語意註釋（定位、批判、舉一反三）。
> 來源：三組唯讀盤點（Stop 端、動手前與使用者訊息端、目標樹／驗證範圍／記憶寫入）共 118 處候選，逐處讀碼核對後收斂成下面這份；行號是 2026-10-15 main 的位置。

## 結論先講
- 真正會「擋錯或放錯」的有 8 處（第一節），其中 3 處本 session 親身踩到：驗證範圍的漏判歸因把我刻意先紅的新案例記成別人漏判、又擋住我的宣告；背景子代理的回報一進來就觸發「偵測到記憶寫入意圖」「架構級變更→先進 Plan Mode」；口令閘用子字串，「先不要 commit」也算下了口令。
- 不是每個固定規則都該交給 LLM。改法分三種：**甲**＝真的要判斷 → LLM 宣告＋理由，程式只查有沒有宣告、核對證據、留帳事後檢討；**乙**＝固定規則其實是某個「查得到的事實」的粗略替身 → 換成查那個事實（0a 就是這種：用內容雜湊判「是不是同一個檔」，不需要 LLM）；**丙**＝本來就是已判斷完的規則或安全邊界 → 合理，保留。
- 同類病有四種（第二節），每種都不只一處；改的時候整類一起改，不逐點補。
- 批判與舉一反三兩問怎麼接進關鍵點，提案在第四節；跟第一節一起審。

## 第 0 項（已修，本次的第一個實例）：已刪的檔是「刪掉」還是「搬走」
- 位置：`hooks/wg_release_rules.py` MOVED_NEW_CODE_SEEN、`hooks/wg_verify_ledger.py` vanished_code_paths。
- 原本：改過的程式檔不見了，同根只要出現**任何**新程式檔，就當成「可能搬過去」照欠補案例。10-15 調度收尾被擋：信箱裡的快照腳本搬走、.gitignore 拿掉那一行、同 session 又合進一支無關的新測試，規則把那支測試當成腳本搬過去的副本。
- 不合理，因為「這個新檔是不是它搬過去的」是查得到的事實，卻用「有新檔」這個替身代替。改法是乙：記每次寫入後的內容雜湊，只有檔名相同或內容相同的新檔才算副本。checklist 推測的「從沒被 git 追蹤過＝素材」沒採用：本 session 新寫、還沒提交的程式被改名搬走，會因為「沒追蹤過」而漏欠。
- 同類：第二節「類 2 代理指標判關聯」。

## 第一節：建議優先改的 8 處（會擋錯或放錯）

### P1 驗證範圍的「範圍漏判」歸因只看時間窗（本 session 實遇）
- 位置：`hooks/wg_verify_scope.py` `_attribute`（約 525–563 行）、`declare` 拒收段（約 351–358 行）；規則 SCOPE_LEAK_OUTSIDE_SCOPE、SCOPE_LEAK_REVIEW_BEFORE_DECLARE。
- 現在誰判：程式。一支測試紅了，只要「它上次綠在某份範圍結案之前、紅在之後、那份範圍沒涵蓋它」就記成那份範圍漏判；有待檢討的漏判，下一次宣告整份拒收。LLM 有逐筆檢討的入口（missed／unrelated），這部分設計是對的。
- 要不要判斷：要。「這支測試紅，跟哪一次改動有關」是判斷題。
- 不合理，因為：本 session 照 G3「先紅後綠」先寫新案例、先跑紅，新案例在那些範圍結案時根本還不存在，卻被記成 44 筆「別的 session 漏判」（兩個已關的 session、11 份範圍 × 4 個新案例）；之後一次正常的改壞又記 11 筆。我自己的範圍宣告被擋到逐筆檢討完才收。誠實流程被擋，責任被推給已關的 session。
- 更好的做法（乙＋甲）：先用查得到的事實篩——那份範圍結案時這個測試節點不存在（檔案歷史或收據裡從沒出現過）→ 不算；紅的測試或它驗的程式正被本 session 改著 → 先歸本 session 自己的範圍。篩剩的才送 LLM 檢討，而且只擋「該負責的那個 session」，不擋別人的宣告。刻意先紅（本 session 新寫或剛改的案例跑紅）比照 RED_WHILE_REVERTED 認成刻意紅。
- 同類還在：重試計數把反證刻意跑出的紅當重試、DeepPostMortem 把它當失敗（維護軌已列）——三處都缺「刻意紅」這個事實。

### P2 commit 口令閘用子字串判「使用者有沒有授權」
- 位置：`hooks/handlers/pre_tool_use.py` `_COMMIT_ORDER_DEFAULT_KEYWORDS`（約 310 行）、`_commit_order_keyword_hit`（約 353 行）。
- 現在誰判：程式。本回合使用者原話含 `commit`、`push`、`提交`、`上GIT`… 任一子字串就放行 commit。
- 要不要判斷：要。「使用者是不是授權了這次版控動作」是語意。
- 不合理，因為：放錯的方向是對外、難收回的動作。「先不要 commit」「commit 訊息怎麼寫比較好？」都含 `commit`，照放行。
- 更好的做法（乙＋甲）：使用者自己定義的縮寫口令（上GIT、上乾淨、執P…）整詞比對、排除否定句；自然語句的授權改成 LLM 在 commit 前引用使用者那一句，程式核對那句真的在本回合 user_typed_text 裡、不在否定句中，並留帳。
- 同類還在：記憶萃取的否決詞用 `"否"` 子字串（`hooks/handlers/ups_gates.py` 約 129 行），使用者句子裡有「是否」就把待記的決策全部丟掉；豁免詞（P7）。

### P3 三種提示吃的不是「使用者打的字」（本 session 實遇）
- 位置：Atom-Write Guard `hooks/handlers/ups_gates.py` 約 195–207 行；研究 fan-out、並行建議 `hooks/handlers/ups_context.py` 約 131、142 行（都吃 `clean_prompt`，只剝 IDE 標籤，見 `user_prompt_submit.py` 約 230 行）；情境分類 `ups_context.py` 約 105–124 行＋`hooks/wisdom_engine.py`（不看這則訊息，看整個 session 的改檔數與累積關鍵字）。
- 現在誰判：程式，用關鍵字與改檔數。
- 要不要判斷：「使用者這次要不要記憶、要不要並行、這件事規模多大」要判斷；但「這則訊息是不是使用者打的」是事實。
- 不合理，因為：已定裁決「所有權威判斷只吃 user_typed_text」；這三處沒照做。本 session 每次背景子代理回報進來，都被注入「偵測到記憶寫入意圖」與「架構級變更→先 EnterPlanMode」；後者還與原設計者「我沒有要你馬上進入 PlanMode」相衝。
- 更好的做法：乙——改吃 user_typed_text，通知類訊息不跑這些提示。情境分類整段拿掉，改在「新需求開始」關鍵點由 LLM 在目標樹寫下這件事的規模（甲）。
- 同類還在：第二節「類 4 同一件事各閘定義不同」。

### P4 寫碼查核 (d)「改了碼就欠一個案例」：案例與改動的對應用時序＋路徑猜
- 位置：`hooks/wg_verify_ledger.py` `case_debt`（約 1311–1359 行；docstring 自承「改的案例是不是對應這次改動，程式判不出來」）、`workflow/config.json` `verify_case_globs`（`**/verify/**`、`**/tests/**`、`**/*test*`）。
- 現在誰判：程式。同根「最後一次改案例檔」之後還改過的程式檔就欠；同根改了**任何一個**案例檔，就清掉之前所有程式的帳；檔名含 test 就算案例（`latest_build.py` 也算）。
- 要不要判斷：要。「這次改動要不要新案例、由哪個案例驗」是判斷題。
- 不合理，因為兩向都錯：改一支不相干的測試就清掉帳（放錯）；不需要新案例的改動（只改訊息字串、純搬家）只能找使用者放行（擋錯，打斷工作）。
- 更好的做法（甲）：每個改過的程式檔，LLM 宣告「由哪個案例驗」（新寫或改的那支，附先紅後綠收據）；程式核對案例存在、改完之後跑綠。宣告「不需要新案例，因為…」時，維持已定裁決「擋滿不准自行放行」：照【收尾放行確認】問使用者，只是題目帶上 LLM 的理由，讓使用者一眼可裁。
- 同類還在：P5。

### P5 (a)「說修好」的收據對不對得上改動，用檔名對應
- 位置：`hooks/wg_verify_ledger.py` 約 803–811、876–890 行。
- 現在誰判：程式。指令裡有 `test_<檔名>`、`verify_<檔名>`、或改檔目錄的 `verify/` 就算驗到。
- 要不要判斷：要，而且這題已經有答案的地方——10-14 起「該測哪些」改由 LLM 宣告驗證範圍；(a) 還在用舊的檔名對應。
- 不合理，因為：同一個判斷，兩個閘用兩套答案。
- 更好的做法（甲，已有入口）：(a) 直接認「本次宣告範圍內、改完之後跑綠的收據」；沒宣告才退回檔名對應。
- 同類還在：搬程式目錄固定要「路徑掃描＋抽樣」兩張收據（MOVE_CODE_DIR_NEEDS_SCAN_AND_SAMPLE）——掃描是事實檢查、合理；「抽哪些驗」應併進宣告的範圍。

### P6 「我做了 X」的宣稱全靠詞表
- 位置：`hooks/wg_evasion.py` 約 254–266 行、`memory/_meta/forbidden-phrases.json`（completion／fixed／measured／tried 四組）、`hooks/wg_verify_ledger.py` 約 423–452 行（轉述判定：子句前 4 字有沒有「使用者／它／他」）、`hooks/wg_release_rules.py` CLAIM_MODIFIER_NOT_OWN（「的＋名詞」）。
- 現在誰判：程式。命中「修好」「跑過」「完成」等詞就算宣稱，再用幾條句型排除轉述。
- 要不要判斷：要。「這句是不是我本回合做了 X 的宣稱」是語意。
- 不合理，因為詞表追不完語境（否定、轉述、假設、說明別人怎麼做）。維護軌第一條就是實例：一般性說明「CC 會怎麼做（跑完、跑不了）」被當成自己宣稱，10-15 連擋三回合。

- 同類還在：退避詞（P7）、糾正詞（第二節類 1）。

### P7 退避與豁免：答應了 LLM 的說明入口，程式卻沒接
- 位置：`memory/_meta/forbidden-phrases.json` 的 `exception` 欄（「除非附『檢測時點＋不修的實際風險』」「除非附『具體為什麼超出』」）；`hooks/wg_evasion.py` 只讀 patterns、沒讀 exception。豁免詞（「先這樣」「留著」「跳過」）在最近 3 則使用者訊息任何位置出現，就關掉退避標記、Deferral、ScanReport、收割，還清掉紅測清單（`ups_gates.py` 約 103 行）。
- 現在誰判：程式，詞表。
- 要不要判斷：要。「這是推遲可做的事，還是有正當理由不做」「使用者說的『跳過』是指哪一件」都是判斷。
- 不合理，因為：規則文字說附理由就可以，LLM 照寫理由照樣被擋——入口是假的；豁免則放太寬，一句「先這樣」可能指別的事，卻清掉紅測。
- 更好的做法（甲）：例外接成結構欄位（收尾檢核 (b) 或一個「不做的理由」宣告：風險、為什麼超出），程式只查有沒有、留帳。使用者豁免要對到具體事項：LLM 引用使用者原句並指出豁免的是哪一項，程式核對原句存在。
- 同類還在：P2 的「否」字否決。

### P8 記憶寫入去重：相似度門檻直接拒寫
- 位置：`tools/memory-write-gate.py` 約 387–441 行（0.8 similar、0.95 duplicate）、`tools/workflow-guardian-mcp/lib/atom-tools.js` 約 223–231 行。
- 現在誰判：程式，相似度數字。
- 要不要判斷：要。「同一條知識、取代舊卡、還是不同的事」是判斷。
- 不合理，因為：取代舊卡本來就該很像；維護軌實例：supersedes 改名被判重複擋住。另一處事實不符：品質分數 0.3～0.5 的 `ask` 在 js 端沒有對應分支，等於直接寫入，和設定說明不一致。

## 第二節：舉一反三——同類病的其他位置（核准第一節後一起排）

**類 1 用字詞清單判語意**（共通病：否定句、轉述、別人的文字會誤觸）

**類 2 用代理指標判「關聯」**（共通改法：先找查得到的事實，剩下交 LLM 宣告）

**類 3 用數量門檻判「夠不夠」**

**類 4 同一件事各閘定義不同**（共通改法：一個定義、一支函式）
- 「讀過」：OverviewHub 認 Bash 唯讀指令（BASH_READONLY_COUNTS_AS_READ），收割與 AtomAudit 只認 Read 工具（`stop.py` 約 221–266 行）。

## 第三節：合理、建議保留的固定規則（附理由）
- **收據防偽造**：跑程式白名單、指令換目錄不採、暫存目錄不算、哨兵字樣——判的是「收據是不是真的」，不是「該不該測」；屬已定裁決的防線邊界。
- **證據級**：實測只配收據、全推論最多算部分、紅收據不算試過——G10「沒試過不算結論」直接定的規則。
- **擋次預算、放行固定字樣、沒人可問就擋到底**——原設計者已裁定的流程。
- **程式檔副檔名、執行期資料目錄、快取目錄**——是定義不是判斷；判不出照算程式（寧擋）。
- **隱私檔清單、跨層寫入閘、寫入目標判不出就擋**——安全邊界。
- **定位四行只查結構**（兩個候選、理由、角色不照抄節點）——這就是「程式管有沒有判斷、不替它判」的正確樣子（根因層詞彙限制除外，見類 4）。
- **驗證範圍宣告**（C-驗證範圍）——現成的好樣子：程式只判「改了程式要宣告」，範圍內容交 LLM。

## 第四節：批判與舉一反三兩問接進關鍵點（提案，跟第一節一起審）

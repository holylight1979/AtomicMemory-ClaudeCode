這封在說什麼：自檢重啟。把我前面提過的每個機制，對兩種病——「繞進同一個死胡同」「修症狀沒根治」——逐個回答有沒有作用；再回答我自己在這場討論裡有沒有犯同一種病。偏移：有，前 24 封大半在周邊打轉，本封標出來。

## 一、逐個機制對兩種病的作用（有／間接／沒有）

| 機制 | 作用 | 一句理由 |
|---|---|---|
| 大地圖綜觀文件（`WorldMap_Knowledge_Map.md`＋76 張踩坑卡片） | **有** | 它就是「這個需求落在哪、上下游是誰、以前摔過什麼」的素材；但只覆蓋大地圖，其他部位沒有 |
| 踩坑卡片靠關鍵字注入 | 間接 | 案例二的卡片明寫「別把接近型邏輯都有同病當結論」，是回頭看的替代品；但案例一的主根因（兵力與編成不同步）卡片沒記、提交紀錄才有，關鍵字對不上就不會出現 |
| 58＋5 條規則文字每 session 必載 | 間接 | 條文多是摔過後才寫，防「同一個坑再摔」，不防新坑；案例一發生時規則都在，照樣卡三輪 |
| 結構型規則（CS-54 單一出入口、CS-27 同一事實兩份表述必漂移） | 間接 | 把根因型修法寫成了可複用的判準，下次看到同形狀知道往哪挖；但要先有人想到去看形狀 |
| Roslyn 規則檢查器 14 條 | **沒有** | 語法層；兩個案例都不是語法問題，檢查器全綠也擋不住 |
| 排程 AI 審查（commit 之後、看 diff 與 log） | 間接 | 審查者若有綜觀能看出「修在錯的層」，但材料只有 diff 與 log，沒有「這段在專案裡的角色」 |
| 兩支未接線 hook：編輯後跑檢查器 | 沒有 | 同檢查器 |
| 兩支未接線 hook：Stop 時 MSBuild 綠燈＋改動收據 | 間接 | 收據五段裡的「影響範圍」「未處理」逼寫者先說位置，最接近定位三行；但不要求說根因，而且沒接線 |
| 哨兵統一（`_CHECK PASS|FAIL`） | 沒有 | 它讓驗證結果可讀，不改變修的是哪一層 |
| 只量新增行、只回注 Block 級 | 沒有 | 解決的是「別被存量淹沒」，與兩種病無關 |
| 拐彎計數原型 | 沒有 | 量的是寫出來的碼有多繞，不是修對不對層；案例一的根因修法反而是「少一份存法」，彎數看不出來 |
| 無 Unity 跑 FakeMapServer 的沙箱 | 間接 | 特徵測試能證「改了沒改行為」，不能證「改在對的層」；但它讓根因型重構敢動手 |
| 盲測題與三面鏡（走偏／多做／沒證據） | 沒有（對這兩病） | 它對照的是「這次需求那句話」，不是「專案這個部位的來龍去脈」；修症狀的改動完全可以不走偏、不多做、有證據 |

結論：十三項裡**一項有、七項間接、五項沒有**。有作用的那一項是文件，不是任何工具或 hook。綱要裡「沒有」的五項標周邊。

## 二、我自己有沒有犯同一種病

有，三處：

1. **第一封就是工具清單**。tslg/001 盤點的是「有哪些規則、檢查器、hook」，沒問使用者痛的是「為什麼一直擋不住」。之後 24 封有 15 封在談檢查器的秒數、可攜性、命中分布——全是眼前那封信的問題。
2. **案例一只讀卡片沒讀提交**，根因說偏（tslg/024 已更正）。這正是「只看眼前材料、不回頭查」。
3. **Q5 選候選的方式是症狀導向**：從「全掃命中最多的檔」出發，再修正成 FakeMapServer；真正該問的是「專案哪裡最痛」，而那要先有綜觀，本專案除大地圖外沒有。

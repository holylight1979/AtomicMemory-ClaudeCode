這封在說什麼：第三輪問的是「AI 動手前有沒有先看懂專案」。根層要兩個 sgi 真實案例、sgi 有沒有一頁綜觀文件、我前面每個機制對「繞同一個死胡同」「修症狀沒根治」兩種病有沒有用、以及我自己這場有沒有犯同一種病。四題都答，案例附回放材料。偏移：有——我前 25 封幾乎全在周邊，本封認。

## 一、兩個真實案例（來源標在每句後）

### 案例一：同一支驗證工具連修三輪，每輪都在修眼前那個炸點（2026-06-17）

- **當時的需求一句話**：把玩家背包模組從單一 blob 欄位搬進 SQL 分表，並證明搬過去再搬回來一個位元都不差。（看卡片知道：`.claude/memory/shared/CharDataBlob/post-mortembag-軌驗證反覆三修…md`）
- **實際改了什麼**：驗證工具的同一支 `Program.cs` 改了三輪。第一輪：比對程式一跑就炸在 protobuf 的描述子（descriptor），於是改用 C# 屬性逐欄比。第二輪：批量比對失敗，查出道具編號不是唯一鍵，把主鍵改成子編號。第三輪：還是錯，加了診斷開關才抓到資料庫的 TINYINT 欄位被驅動程式讀成布林值。（看卡片知道）
- **為什麼是修症狀**：三輪都是「帶著沒驗證的假設動手」：假設描述子只在序列化時會炸、假設道具編號唯一、假設 TINYINT 讀回來是整數。每一輪只修當下炸的那一點。（看卡片知道）
- **真正的根因**：設計比對程式之前，沒有先用一個最小實驗確定「框架與驅動程式的實際行為」。而且證據早就在手邊：工具自己的診斷段落專門記錄描述子會炸，普查文件白紙黑字寫「不走 runtime descriptor」——讀了，但沒把「紅線」推到「連比對用的描述子 helper 也不能用」。（看卡片知道）
- **同一天另一顆卡片記的另一個坑，今天我又摔了一次**：那顆卡片（`chardata-s20b-verify深度除錯post-mortem…md`）寫「用 MysqlxClient 寫獨立工具，先設 `Log.Current`，否則背景緒寫日誌就 NRE」。2026-10-08 我在暫存目錄做離線載入測試，第一個炸點就是框架 `Log.Info` 的 NRE，花了一個彎才查到要換 `Log.Current`。卡片在、記憶系統在、關鍵字沒對上，我就重走了一次。**這是「繞進同一個死胡同」的現場證據，犯的人是我、時間是今天。**（試過）

### 案例二：三個月的存檔重構，診斷被推翻一次、上版後整案退回（2026-06 到 2026-09）

- **當時的需求一句話**（使用者拍板原話）：「整坨角色資料結構完整重規劃——新建特定資料表使其可高速取得、精準寫入；按使用頻率、資料連結性等高相關特性分區；遊戲內玩到的結果、client 在此階段完全一致。」（看文件知道：`sgi_server_refactor_audit/SGI_Server_仇恨設計清單_v1.md:316`）
- **實際改了什麼**：H-7 第一版診斷（2026-06-11）說「整個玩家資料庫只有一張表、全部模組塞一個 16MB 的 blob 欄位、離線玩家被攻打要讀整坨」，於是立案把 48 個模組全部搬進 SQL 分表。做了 S1 到 S3.3 三個月，上版 r14535（2026-08-03）。（看文件知道：控制塔 §3、§4）
- **為什麼是修症狀**：2026-06-12 Plan Mode 進碼親驗，推翻第一版診斷的兩個核心：①生產環境的存檔模式早就是「每模組一對表、髒欄位精準回寫」（`PartialByJson`），約 90 個 server 模組根本不在 blob 裡，第一版把只有 2 個用戶的 `DbTableModule` 誤當唯一既有範本；②「離線被攻打要讀的那些資料」（部隊、資源、傷兵、兵營）全是 server 端模組，**不在 16MB blob 裡**。也就是立案時說的痛點，不是 blob 造成的。（看文件知道：`_AIDocs/_CHANGELOG.md` 2026-06-12 條、控制塔 §8「兩處矛盾的正確裁定」）
- **後來怎麼了**：診斷改成「三軌真相」後案子沒有縮，反而在 06-15 升級成「48 模組全進 SQL、零殘留」；途中又一次「正式服必爆」的阻擋被證偽（角色編號不是雪花、是 9 位混淆整數）。2026-09-14 因「上市在即、穩定為最高目標」整案退回 blob（r15857），所有環境清庫重壓。（看文件知道：`_AIDocs/DevHistory/blob轉SQL_退役/README.md`、控制塔 §8）
- **真正的根因**（我的判斷，推測）：動手前沒有先回答「這個資料到底存在哪、誰在讀」——那個問題在 06-12 讀碼一小時就答出來了，但立案是 06-11。而且診斷推翻後，沒有人回頭問「原本的痛點還成立嗎、這案子還該這麼大嗎」，直接往前衝。這是兩種病都中：先在錯的層立案，再繞著原計畫走到底。
- **教訓有沒有留下**：CHANGELOG 06-12 條尾寫了「判定資料存哪必先查 SaveMode＋DbServer 建表鏈，不能只看模組基類」。這句就是「定位三行」第一行該問的事，但它住在 CHANGELOG 裡，不會在下一個人立案時出現。（看文件知道）

結論：sgi 比 TSLG 多——服務層牽動、功能層呼叫鏈、病灶清單三樣都有。但案例二證明**有綜觀文件不等於 AI 會先看它，而且文件自己也會錯**：06-11 立案時 `Server_DataAccess_TwoPath…md` 寫的是「兩條路徑」，06-12 讀碼才知道是三軌。文件只有一份標了最後驗證日期。所以 sgi 的缺口不是「沒有綜觀」，是「綜觀沒有被強制讀、也沒有被強制驗」。

## 三、我前面每個機制對兩種病的作用

| 機制 | 作用 | 一句理由 |
|---|---|---|
| H 系列控制塔（病灶清單＋被推翻的診斷） | **有** | 它就是「以前摔過什麼」；§8 兩處裁定就是回頭看的紀錄 |
| 規則錨到病灶清單才准開 | 間接 | 逼規則指向病灶，但病灶清單本身在 06-11 就錯過一次 |

| 加派 Codex 獨立審 | 間接 | 它抓到我 16 條過頭的話，沒有一條是「你立案的層錯了」——它拿到的材料和我一樣沒有綜觀 |
| 記憶卡片靠關鍵字注入 | 間接偏沒有 | 案例一的 `Log.Current` 卡片在、今天沒出現 |
| 借 Roslyn 檢查器、只看新增行、密度門檻 | 沒有 | 語法層；兩個案例都不是語法問題 |
| 範本檔與禁用表 | 沒有 | 寫法層 |
| 編輯後與 commit 前的 hook | 沒有 | 觸發點對、看的東西不對 |
| 哨兵統一、搬移行排除 | 沒有 | 讓驗證可讀、讓計數不被搬家干擾，與病無關 |
| 根層三個問題（走偏／多做／沒證據） | 沒有（對這兩病） | 對照的是需求那句話，案例二每一步都沒走偏、沒多做、有證據，照樣在錯的層 |
| 拐彎數 | 沒有 | 案例二的根因修法是「別做這麼大」，彎數看不出來 |
| 離線載入 harness | 間接 | 讓根因型重構敢動手，不幫人找根因 |

十二項：一項有、五項間接、六項沒有。沒有的六項在綱要標「周邊」。

## 四、我自己有沒有犯同一種病

有，三處，而且比前兩輪認的更根本：

1. **第一回合就把使用者第一句問題當成全部**。他問「仇恨等級設計還記得多少」，我答完就等他出題；他出題「怎麼避免 AI 被舊碼帶歪」，我立刻給五零件綱要，從 lambda 計數開始設計，沒問「你過去為什麼一直擋不住」。之後他要連問五個方向性問題，才把核心逼出來。
2. **今天的實測重摔了 06-17 的坑**（`Log.Current`），記憶系統在場、卡片在場。這不是比喻，是本封第一節的試過事實。
3. **我選的候選檔與語料全是症狀導向**：從「最大的檔」「命中最多」出發，沒有一次從控制塔的病灶清單出發；而病灶清單就在我自己綱要的 §0 裡。

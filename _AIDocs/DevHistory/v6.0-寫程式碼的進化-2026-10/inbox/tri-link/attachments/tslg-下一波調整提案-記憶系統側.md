# 下一波調整提案（記憶系統側）— tslg 槽的側觀吸收（2026-10-09，T1～T17 之後）

> 給誰：根層（主控台）彙整下一波計畫用；SGI 對照用。
> 寫法：每條＝【觀察（這波哪件事、哪封信）】→【要改記憶系統的哪一層：hook／MCP／atom 注入／萃取範圍／變量】→【怎麼驗它有用（可量的數字）】。證據級照三方慣例：試過／看程式知道／推測。
> 一句總結：這波證明「有東西可看＋在對的時機送到眼前＋動手前被要求先看」三件事缺一不可；下一波要把三件事從「人派工做出來」變成「裝了原子記憶系統就自動發生」，而且要能量。

## 0. 先定義「自動達成」要量什麼（否則下一波又變成做了一堆機制、不知道有沒有用）
- **S1 首改前綜觀**：第一次 Edit 某部位的檔之前，讀了幾個檔、跨幾個目錄、有沒有讀該部位導讀卡（`_overview-hub.log` 已有：`reads_after_inject`、`located`、`located_via`）。基線（R4）：三邊首改前平均讀 10 檔跨 4 目錄；正樣本 23～37。
- **S2 同題改幾輪**：同一檔 14 天內被 ≥2 筆 fix 改到（根層已有算法，svn log 版要補）。
- **S3 修根因比例**：定位三行「根因層」那行寫「根因」且前例指到一張真卡的比例（log 可加 `located_quality`）。
- **S4 工具靜默失效率**：SessionStart 自檢紅燈數（rule_check selftest／smells build／Bridge）。
- **S5 注入命中率**：被注入的卡在同 session 後續被 Read／引用的比例 vs 被 AtomAudit 判「無關」的比例（本場：4 顆 cold 卡被問，3 顆無關）。
這五個數字 SessionEnd 自動算一次寫進 `workflow/`，下一波每條機制都對應其中一個。

## 1. 「有東西可看」——導讀卡成為專案的必備產物，不是這波人工補的
- 觀察【試過】：七張部位導讀卡是這波最有效的注入（大地圖、戰鬥、工具 MCP 三張在我動手前都真的改變了我讀什麼）；但它們是 T7～T10 人工一張張寫的，寫入被三個閘（去重 0.816、矛盾誤判、預算 3072）各擋過。
- 要改：
  1. **卡片結構化**：標題含「導讀／hub索引」的卡，write-gate 檢查五段都在（部位與邊界／上下游與權威／動手前必問／已知病灶／驗法＋`Depends:` 必填）；缺段擋回，附範本。現在只擋相似度與預算，不擋「少一段」。
  2. **對照表成為專案根層契約**：`<專案>/.claude/overview-map.md` 由 `install.py --verify` 檢查存在且每列卡名存在；沒有就提示用 skill `read-project` 產生——`read-project` 改成直接產五段導讀卡＋對照表列，而不是只產 DocIndex。
  3. **現況帳不進卡**：預算 3072 這次逼我把「15→7、三個入口名」壓成一行、帳放 `_AIDocs` 文件——這是對的，把它寫進 write-gate 的擋回訊息與 `read-project` 範本（卡＝指標＋必問＋病灶指標；數字與清單一律文件）。
- 驗：S5（注入後被引用率）、`Depends` 過期偵測在健檢出現的次數（T17 補掛 3 檔後應可量）。

## 2. 「在對的時機送到眼前」——注入從「關鍵字命中」加上「部位親和」
- 觀察【試過】：R5 以路徑前綴判部位、第一次碰到就整卡注入，是這波命中率最高的注入；相對地，純關鍵字 cold 注入在本場被 AtomAudit 點名 4 顆有 3 顆無關（dotnet SpecialFolder、project-todo、程式註解規範）——它們的 trigger 字對上了任務域，但跟我正在改的部位無關。
- 要改：
  1. **atom 加 `Part:` 欄**（值＝對照表的範疇名，寫入時由路徑或 trigger 自動推、也可手填）；UPS 注入排序加「與本 session 已碰部位相同」的加權（變量 `part_affinity_boost`，預設 1.5），不同部位的 cold 卡降權或不注。
  2. **部位 = 一個萃取範圍**：`memory_search` 與注入都支援 `part=大地圖` 過濾；根層的「不同範圍所需萃取 atoms」就落在這個欄位，而不是再開一層資料夾。
  3. **根因層卡掛在部位上**：對照表一列多卡全注已做；再加「觸發詞 → 根因層卡」：使用者或 AI 說「改了還是不對／又壞了／第 N 次修」時，UPS 注入當前部位的根因層卡並附兩問（這個數值有幾份存法？這個失敗有沒有訊號？）——這兩問是本場大地圖兩個歷史案例的共同形狀，比任何規則都先問。
- 驗：S5 升、AtomAudit「無關」比例降；S2 同題改幾輪降。

## 3. 「動手前被要求先看」——R5 從 dry-run 走向可量化的擋，但擋的是「沒看」不是「沒交格式」
- 觀察【試過】：三管道後正樣本 13 筆，但全是刻意做的；真正的負樣本形狀是「注入由 Edit 觸發、注入後讀 0 檔就改」（T12 那五筆）。另：定位三行寫在回覆文字會被 harness 掉字（本場 2/3），Bash 註解穩。
- 要改：
  1. **擋的判準改成「注入後讀檔數 ≥ N 且三行有交」**（變量 `min_reads_before_edit`，預設取該專案 R4 基線的一半，TSLG＝5），只交三行不讀檔仍擋；dry-run 期先只提醒。
  2. **注入文字自帶「填空範本」**：把該部位已知病灶卡名列成選單，前例那行要求「填一張卡名或『無』」——可機器核（卡名存在即 `located_quality=linked`），比自由文字可量。
  3. **三行的持久化**：hook 注入文字直接教「放在下一個 Bash 指令開頭的 `#` 註解」（已做）；再加 PreToolUse 對 Edit 的檢查若發現三行只在 thinking，提醒改放工具參數（因為下一 session 看不到 thinking）。
- 驗：S1、S3；開擋後「被擋次數／每次被擋後讀檔數」。

## 4. 「不修症狀」——把專案的病灶候選池變成機器產物並注入
- 觀察【試過】：smells v2（容器散落／讀路徑／純轉接／入口可達性）＋ #88 缺陷文件就是候選池；Codex 盲測只憑這份輸出就挑中 2/3 真問題還多挖一個潛伏缺陷。但這份報告現在是人手跑、人手讀。
- 要改：
  1. **專案工具卡登記「候選池產生器」**：`overview-hub.json` 加 `smells_cmd`／`smells_report`；SessionStart（或第一次碰部位時）若報告超過 N 天就背景重跑，注入時附該部位的前 5 筆（容器散落、只有測試入口）當 cold 指標。
  2. **MCP 工具 `project_smells(part)`**：AI 要「找最該修」時主動拿，不用再記指令。
  3. **缺陷文件格式固定**（#88 那張表：位置／症狀／根因／修法／狀態），寫入閘不管它，但 `read-project` 範本要有；導讀卡病灶段只指向它。
- 驗：S3（根因比例）、盲測命中率（三邊都有數字了：TSLG 3 挑 2 中＋1 真潛伏）。

## 5. 「程式能擋的不交給 AI」＋「腳本自帶驗證」——工具自檢進 SessionStart
- 觀察【試過】：本場 rule_check selftest 綠、hook 兩支已接線，但工具卡病灶段寫「兩支 hook 未接線」是過時的；SGI 也有三支檢查器沒掛打包前。工具的共同病灶（工具卡）：「假設的環境與實際不同時靜默失效」。
- 要改：
  1. `overview-hub.json`（或專案 `.claude/verify/tools.json`）登記 `tool_selftests[]`（指令＋預期尾行哨兵），SessionStart 健檢跑一遍，紅燈進 `[Guardian:HealthCheck]`；過時的工具卡由健檢結果自動 append 一行「YYYY-MM-DD selftest 紅／綠」。
  2. 收據閘已會擋「改 .cs 沒收據」；再加「收據測試段寫『未跑』而宣告完成」的 Stop 提醒（只提醒）。
- 驗：S4。

## 6. 「數字不帶偏」＋「太慢／太吃記憶體」——基線卡要帶尺
- 觀察【試過】：MapTickPerf 的配置數字在 Editor 比 Profiler 分攤高 13 倍（Editor 自身配置混入）；smells 的「彎數」要排除分派型才不帶偏。數字沒帶尺就會被下一個人當結論。
- 要改：
  1. **基線卡型別**：標題含「基線／baseline」的卡，write-gate 要求知識行含「尺（工具＋條件）」與日期，`Depends` 指到量尺程式（MapTickPerf 卡已照此寫）。
  2. 注入：提示詞含「太慢／卡／記憶體／效能」→ 注入該專案基線卡＋量法，而不是讓 AI 憑感覺改。
- 驗：基線卡被引用時有沒有把「Editor vs 實機」寫對（人審一次即可）。

## 7. 「Codex 與 Claude 各自想」＋「第三人」——第二意見變成一個工具
- 觀察【試過】：本場三趟 Codex（填表、核草稿、盲挑）都有產出，但每趟我手工拼材料、還踩了 `--skip-git-repo-check` 與沙箱讀不到檔兩個坑。
- 要改：MCP 工具 `second_opinion(kind, part)`：自動打包（部位導讀卡＋候選池前 N＋本 session diff 或草稿）餵 `codex exec`（唯讀、skip-git-repo-check、材料內嵌），回「獨立填／核對／分歧三段」；Stop 時若 diff 落在 deny 部位可建議跑一趟（變量 `codex_review_on_stop`）。
- 驗：分歧條數與採納率（本場：Codex 抓到大地圖卡沒 Depends 這類真缺口）。

## 8. 「沒試過不算結論」——證據級從信件慣例變成 Stop 閘的輸入
- 觀察【試過】：三方信件的「分級＋自檢」有效（我自己抓到「應該直接跑卻說你要我就跑」）；但 session 收尾訊息沒有這個格式。
- 要改：anti_evasion_report 的 (a) 欄要求每項帶證據級標記；Stop 閘對「綠／通過／驗過」字樣抽查本回合是否有對應工具輸出（exit 0／OK）——只提醒不擋。
- 驗：S4 與「說綠但沒輸出」的提醒次數。

## 9. 這波 TSLG 可以當下一波的驗證場（不用再開新戰場）
- 已有：7 張導讀卡、對照表、覆蓋檔、smells 報告、#88 缺陷文件、MapTickPerf 基線、無人值守 Unity 鏈（拉起→登入→進圖→量→停）。
- 下一波每條機制做完，我這邊能跑的量：S1～S5 自然數據（要等真工作，但可以用「真的接 25 入口裡一個」當真工作）、盲測重跑、Codex second_opinion 一趟、selftest 健檢。
- 建議順序（CP 值）：§2 部位親和（改排序、零新資料）→ §3 擋的判準（改一個變量）→ §1 卡片結構化（write-gate 多一段檢查）→ §4 候選池注入 → §5 自檢 → §7 工具化 Codex → §6、§8。

## 10. 我這邊沒把握、要主控台定的
- `Part:` 欄的值要不要全域統一（各專案對照表的範疇名不同）；還是只在專案 shared 層有效。
- 候選池（smells）跑一次 8 秒、要 dotnet；SessionStart 背景跑會不會撞 Windows 黑窗那個坑（MCP 雙開那張卡）。
- 「同題改幾輪」用 svn log 算的版本誰寫（根層有 git 版）。

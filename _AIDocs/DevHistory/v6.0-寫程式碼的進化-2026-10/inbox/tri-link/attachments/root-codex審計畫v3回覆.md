建議先補齊「自動產生專案知識、跨環境執行契約、結果驗收」三個缺口，再決定哪些差異需要變量；以下僅依三份指定文件審查，段落簡稱「計畫」「SGI」「TSLG」。

**（1）角色分工與變量總表**

| 判斷 | 理由與建議 |
|---|---|
| `ledger_path` 沒有足夠理由開放專案覆蓋。 | 既有哨兵格式不同只需要輸入轉換，不需要改帳本位置，固定根層落點反而符合收尾與審查共用證據的設計（計畫§二②、§五；SGI§一#3）。 |
| `locate_template` 可收回根層，專案差異保留在 `locate_extra`。 | 「想換問法」不足以支持覆蓋核心定位契約，否則專案可能刪掉根因或前例要求，而真正的部位必問差異已有第四問承接（計畫§三H4、§五；SGI§二「部位」）。 |
| `min_overview_evidence` 不宜整包開放覆蓋。 | 兩份輸入沒有支持專案停用讀卡要求，零 Depends 應由冷啟動或部位狀態明確處理，不能把必要證據降成任意門檻（計畫§五、§八第2點；TSLG§三，亦即§3）。 |
| `part_affinity_boost` 建議先維持根層預設，待有校準證據再開覆蓋。 | 「cold 卡太多或太少」不能區分候選池品質、錯誤標籤與排序權重問題，直接交專案調倍率容易把召回缺陷調成看似正常（計畫§三H3、§五；TSLG§2）。 |
| SGI 要求的「唯一讀起點路徑」沒有明確設定欄位。 | 部位卡、病灶清單與檢查器已有 profile 欄位，但專案權威入口仍未被命名，應補可繼承的入口引用而非讓 session 自行猜測（SGI§二「專案」；計畫§五、§七）。 |
| 候選池筆數與根因卡觸發映射尚未定成設定契約。 | TSLG 明提前5筆及「觸發詞→根因層卡」，計畫卻留下多處未定義的前 N 與固定兩問，應區分根層預設筆數、部位卡引用和可增補觸發詞（TSLG§2第3點、§4第1點；計畫§三H5／M3／M4、§五）。 |
| `min_reads_before_edit` 不算漏項，效能門檻也不應重複新增。 | 前者已被第三版明確改成讀卡與 Depends 證據，後者已有 profile 量尺門檻欄，真正要補的是型別、單位與覆蓋規則（TSLG§3第1點；SGI§一#7；計畫§七、§九TSLG裁決）。 |
| 「專案層擁有並維護全部知識產物」最容易把 session 拉回修症狀。 | 配上根層只調預設與修閘的角色，機制缺口可能再次被專案補卡、補表、補檢查器遮住，應明定根層負責產生與更新流程、專案只提供領域事實，且本波不得要求兩專案補做（計畫開頭範圍、§四；SGI§零；TSLG§1）。 |
| 公司層仍缺知識歸屬契約，只有設定覆蓋不夠。 | M2 只有部位、global、shared、local 路由，未交代公司工具卡與僅公司適用教訓如何儲存、召回及隔離，應補公司作用域而非只加同名設定檔（計畫§三M2、§四公司層、§七；SGI§二）。 |

**（2）多專案奇耙設定**

| 判斷 | 需要的不同做法或漏列情境 |
|---|---|
| `path_bases` 只能找得到檔案，不能保證找對檔案。 | 若兩個基準下同名相對路徑都存在，必須讓每列明示基準或使用具命名空間的路徑引用，並把歧義列為錯誤（計畫§五、§六「表裡路徑兩種基準」）。 |
| `vcs: auto` 吸收不了跨 repo、跨 server 的受測版本。 | 偵測版本控制種類之外，還需要 repo 身分、部署目標與各 repo 內容快照的對照，單一 rev 加改動檔名不能識別未提交內容或實際執行版本（計畫§三H6、§六「3 repo 2台server」；SGI§一#12）。 |
| `codex_cmd` 與材料內嵌處理的是不同故障。 | 內嵌材料可解讀檔不可達，程序起不來則需要啟動能力檢測與明確失敗回報，覆蓋指令或寫 atom 都不能證明執行器已可用（計畫§六「1385」；SGI§一#1；TSLG§7）。 |
| `sentinel_regex` 只能辨認文字，不能吸收驗證語義。 | 不同腳本須映射成含檢查項、受測範圍、PASS／FAIL／DONE 與 exit 的統一紀錄，並處理同次輸出的多個結果，不能只拿最後一個哨兵代表整次驗證（計畫§三H6、§五、§六「哨兵格式不一」；SGI§一#3／#6）。 |
| 把 Unity 量尺寫成自由文字，只完成登記而未完成自動執行。 | TSLG 已有「拉起→登入→進圖→量→停」鏈，根層需要可掛接的前置條件、執行、收證與清理介面，否則 H8 仍依賴 session 人工完成整條鏈（計畫§六「Unity Play Mode」；TSLG§9）。 |
| 第六節漏列了 transcript 掉字與讀檔通道差異。 | 應把 Bash 讀檔、一般 Read、工具參數與回覆文字轉成統一可觀測事件，不能用定位格式設定假裝不同通道都能被可靠收集（SGI§二「跨專案」、§三；TSLG§3）。 |
| 第六節漏列了「既有卡沒有 Depends 或引用已過期」。 | 新卡必填不會修復 SGI 的既有零覆蓋卡與 TSLG 的過期引用，根層須提供覆蓋率、失效引用健檢及缺資料時的退化行為，本波可用固定樣本驗證而不修改兩專案（SGI§一#8、§三；TSLG§1驗法；計畫§三M1）。 |
| 第六節漏列了「相同掃描數字代表不同設計意圖」。 | SGI 的刻意分層與 TSLG 的分派型排除需要掃描結果分類、理由與領域判讀契約，無法只用數值門檻吸收（SGI§一#5；TSLG§6；計畫§三R3、§六）。 |
| 第六節漏列了不同框架的重構證法適用性。 | P2 的舊源碼解析與新建置反射是特定證法，泛用根層須允許替換預期值來源與執行器，並明示不支援範圍（SGI§一#13；計畫§三P2、§六）。 |

**（3）機制與結果題組的落差、矛盾及重複**

| 機制或關係 | 審查結論 |
|---|---|
| H1／H4 的驗法尚不能證明修到根因。 | 歷史回放未定義根因正確性的評分，而 S1／S3 只驗讀過與填過，須加入「格式全對但修錯層」及「無前例但修對」的反例（計畫§二結果題組「核」、S1／S3、§三H1／H4）。 |
| H2 的 S2 不能單獨量出壓縮後是否維持目標。 | 同檔 fix 次數受任務與提交習慣影響，須用同一任務壓縮前後的對照案例，直接驗目標、限制與跨部位線索是否保留（計畫§二S2、§三H2）。 |
| H3／M2／A1 的召回與引用不能證明教訓已被採用。 | 應增加已知舊碼陷阱的後續修改題，檢查是否重犯及教訓能否持久找回，A1 雖誠實限定只驗召回，仍不足支撐其對應行為要求（計畫§三H3／M2／A1、§二S5；SGI§一#2）。 |
| H5／M4 的固定候選池只能驗排序，不能驗自動發現問題。 | 題組已提供候選與優先項，未測缺病灶文件、未出現觸發詞或報告過期時是否仍能找出高價值根因（計畫§二結果題組H5／M4、§三H5／M4；TSLG§4）。 |
| H6／R2 的三個負例不足以驗收可靠對帳。 | 全部都提醒也能取得高攔截率，須補合法 PASS、DONE 的量測宣告、多哨兵及修改後重測等正反例，同時計算漏收與誤報（計畫§二結果題組H6、§三H6／R2）。 |
| H7／R1 的紅燈數量不等於靜默失效檢出率。 | 未執行或未接線的檢查也可能沒有紅燈，須故意破壞依賴、接線與哨兵輸出，再驗是否在使用前被發現（計畫§二S4、§三H7／R1；TSLG§5）。 |
| H8／R3 的「基線卡三欄齊」不能證明數字沒帶偏。 | 即使工具、條件、日期俱全仍可能混用 Editor 與實機數據，須提供不可比較的數據對及刻意分層案例，驗最終判斷而非欄位存在（計畫§三H8／R3；TSLG§6；SGI§一#5）。 |
| M3 的三段齊全率與時間戳不能證明同材料獨立作答。 | 須驗兩方輸入材料雜湊相同且答案互不可見，並分開測獨立診斷與讀取 Claude 草稿的審查模式，因為先落檔仍可能把答案放進材料包（計畫§三M3、§二結果題組；TSLG§7）。 |
| M1 的第二次寫入成功率與 P2 的單一常數變異都過窄。 | 前者不能證明教訓完整保存且下次可取回，後者只能證明抓得到那個常數變化，應各補語義保存與多類行為變異案例（計畫§三M1／P2、§二結果題組P2）。 |
| T1 的驗收明確避開了整份計畫要保證的結果。 | 零卡專案只驗入口、骨架與提示而排除綜觀，無法支持「任何人、任何專案自動達成」的主張，須增加無人工預填知識的首次任務驗收（計畫§一「新」、§二結果題組「新」、§八）。 |
| T3 與 P1 缺少各自的結果驗收。 | T3 須驗回路是否導向正確介入而非只產分數，P1 須驗檢查失敗確實阻止下游動作，現有 S1～S5 與空白驗欄都沒有涵蓋（計畫§二「數字→行動回路」、§三T3／P1）。 |
| H1 與 H4／H5 有提示策略上的張力。 | H1 依據「先寫定位反而提早停止」改用探索提示，H4／H5 卻仍把交三行與填前例列為主流程，須驗組合後是否重新誘發填表即完成（計畫§三H1／H4／H5、§四專案層）。 |
| H4 與 T1 的冷啟動契約尚未接合。 | 骨架卡允許空段且可能尚無可讀 Depends，H4 卻要求讀卡與至少一個 Depends，允許前例填「無」並未解除這個前置條件衝突（計畫§三H4／T1、§八第2點）。 |
| H8 與 H6 對「試過」的證據語義可能衝突。 | H8 量法可產生 DONE，但 H6 對標【試過】的句子只認 PASS，應分開驗「已量測」與「已達標」兩種宣告（計畫§三H6／H8、§六「量測類不是判定」）。 |
| H6 與 R2 是已明示合併驗法的重複責任，不宜算兩份獨立效果。 | 應由 R2 定義宣告與證據分級、H6 負責紀錄及核對，避免各自判定同一句話或重複計算驗收成果（計畫§三H6／R2）。 |

**我最懷疑的三件事。** 第一，所謂「自動化」仍建立在專案已有人補好卡、病灶表與量尺的前提上，而零知識情境被排除在成效驗收外（計畫§四、§八）。第二，系統可能把「會讀卡、會填定位、會印 PASS」誤認為「會找根因、會正確驗證」，現有題組尚不足以拆穿這種表面合格（計畫§二S1／S3／S4、§三H4／H6）。第三，「多專案差異一律靠變量」可能只是把尚未設計好的執行、版本與作用域契約交給使用者配置，最後仍需專案 session 手工補洞（計畫§四～§七）。

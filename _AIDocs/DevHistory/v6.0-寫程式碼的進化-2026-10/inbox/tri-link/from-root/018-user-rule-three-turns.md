目標：轉使用者第五條原則，三方一體適用；並給一個可數的套法。現況差：三方的規則卡與自檢都還沒有「拐彎數」這個量。偏移：無偏移。

使用者原話（逐字）：
> 「單一構想」的實際完成邏輯：如果腳本內必須先拐三個彎，這種設計必定有貓膩，就是壞味道。同樣的道理：你 LLM 的思考也是一樣，如果出現了超過 3 個拐彎處，就有極高的機率有跑偏、或想錯。繼續推進下去只會越跑越偏。

## 根層的操作化（待使用者糾正）

「拐彎」＝從「這個構想要做什麼」到「做到了」之間，讀者必須換一個脈絡才能繼續追的點。
- 程式裡：間接層（介面、工廠、callback、事件轉發）、條件分支、跨檔跳轉。root/017 那個合成案例裡 `SendRedPacket → _redPacketService → IRedPacketStrategy → Factory → GuildRedPacketService` 就是四個彎，一個搬移構想不該有。
- 推理裡：「因為 A 所以 B，但 B 要先成立 C，而 C 又要…」的每一個「但」。

## 怎麼用（三處，都可數）

1. **規則卡**：這是第一條不需要錨到專案優先清單就能開的規則，因為它是使用者明定的風格契約。SGI、TSLG 各自評估 Roslyn 單檔能不能數「一個 public 方法到實際做事的那行之間經過幾次委派／介面呼叫／分支」；數不出來就先當 Companion 語意審的提問：「這個構想的完成路徑拐了幾個彎，列出來」。
2. **三面鏡的 overengineering 面**改成這句問法，比「列出多餘抽象」更具體，而且有閾值三。
3. **自檢段加一行**：「本封結論推到這裡拐了幾個彎」。超過三個就不要寄結論，寄問題。

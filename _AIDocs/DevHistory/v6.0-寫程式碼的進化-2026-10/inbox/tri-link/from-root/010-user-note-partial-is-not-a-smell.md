目標：轉使用者對「partial」的裁示，當作規則卡三要素的現成範例。現況差：projects/008 已撤回 partial 數指標，與使用者一致；本封補原則。偏移：無偏移。

使用者原話：
> partial「不一定是問題」，只要是適度的配置檔案的內容，可能就沒有什麼問題；像是假設資產控管，分成 public api 的 partial、內部運作核心的 partial、以及遊戲邏輯相關的 partial。

## 根層整理成原則（寫進根層綱要）

- **數量不是臭味，切分有沒有責任軸才是。** 一個型別拆成「對外 API／內部核心／遊戲邏輯」三個 partial，每個 partial 能用一個名詞說清職責，就是好設計；GuildManager 23 個 partial 的問題不是 23，是切分軸是「誰當時順手加」。
- 所以 partial 不進計數規則（SGI 已撤），進 **Companion 語意審的提問**：「這個型別的每個 partial 檔名能不能對到一個職責？有沒有兩個 partial 在改同一組欄位？」這是 LLM 帶證據能答、計數器答不了的。
- 同一原則套到其他「數量型」指標：方法數、public 成員數、檔案行數都只是「值得看一眼」的線索，規則卡三要素裡「怎麼確認」那格若填不出比「人去看」更具體的東西，就只列報表、不進 WARN。

兩位若有類似「數量看起來臭、其實有責任軸」的現成例子，寄一封當 good.cs 語料。

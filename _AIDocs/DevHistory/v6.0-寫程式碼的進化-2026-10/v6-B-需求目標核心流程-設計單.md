| 名詞 | 白話 |
|---|---|

| 子代理 | 主 session 派出去做一塊工作、做完回報的另一個 AI |

## 現況（只寫事實）

- 系統裡跟「目標」沾邊的，現在只有**意圖分類**：用關鍵字把每則訊息分成 debug、feature、perf 等十類，拿來決定導讀卡先送哪幾段、用哪個視角。它分的是手段，不是需求目標。

- Codex 驗收審查拿到的「使用者目標」，是這個 session 第一則訊息的原文，之後不會更新。
- 定位三行、寫碼查核閘、收尾檢核，沒有任何一處問「這次的改動服務哪個目標」。

## 一、這個流程要達成什麼（G8、G0、G14、G16）

**一句話**：日後所有的需求，AI 都在關鍵處自然地「針對需求目標」——抓住這個需求真正要達成什麼、讓它在工作中長出子目標、回頭對照做法有沒有更接近；不用人提醒，換 session、壓縮之後也不會淡掉。

這個流程自己的目標樹（用第二節的格式寫，順便示範一棵樹長什麼樣）：

- **T1** 上面那一句。
  - **T1.1** 不逼人事先把目標講完：子目標可以在工作中長出來，說不清的先寫「待展開」。（原話：「一旦描述出來就已經長歪了」）
  - **T1.2** 記憶與知識類由 AI 靜默做好；寫程式類沒過目標查核不放行。（原設計者裁決）
  - **T1.3** 任何使用者、任何專案都成立，含零卡片新專案的第一個任務；不需要人貼 prompt。（G8、G14、G16）
  - **T1.4** 目標在每個關鍵點都被送回眼前：壓縮後、換 session、派子代理之後都還在。（新增；現況壓縮後只剩意圖分類）
  - **T1.5** 能用沒有預填答案的新任務觀察到效果，不是只檢查格式有沒有填。（B5）
  - **T1.6** 使用者的原話一直是權威，AI 寫的目標樹只是它的解讀；兩者都留著，審查時並排看。（新增，來自 Codex 初審）
  - **T1.7** 待展開：「LLM 抓的目標對不對」要怎麼長期看出來。程式判不了；先靠 B5 由人與 Codex 判，之後看守門紀錄的累積。

和草案相比：草案的四條沿用為 T1.1、T1.2、T1.3、T1.5；T1.4、T1.6、T1.7 是新增。

**分工原則**（全文都照這條）：

- 程式只管四件事：**時機**（在哪個關鍵點要 LLM 判斷）、**留存**（把結果記住）、**送回**（下一個關鍵點把它放回眼前）、**有沒有做**（有沒有寫、有沒有掛到已存在的目標、引用的東西在不在、先後順序對不對）。
- LLM 負責所有判斷：目標是什麼、長出哪些子目標、做法有沒有更接近、證據支持哪一條、該不該問人。
- 程式不判內容：不看目標寫得好不好、不算字數、不比相似度，也不判證據是不是真的證明了那件事。
- 因此「樹齊全、每條都有結論、引用都在」**不等於目標達成**。程式保證的是這個過程一定被走過；走得對不對，靠 LLM 自己、靠第七節的驗法。

## 二、目標樹怎麼存、怎麼活（G8、G13、G14）

### 2.1 一棵樹長什麼樣

一個需求一棵樹。樹根是「這個需求真正要達成什麼」，底下是子目標，子目標還能再長子目標。

**樹本身的欄位**（全部由程式寫）：

| 欄位 | 白話 |
|---|---|
| 編號 | T1、T2…（這個 session 的第幾個需求） |
| 使用者原話 | 這棵樹活著期間，**使用者本人打的**每一則話（含後來的糾正與裁決）；這是權威來源，樹是 AI 的解讀 |
| 同伴轉述 | 別的 session（例如總控台）用跨 session 訊息送來的話；照記，但不當權威，審查時標明是轉述 |
| 狀態 | 進行中／已對照（交過完整對照，可能還有未完的節點）／結束（每個節點都是達成或放棄） |
| 目標版本 | 節點文字、增減、樹根每改一次就加一 |
| 類別 | 寫碼類或記憶知識類；改過程式檔就升成寫碼類，不會降回（第五節） |
| 關聯改動 | 這棵樹期間改過哪些檔；每個部位在定位時指到哪個節點 |
| 待對照的改動 | 改了程式、還沒回頭對照的改動，各掛在哪個節點（4.5 的「對照義務」） |
| 關鍵點紀錄 | 每次走過哪個關鍵點、當時指到哪個節點 |

**節點的欄位**。先定三條分類軸，每條軸一個欄位，不混成一個欄位：

| 軸 | 欄位 | 可填的值 | 誰寫 |
|---|---|---|---|
| 內容 | 文字 | 用使用者的語言，只寫目標、不寫手段 | LLM |
| 內容 | 來源 | 使用者說的／推出來的／工作中長出的 | LLM |
| 清楚度 | 清楚度 | 明確／待展開（待展開時，文字寫方向） | LLM |
| 進度 | 狀態 | 未開始／進行中／達成／部分／沒有／放棄 | LLM |

其他欄位：

| 欄位 | 內容 | 誰寫 |
|---|---|---|
| 證據 | 每一筆：指標（收據、驗證案例檔、檔:行、卡名）、證據級（實測／讀碼／推論）、它支持哪幾個節點 | LLM 寫；程式查指標在不在、先後對不對 |
| 未完事項 | 狀態是「部分」或「沒有」時，接下來要追什麼 | LLM 寫；程式轉進追蹤帳本 |
| 變更紀錄 | 每次改文字或狀態：哪個回合、為什麼 | LLM 寫為什麼；程式記回合與先後序號 |
| 節點編號 | T2.1、T2.1.3… | 程式配 |

「放棄」是進度軸的終點之一。方向改了，舊節點標「放棄」並寫為什麼，不刪掉——之後才看得出方向改過。

### 2.2 存在哪

| 放在哪 | 放什麼 | 活多久 | 為什麼放這裡 |
|---|---|---|---|
| 目標檔 `workflow/need-goal/<session>.json`（工作暫存的一部分，獨立成檔） | 整棵樹、全部欄位；這個 session 的改檔與收據也在這裡蓋同一套先後序號 | 這個 session（含恢復與壓縮） | 每個關鍵點都要即時讀寫（定案②）。獨立成檔、整段「讀→改→寫」上鎖：主 session 與子代理的 hook 會同時跑，放進共用的工作暫存會互相覆蓋 |
| 續接單 | 狀態不是「結束」的樹：使用者原話摘要、節點、狀態、待展開、證據指標 | 到下個 session 接手 | 跨 session 接續（定案②）。「已對照但有未完」的樹也要帶，才不會丟掉原始目標與父子關係 |
| 既有的追蹤帳本 `workflow/tracking/<專案>.jsonl` | 完整對照時「部分／沒有」節點的未完事項 | 到結案 | 解不了的要持續追（G13）；用現有帳本，不另開 |
| 既有的守門紀錄 `Logs/guard-need_goal.jsonl` | 每次寫樹、走過哪個關鍵點、擋了什麼 | 本機紀錄 | 給 B5 判分與健檢看；不注入、不佔 token |
| 記憶卡 | 只有 LLM 判斷值得留的教訓（例：「這類需求常藏著某種沒說出口的子目標」），走現有的知識收割 | 長期 | 每棵樹都存成卡，不相關時也會佔 token |

### 2.3 一棵樹的一生

| 事件 | 樹的狀態變成 | 誰觸發 |
|---|---|---|
| 使用者提出要動手的需求，AI 寫下樹根 | 進行中 | LLM（程式在任務開始時提醒一次；寫碼類沒樹不准改程式） |
| 工作中想到、讀到、被糾正 | 不變；節點增減或改寫，目標版本加一 | LLM（程式在讀入範圍變大、被糾正時提醒） |
| 改了程式 | 不變；那筆改動進「待對照」 | 程式 |
| AI 對改到的節點交一句進度（輕量對照） | 不變；那筆改動從「待對照」移除 | LLM |
| AI 交完整對照（每個節點都有終點結論） | 已對照；若每個節點都是達成或放棄 → 結束 | LLM |
| 已對照或結束之後又改了程式 | 回到進行中，該改動進「待對照」 | 程式 |
| 已對照或結束之後又改了目標 | 回到進行中，舊的完整對照作廢 | 程式 |
| 使用者換題，AI 開新樹 | 舊樹維持原狀態（不卡換題）；新樹成為「目前的樹」 | LLM |
| 整個需求不做了 | 樹根標放棄並寫為什麼 → 結束 | LLM |

### 2.4 跨 session、壓縮、子代理（T1.4）

| 情境 | 程式做什麼 | LLM 做什麼 |
|---|---|---|
| 同一個 session 恢復 | 目標檔原樣沿用（獨立成檔，工作暫存重建也不影響它，先後序號也還在） | 無 |
| 壓縮 | 另外組一段「需求目標樹」重送，**不依附部位綜觀**（沒有部位表的任務也照送）；原本「主目標」那一行改成指向這段，意圖分類降成附註 | 讀回後照常工作 |
| 換 session | 自動產生的續接單加一塊【需求目標樹】；手寫續接單（/handoff）的模板也加這塊。新 session 讀到續接單時：還沒有樹就自動匯入並送回眼前（配新編號，記下舊編號對照）；已經有樹就提示「要接續請匯入」。匯入的證據標成「前一個 session 的證據」：只供閱讀；之後再改到的節點要交新的證據。區塊寫法對齊既有的交接品質卡（`handoff-綜觀品質與抗失真寫法`）：每個節點帶最近一次「為什麼」、證據級直接標出哪些已驗證哪些只是推論、待展開的節點就是未解問題 | 照 /continue 現有的規矩先回讀（用自己的話覆述目標與現況），確認匯入的樹還對，接著做 |
| 派子代理 | 子代理改的檔記到主 session 的樹，進「待對照」；子代理交定位第四行時，指主 session 的節點。子代理自己的回合結束**不做目標對照**（只跑現有寫碼查核） | 主 session 派工時把相關節點寫進任務說明；子代理回報後，主 session 看過它的改動、自己對照 |
| 裁判子 session（唯讀的第二意見） | 不套目標流程（它沒有寫入目標的路徑，硬套會永遠補不齊） | 無 |
| Codex 驗收審查 | 審查同時拿到「使用者原話（權威）」、「同伴轉述」與「目標樹（AI 的解讀）」，三者分開標示 | 無 |

## 三、`need_goal` 工具（G8、G6）

### 3.1 五個動作

| 動作 | 做什麼 | 主要參數 | 誰、什麼時候呼叫 |
|---|---|---|---|
| set | 寫下樹根；換題時開新樹；從續接單匯入 | `goal`（一句、使用者的語言）、`new_task`（是不是換題）、`why`（改寫樹根時必填）、`import_from`（續接單路徑） | LLM：任務開始、判斷換題、大方向改了 |
| add | 加子目標，可一次多個 | `parent`（掛在哪個節點，省略＝樹根）、`items[{text, clarity, origin}]` | LLM：工作中長出子目標時 |
| update | 改節點的文字、狀態、清楚度；也是「輕量對照」的入口 | `items[{id, text?, status?, clarity?, why}]`（why 必填：這次改動讓它更接近了沒、為什麼） | LLM：改了程式之後、被糾正、讀到新資訊、做法改變 |
| reconcile | 完整對照：每個還活著的節點交終點結論 | `items[{id, status, evidence[{kind, ref, level, covers}], followup?, note?}]`、`turns?`（拐了幾個彎，C-G11 用） | LLM：交付邊界前（4.5） |
| read | 把目前的樹送回眼前 | 無 | LLM：隨時想看的時候 |

- reconcile 的 `status` 只收終點值：達成／部分／沒有／放棄。
- 證據每一筆的 `kind`：receipt（收據）／case（驗證案例檔）／file（檔:行）／atom（卡名）；`level`：實測／讀碼／推論；`covers`：這筆證據支持哪幾個節點（由 LLM 判斷、寫明）。
- 規則（程式只核對組合，不判內容）：「實測」只能配收據；檔案、驗證案例檔、卡名只能是讀碼或推論——檔案存在不等於跑過。

### 3.2 回傳什麼

- 工具本身只回一行確認，例如 `[NeedGoal] add 已收到`。
- 緊接著 hook 補一段只給 AI 看的提示：**更新後的整棵樹**（含程式配好的節點編號），以及被拒收的項目與原因（例：update 沒寫 why、reconcile 漏了節點、證據指標找不到、實測沒配收據）。
- 所以「讀回」不必另開一條路：每次呼叫之後，AI 眼前就是最新的樹。

### 3.3 兩端各做什麼

| 端 | 做什麼 | 不碰什麼 | 為什麼這樣分 |
|---|---|---|---|
| JS（MCP 伺服器，`tools/workflow-guardian-mcp/`） | 驗參數：動作合法、必填有填、列舉值合法；不合法直接拒收 | 不讀寫目標檔、不配編號 | MCP 伺服器不知道是哪個 session 在呼叫；現有的收尾檢核、收割回報都照這條規矩，只讓 Python 寫 |
| Python（hook，工具呼叫後那一刻） | 套用到該 session 的樹、配編號、記回合與變更紀錄、查證據指標與先後、送回更新後的樹、記守門紀錄 | 不判內容好壞 | hook 帶著原始的 session 身份與回合序號 |

- 只有 Python 一個模組在寫，**不等於**同一時間只有一個行程在寫：主 session 與子代理的 hook 會同時跑。所以目標檔的每次操作（寫樹、蓋改檔、蓋收據、配序號）都是「上鎖 → 讀 → 改 → 寫 → 解鎖」一整段，不能只鎖寫入那一下。

## 四、五個關鍵點的接線（G0、G1、G6、G10、G16）

每一點分成：時機、程式做什麼、LLM 判斷什麼、兩類任務各怎麼處理。「接點」那一行是技術位置，只寫函式名、不寫行號（兩條分支還在改）。

### 4.1 新需求開始

- **時機**：使用者送出訊息的那一刻。只算**使用者本人打的字**：背景通知、子代理完成通知、別的 session 送來的跨 session 訊息都不是使用者說的話，不算。
- **怎麼分「是不是使用者本人打的」**：沿用現有的「系統產生的訊息」判斷（`wg_core.is_harness_generated_prompt`）。它原本只認背景通知與系統通知兩種開頭，跨 session 訊息會被當成使用者原話（2026-10-12 實測，見附錄 D(3)）；總控台已裁定要修，派給 a3（020b：把跨 session 訊息的開頭加進判斷）。修好之後，CommitOrder 閘、糾正偵測、本流程用的是同一個判斷。
- **程式做什麼**（只看「有沒有樹」，不看訊息內容）：
  - 沒有進行中的樹，而且是這個 session 第一則使用者訊息、或上一棵樹剛對照完／結束 → 送一句：「若這是要動手的需求，先用 need_goal 寫下它真正要達成什麼（一句、用使用者的話、不寫手段）；純問答可以不寫。」
  - 有進行中的樹 → 使用者本人打的話記進那棵樹的「使用者原話」，跨 session 訊息記進「同伴轉述」；並送一行樹根與摘要，例如「目前需求目標 T2：…（子目標 3、待展開 1、待對照的改動 2）；這則若換題，用 need_goal(set, new_task)」。這一行是送回，不是提問。
- **LLM 判斷**：這則訊息是新需求、接續、還是糾正；要不要寫樹；樹根怎麼寫才是目標而不是手段。
- **兩類任務**：這時還不知道會改什麼檔，兩類一樣。真正的強制在 4.2（寫碼類沒樹不准改程式）。
- **為什麼不每則都問**：定案①（只在任務開始或明顯換題時抓目標）。「明顯換題」由 LLM 看著每則送回的樹根那一行來判斷。
- **接點**：`hooks/handlers/user_prompt_submit.py` 的 `handle_user_prompt_submit`，放在 `classify_intent` 之後、OverviewHub `on_prompt` 之前（目標那一行排在導讀卡前面）；用 `wg_core.is_harness_generated_prompt` 排除非使用者訊息；新函式 `wg_need_goal.on_prompt`。

### 4.2 動手改程式前（併入定位三行，變成四行）

- **時機**：AI 要用 Write／Edit／Bash／PowerShell 改檔的前一刻，每個寫入目標各判一次。
- **程式做什麼**，分兩層：
  - **第一層：有沒有樹**——放在寫入目標解析出來之後、OverviewHub 任何判斷之前，所以不受「OverviewHub 關掉」「找不到專案根」「部位表沒列到這個檔」影響：
    1. 暫存檔（scratchpad、系統暫存目錄，跟現在不記進改檔紀錄的範圍相同）→ 不管。
    2. 判這個檔是寫碼類還是記憶知識類（第五節）。
    3. 寫碼類、沒有進行中的樹 → 擋下，原因：「先用 need_goal 寫下這個需求要達成什麼，再改程式。」
  - **第二層：定位**——交給 OverviewHub 原本的流程，再加三件事：
    4. 寫碼類、在部位表上的部位：定位三行變成四行，第四行是「**定位｜目標：<節點編號>——這一塊在目標裡的角色**」。程式只核對第四行指到的編號存在於進行中的樹；缺第四行、或編號不存在 → 照現有的「證據不足」擋下，並列出目前的節點讓它選。核對通過 → 把「這個部位 → 這個節點」記進關聯改動。
    5. 目標改過（開了新樹、或樹根改寫）之後，已交過定位的部位要重交：程式把「已定位」清掉，而且只認清掉之後才交的那一組。
    6. 記憶知識類：部位表上的（定位三行）與部位表外的（先讀過同目錄幾個檔）兩條門檻都跳過；「程式產物不可手改」與「設定檔有錯就擋」照舊。這一條同時完成 checklist 的「C-知識類部位」。
  - 第一次碰到某部位時送的導讀卡，開頭附上目標樹精簡版，讓「目標」與「這一塊的說明」同時在眼前。
- **各種提前結束的路徑，預期行為**：
  | 情況 | 第一層（有沒有樹） | 第二層（定位） |
  |---|---|---|
  | OverviewHub 設定關掉 | 照查 | 不查 |
  | 檔案不在任何專案根底下（非暫存檔） | 照查 | 不查 |
  | 部位表沒列到、或專案沒有部位表 | 照查 | 寫碼類照現有規則要先讀過同目錄的檔；知識類不查 |
  | 改的是 OverviewHub 自己的設定檔 | 照查 | 照現有規則放行（才修得回來） |
- **LLM 判斷**：這次改動服務哪個節點、這一塊在目標裡扮演什麼角色；修問題時列出根因候選與為什麼選這個（找不到第二個就寫為什麼不存在，沿用現有句子），做新功能時改寫方案比較。要寫幾個、寫哪一種，由 LLM 依任務判斷（C-G0）。
- **接點**：第一層在 `hooks/handlers/pre_tool_use.py` 的 `handle_pre_tool_use`，逐寫入目標呼叫 `wg_overview.on_edit` 之前，呼叫 `wg_need_goal.edit_gate`；暫存檔判斷沿用 `hooks/handlers/_shared.py` 的 `_is_ephemeral_path`（post_tool_use 記改檔時用的同一支）。第二層在 `hooks/wg_overview.py` 的 `on_edit`：知識類在 `_lookup` 之後、`_unmapped_edit` 與證據檢查之前分流；第四行核對放在找到定位三行之後、`_layer_mismatch` 旁邊；重交靠清 `located` 並把 `transcript_offset` 移到當下。第四行的解析在 `lib/overview_hub.py` 的 `LOCATE_RE`、`locate_groups`、`locate_values`、`DEFAULT_LOCATE_TEMPLATE`。導讀卡附樹在 `wg_overview._inject` → `build_injection_ex` 的開頭段。

### 4.3 讀入範圍變大、被使用者糾正、目標改變

- **程式做什麼**（三種觸發，都只提醒、不擋）：

| 觸發 | 程式怎麼知道（只計數，不看內容） | 送什麼 |
|---|---|---|
| 讀入範圍變大 | 樹開了之後，第一次碰到第二個（及之後每一個新的）部位；或樹最後一次更新之後，讀過的檔跨了 3 個以上的頂層目錄 | 「讀入範圍擴到【X】：目標樹要長新的子目標嗎？先前在【Y】的判斷要改觀嗎？」每棵樹每個部位一次，同一回合合併成一則 |
| 被使用者糾正 | 現有的糾正偵測（「不對」「重來」「不是我要的」這類字眼）命中；只算使用者本人打的字（同 4.1 的判斷） | 「使用者糾正了：目標樹哪一條要改？做法還對準嗎？」＋目前的樹 |
| 目標改變 | LLM 自己用 need_goal 改了樹根或開了新樹 | 已碰過的部位下次再讀到時，導讀卡改用「目標視角」重送一次；定位要重交（4.2 第 5 步） |

- 同一個檔放行改了 3 次以上時，另送一句「這一處改了好幾次：是不是繞路了？」——只是提醒，不當成思考拐了幾個彎的量測（C-G11 的彎數由 LLM 自己判斷）。
- **LLM 判斷**：要不要長新的子目標、先前哪個判斷改觀了、做法還對不對；有改就用 need_goal 記下，並寫為什麼。
- **兩類任務**：一樣（都是只給 AI 看的提示，不擋）。
- **接點**：讀入範圍在 `hooks/handlers/post_tool_use.py` → `wg_overview.on_read`（`_inject` 對新部位觸發時、`_record_read` 記 `reads_after` 時算目錄數）；糾正在 `user_prompt_submit.py` 呼叫 `wg_friction.record_correction` 的地方，拿它的回傳值；目標改變在 need_goal 的 PostToolUse 分支，清 `state["overview_hub"]` 各紀錄的 `located` 並記目標改變的回合；同檔多次沿用 `edit_counts`。

### 4.4 問使用者之前

- **時機**：AI 呼叫 AskUserQuestion（提問）或 ExitPlanMode（交出計畫等核准）的前一刻。
- **程式做什麼**：
  - 有進行中的樹 → 題目（或計畫）裡要寫出它掛在哪個節點，寫節點編號即可。沒寫、或編號不存在：寫碼類擋下並列出節點；記憶知識類不擋，只補一句提示並記守門紀錄。
  - 豁免：①題目含【收尾放行確認】，**而且**這個 session 真的有一筆擋滿待放行的紀錄（光加標記不算）；②還沒有任何樹（例如任務一開始就要先釐清目標）——這時改送一句「問完把答案寫進 need_goal」。
  - 通過 → 在關鍵點紀錄記一筆「問了，掛在哪個節點」。
- **LLM 判斷**：全貌對齊了沒（沒對齊就先補，不急著要人拍板，G16）；這題卡在哪個目標、為什麼卡在這裡、推薦答案是什麼；自己判斷得了的不推給人。
- **草案寫的「不擋使用者主動要求的問題」怎麼落實**：這道檢查只要求題目標上節點編號，不會讓題目問不出去。使用者主動要 AI 問的時候，標上編號照樣問得出去，所以不另設關鍵字豁免——關鍵字豁免本身會變成繞過的口子。
- **要先實測的假設**：官方文件沒寫明 PreToolUse 會不會對 AskUserQuestion／ExitPlanMode 觸發，也沒寫 ExitPlanMode 的計畫正文放在工具輸入的哪個欄位。實測步驟在附錄 D(1)，排在 A 段合併後、動工前，由原設計者配合跑；若不成立，退一步改在工具呼叫後記錄，並於下一則訊息提醒（不能擋，效果較弱，要寫進文件）。
- **接點**：`settings.json` 的 PreToolUse matcher 加 `AskUserQuestion|ExitPlanMode`；`pre_tool_use.handle_pre_tool_use` 加一個分支，呼叫 `wg_need_goal.on_ask`；放行標記沿用 `wg_release.RELEASE_TAG`，待放行紀錄沿用 `wg_release.pending_of` 與 `state["last_block"]`。

### 4.5 改了程式之後、交付之前（併入寫碼查核閘與收尾檢核）

這一點分成兩層，因為「回頭對照」與「交付」是兩件事。

**第一層：對照義務（不看措辭，每次回合結束都查）**

- **程式記什麼**：每改一次寫碼類檔，就在目標檔記一筆「待對照」，掛在那個部位定位時指的節點（沒有部位表的檔，掛在樹根）。
- **怎麼清**：AI 用 update 或 reconcile 交了一句對照，項目裡指到那個節點（或它底下的節點），而且交的時間在那次改動之後——那筆就清掉。update 的 why 寫的就是「這次改動讓它更接近了沒、為什麼」。
- **回合結束時還有沒清的**：併進寫碼查核閘的擋訊息，新增一條「(f1) 改了程式還沒回頭對照目標」。不看 AI 怎麼措辭，跟現有的「(d) 改了程式沒補驗證案例」同一種義務（track-e 已經這樣做）。
- **代價**：中途回合只要交一句進度（一次工具呼叫），不必把整棵樹結案。中途要先問使用者時，用 AskUserQuestion 不會觸發回合結束，義務留著，之後再清。

**第二層：交付邊界的完整對照**

- **哪些時候是交付邊界**：①這則回覆宣告完成（或先前擋滿時留下的宣告原話還待查）②本回合交了收尾檢核 ③**要 commit 之前**（在 commit 指令執行前就查，不是事後補查）。
- **程式查什麼**（只有寫碼類樹才擋；只查有沒有、先後，不判真假）：
  1. 有樹，而且目前的樹交過完整對照。
  2. 那次完整對照的目標版本等於現在的目標版本（之後改過目標，對照作廢）。
  3. 每個還活著的節點都出現在對照裡，狀態是終點（達成／部分／沒有／放棄）。
  4. 達成、部分都附了證據，指標存在：收據在本 session（含它的子代理）的收據裡、檔案與驗證案例檔在磁碟上、卡名找得到。
  5. 先後：證據是收據時，要晚於它所支持的節點最後一次被改動（只看那幾個節點掛的改動，不因改了不相關的另一塊而整樹重驗）。
  6. 「達成」不能只有推論；推論最多標「部分」。「實測」只能配收據。這條直接對應「沒試過不算結論」（G10）。
  7. 部分、沒有都寫了未完事項。
- **缺了怎麼擋**：在回合結束時，缺的項目併進寫碼查核閘的擋訊息，成為「(f2) 交付前的目標對照」；在 commit 前，用 deny 擋下 commit 並列出缺什麼。回合結束那一處跟現有的 (a)～(d) 共用同一個每回合擋次上限、同一個擋滿問使用者流程：擋到上限仍沒解，AI 必須用 AskUserQuestion 帶【收尾放行確認】問使用者，使用者選放行才收尾；擋滿留下的待放行紀錄跨回合承接。不另開一道閘、不另一套預算與放行規則（定案③）。
- **沒人可問時**（`claude -p` 這類非互動執行）：照現有規則擋到底。子代理與裁判子 session 不跑目標對照（2.4）。
- **收尾檢核報告**：AI 交收尾檢核時，程式自動把目標樹、使用者原話摘要與對照結果附進報告檔，HUD 視窗多一塊「目標對照」。AI 不用在報告裡重打一次，收尾檢核也不多一欄。
- **完整對照通過之後**：程式把「部分／沒有」節點的未完事項寫進追蹤帳本；樹的狀態變成「已對照」（還有未完的，照樣帶進續接單）；寫碼類樹再送一次掃視提示（C-G4）。
- **LLM 判斷**：每個節點真的達成了嗎、哪一筆證據支持哪個節點、證據是不是改完之後的實證、證據級怎麼標、還差什麼、這次在附近看到的問題哪一件最該修。
- **記憶知識類**：兩層都不擋、報告不加欄。有樹卻沒對照時，在 session 結束時記一筆守門紀錄（健檢看得到），不打擾使用者。
- **措辭繞過還剩什麼**：第一層保證「每次改程式都回頭對照過」，不靠措辭。第二層的回合結束觸發仍看措辭：AI 若一直不宣告完成、不交收尾檢核、也不 commit，完整對照就不會被強制。這種樹會一直是「進行中」，被帶進續接單、每則訊息送回、session 結束時記進守門紀錄，健檢看得到；這一段殘餘風險照實寫在這裡，不宣稱已堵住。
- **接點**：回合結束在 `hooks/handlers/stop.py` 的 `_verify_gates`（把 `wg_need_goal.goal_gate_reason` 的結果併進 `reason`，`kind` 仍是 reconcile，所以自動吃到擋次預算、`pending_release`、`exhausted_message`、`user_released`）。`_code_gate_to_the_end` 收到的是收據鍵（子代理是 `<sid>#agent:<id>`），**不拿它找目標樹**，也不在那裡跑目標對照。commit 前在 `pre_tool_use.handle_pre_tool_use` 偵測 commit 指令的地方（沿用 `_git_commit_segments`／`_svn_segments`）呼叫 `wg_need_goal.commit_gate`。宣告與待查原話沿用 `wg_evasion.claims_completion` 與 `wg_release.pending_of(...)["claims"]`。收尾檢核附樹放在 `post_tool_use.py` anti_evasion_report 分支的 `_write_aec_report_file` 之前；HUD 在 `aec-hud-html.js`（報告檔多一個鍵不會壞，HUD 不驗鍵）。

## 五、兩類任務怎麼分（原設計者裁決、G6）

- **判準**：一個檔算不算程式檔，用寫碼查核閘「補驗證案例」那條已經在用的同一份副檔名清單（`reconcile_gate.code_exts`，40 種：.py、.js、.cs、.ps1、.sh、.sql…）；沒有副檔名的檔，第一行是 `#!`（腳本）也算程式檔。
- **任務的類別**：這棵樹期間只要改過一個程式檔，就升成寫碼類，之後不降回。沒改過程式檔的（寫卡片、整理 _AIDocs、改 rules、改設定 json、寫設計單）都是記憶知識類。
- **清單怎麼合併**：現在的寫法是專案設定直接**取代**預設清單（給一個空清單就整個關掉）。改成**聯集**：預設 40 種是底，各層只能往上加，不能拿掉。這一條同時要改寫碼查核閘那邊，兩邊才是同一份定義。
- **為什麼不在部位表加一欄「類別」**：一份定義、三個地方用（補驗證案例、目標查核、定位要不要求），不會兩邊對不上；欄位則可能被標錯，把程式碼目錄標成知識類，整段查核就失效。聯集合併後，專案只能把更多東西拉進寫碼類（例如它的 .json 資料表），不能把程式踢出去。
- **根層自己的程式**（hooks、lib、tools 底下的 .py／.js）算寫碼類，跟現在的寫碼查核閘一致；根層的卡片、規則、設定、文件算記憶知識類。這對應原話：「原子記憶知識相關的、這些在我根層的設定原本就是AI自己要透過智慧、盡量靜默做到好；而專案內的腳本相關，如果沒有經歷過我這次v6要求的目標查核通過，本來就不應該放行。」
- **改守門設定的情況**：改 `workflow/config.json`、`.claude/overview-hub.json` 這類設定不擋（屬知識類），但收尾檢核的 (f)「靜默狀態改變」本來就要列出改了設定；這類改動同時記進守門紀錄。
- **靜默版具體是什麼**：

| 關鍵點 | 寫碼類 | 記憶知識類（靜默版） |
|---|---|---|
| 新需求開始 | 提醒寫目標；有樹時每則送回樹根 | 同左（只有 AI 看得到） |
| 動手前 | 沒樹就擋；定位四行 | 不擋、不要求定位；改檔照樣記進樹 |
| 讀入範圍變大、被糾正 | 提醒 | 同左 |
| 問使用者前 | 題目沒掛節點就擋 | 不擋；補一句提示並記紀錄 |
| 改了之後、交付之前 | 沒回頭對照就擋；交付邊界缺完整對照就擋，擋滿問使用者 | 不擋、報告不加欄；沒對照只記守門紀錄 |

「內部仍走過程」的意思：AI 照樣寫樹、照樣對照，只是沒有任何一步會攔它。有沒有做到，看守門紀錄與健檢。

## 七、怎麼知道做對了（B5；G9、G10、G14）

### 7.1 原則

- 題目**沒有預填答案**：由跟受測 session 無關的作者（Codex）在測試當天出題；答案（藏著的子目標、根因在哪、檢查用的測試）由測試控制端（總控台）保管，放在受測 session 的資料根與專案根之外。第二意見工具的「封存關鍵字」只能檢查交給它的材料，不能證明受測 session 讀不到答案，所以不靠它當隔離。
- 這份設計單只寫**題型與觀察點**，不寫具體題目——寫了，受測 session 讀得到這份文件，題目就成了預填答案。
- 每題在乾淨環境跑：資料根指到暫存目錄，不帶任何卡片與歷史。
- **對照組是必要的**：同一題、相同條件，另開一個把本流程關掉的 session 再跑一次。沒有對照組，只能說「流程有被走過」，不能說「流程讓結果變好」。
- 評分同時看兩種證據：**結果**（控制端保管的檢查測試跑起來過不過、其他呼叫者是否正常）與**過程**（人與 Codex 判目標抓得對不對）。合理的替代子目標也算對，不要求跟答案字面相同。
- 過程數字（樹建了沒、對照覆蓋率、擋了幾次）只當代理，不當驗收。

### 7.2 題型

| 題型 | 題目的樣子 | 觀察什麼 |
|---|---|---|
| 一、零卡片新專案的第一次任務 | 沒有部位表、沒有卡片的小專案（真的能跑，數個檔）；使用者描述的症狀在 A 檔，根因在 B 檔，而 B 還有別的呼叫者 | ①動手前有沒有先寫目標 ②有沒有因為「B 還有別的呼叫者」長出「不能弄壞另一條路」這類子目標，長出之後做法有沒有跟著變 ③結果：症狀修好、另一條路沒壞 ④第一次改程式前，有沒有先畫出跟需求相關的最小地圖（C-G14 的前導觀察） |
| 二、藏著沒說出口的子目標 | 需求只說一件事，但做對它必然牽涉使用者沒說的第二件（例如向下相容、文件同步） | ①那個子目標什麼時候出現、來源標什麼；動手前就推得出來卻沒推，記為「部分」 ②出現之後做法有沒有跟著變 ③自己判斷得了的有沒有自己判斷，而不是丟回去問使用者 ④結果：兩件都做對 |
| 三、中途使用者糾正改了方向 | 開工兩三回合後，「使用者」說一句改變方向的話（只說方向，不說怎麼做） | ①樹根有沒有改寫並附為什麼 ②先前的改動有沒有重新評估（保留或撤回） ③舊節點標「放棄」而不是被默默刪掉 ④之後的定位第四行指到新節點 |
| 四、記憶知識類（靜默） | 例如整理幾張互相重疊的卡片 | ①整個過程沒被擋、報告沒多欄 ②守門紀錄裡仍有一棵樹、收尾有對照 |
| 五、跨 session 接續 | 寫碼類任務做到一半交接，新 session 用 /continue 接 | ①新 session 不用人重講，目標樹自動回到眼前 ②未完成的節點接著做 ③前一個 session 的證據沒被當成這次的證據 |
| 六、格式齊全但結果錯 | 一題容易「看起來做完」的任務；受測 session 交出的樹與對照完整 | 結果檢查若沒過：對照裡有沒有誠實標「部分／沒有」；若標了「達成」——記為流程沒擋住的案例，回頭看是哪一層讓它過的 |
| 七、結果正確卻被誤擋 | 一題誠實照做就能完成的任務（含中途要先問使用者、派子代理） | 有沒有被擋到過不了、或被逼著做無意義的填表；每次被擋都記下是哪一條、合不合理 |

### 7.3 誰判、怎麼判

- 原設計者與 Codex 各自拿**同一份材料**判（G9）：受測 session 的對話紀錄、目標檔與守門紀錄、改動 diff、結果檢查的輸出、最後的樹。
- 每個觀察點各給「達成／部分／沒有」，並指到對話紀錄裡的位置。
- 兩邊結果並排；不一致的列出來，由原設計者裁決並寫理由。
- 總控台負責準備環境、準備題目文字、保管答案與檢查測試、收材料；不參與判分。
- **題目與題型三的中途糾正，都由原設計者在受測分頁的輸入框親自送出**。原因：跨 session 訊息不算使用者原話（4.1；a3 020b 修好之後），由總控台送的話只會被記成同伴轉述，觸發不了「新需求開始」，也算不上糾正。不另開「測試時把同伴訊息當使用者原話」的開關——開關本身會變成繞過的口子。

## 八、如果做了什麼，會有什麼危險（G6、G10、G16；各條對應的目標寫在條內）

每條的格式：如果做了什麼 → 會發生什麼 → 這份設計怎麼處理。

1. 如果每則使用者訊息都要 AI 重寫一次目標 → 太吵，AI 會學會敷衍一句了事，目標變成填表儀式 → 只在任務開始、上一棵樹對照完後提醒；其餘訊息只送回一行樹根（定案①）。
2. 如果程式去判目標的內容（字數、關鍵字、跟原話的相似度）→ AI 會迎合格式寫，判斷又變成措辭遊戲，目標反而長歪 → 程式只核對有沒有、在不在、先後對不對。
3. 如果把「樹齊全、每條有結論、引用都在」當成目標達成 → 偏離原始需求的工作也能整齊過關（Codex 初審指出的最大風險）→ 使用者原話一直留著當權威、審查並排看原話與樹；B5 用結果檢查與對照組判效果，不用過程數字。
4. 如果要求一開始就把子目標列完，或規定子目標一定要在動手前出現 → 正是原話說的「一旦描述出來就已經長歪了」→ 允許待展開、允許工作中長出；驗收看「長出之後做法有沒有跟著變」。
5. 如果把收尾目標對照做成一道新閘、自帶擋次預算 → 同一個收尾被兩道閘各擋兩次、兩套放行規則，誠實照做的流程被拖住 → 併進寫碼查核閘，共用預算與擋滿問使用者。
6. 如果每回合結束都要求整棵樹結案 → 中途回合也被擋，對照變成照抄上一次狀態的儀式 → 中途只要求對改到的節點交一句進度；整棵樹的完整對照只在交付邊界要。
7. 如果只在 AI 說「完成」時才查 → 不說完成就永遠不查（track-e 踩過靠措辭避開）→ 「改了就要回頭對照」不看措辭；commit 前也查；仍不宣告的殘餘情況照實寫在 4.5，靠續接單、每則送回與健檢浮出。
8. 如果 commit 的檢查放在回合結束才做 → commit 已經發生，擋不回來 → 在 commit 指令執行前查。
9. 如果完整對照不綁目標版本 → 對照完再改目標，舊的對照還算數，「服務哪個目標」只剩形式 → 目標版本變了，舊對照作廢。
10. 如果證據的先後以整棵樹最後一次改動為準 → 改了不相關的一塊，已驗好的另一塊也要重驗，誠實流程被拖住 → 只看那筆證據支持的節點掛了哪些改動。
11. 如果檔案存在就能當「實測」 → 沒跑過也算試過（G10）→ 實測只配收據；推論最多標部分。
12. 如果「部分完成」就算結案、不進續接單 → 原始目標與父子關係只剩追蹤帳本裡零散的一行 → 「已對照」與「結束」分開；沒結束的樹都帶進續接單。
13. 如果記憶知識類也擋 → 違反原設計者裁決，根層整理卡片、寫文件會被打斷 → 只擋寫碼類，知識類只記紀錄。
14. 如果用部位表的欄位、或可被各層取代的副檔名清單決定類別 → 欄位一標錯、清單一清空，寫碼類的查核整段失效 → 副檔名清單改聯集合併，各層只能加不能減。
15. 如果「有沒有樹」的檢查放在 OverviewHub 的判斷裡面 → OverviewHub 關掉、找不到專案根、部位表沒列到時就整段不查，新專案剛好是最常發生的情況 → 放在寫入目標解析之後、OverviewHub 之前。
16. 如果提問的豁免只看題目裡有沒有【收尾放行確認】 → AI 自己加上標記就能避開節點檢查 → 豁免要對得上一筆真的待放行紀錄。
17. 如果壓縮後的目標重送依附部位綜觀 → 沒有部位表的任務壓縮後什麼都沒送，「目標被淡化」重演 → 目標樹獨立重送。
18. 如果目標樹跟其他紀錄擠在同一個工作暫存檔、只鎖寫入那一下 → 主 session 與子代理的 hook 同時跑時互相覆蓋，節點、改動歸屬、先後序號會掉 → 目標樹獨立成檔，每次操作整段上鎖，改檔與收據也在同一個檔裡蓋同一套序號。
19. 如果要求子代理也自己對照整棵樹 → 子代理看不到全貌、替主 session 結案；或拿錯身份找樹，永遠補不齊 → 子代理不對照，主 session 看過它的改動後自己對照；收據身份與 session 身份分開。
20. 如果 Codex 驗收審查只拿 AI 寫的目標樹 → AI 漏掉的限制，審查也跟著漏，兩家模型同一個盲點（G9）→ 審查同時拿使用者原話（權威）與目標樹（解讀），分開標示。
21. 如果匯入的舊證據當成這次的證據 → 換了 session、程式可能已變，舊收據卻還在替新結論背書 → 匯入的證據只供閱讀，之後再改到的節點要交新證據。
22. 如果把具體測試題寫進這份設計單 → 受測 session 讀得到，題目就成了預填答案 → 只寫題型與觀察點，題目當天由 Codex 出、答案由控制端保管在受測環境之外。
23. 如果讀入範圍一擴大就提醒 → 跨目錄探索時洗版，提醒變噪音 → 每棵樹每個部位一次、同一回合合併、目錄門檻 3。
24. 如果把別的 session 送來的訊息當成使用者原話 → 同伴可以替使用者下口令（例如「上GIT」放行 commit）、被算成使用者糾正、改寫目標的權威來源（2026-10-12 實測現況就是如此，附錄 D(3)）→ 只收使用者本人打的字；同伴訊息記成「同伴轉述」、不當權威；判斷由 a3 020b 統一修在系統產生訊息的判斷裡。
25. 如果為了測試另開「把同伴訊息當使用者原話」的開關 → 開關本身就是繞過的口子，忘了關或被打開都會讓第 24 條失效 → 不開；B5 的題目與中途糾正由原設計者親自送出。

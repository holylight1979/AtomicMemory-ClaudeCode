# 原子記憶系統根基調整（預計畫）：讓 AI 在任何專案寫程式時，自動綜觀、判斷、深入、驗證

> **這份是什麼**：真正動手前的預計畫。原設計者認可後，才進 Plan Mode 定執行細節。
> **怎麼讀**：前半（一～六）給原設計者看，每句只講一件事，每一項掛目標代號 G。後半（附錄）給接手實作的根層 AI，原設計者不必讀；附錄每一列也掛 G。
> **四類內容分開放**（G15）：目標（原設計者要什麼）、做法（系統補什麼）、證據（上一波看到什麼）、技術細節（怎麼實作）不混在同一句。前半只放目標與做法，證據縮成一個指標，技術細節全在附錄。
> **範圍**：只改根基，根層、專案層、公司層都能用的帶變量規則；參與的兩個專案不再調整，已做的當樣本。
> **可靠度**：【試過】有紀錄；【看程式知道】讀碼或文件；【推測】沒驗；【大家同意】三邊點頭沒驗。

## 二、核心模型：寫碼的腦要分片，依目標與讀入範圍算關注權重（回答原設計者第五點，並吸收 G1 校正）

原設計者問：「是否需要把寫程式的腦建立成架構級的分片，每次目標算不同的關注加權，像 atom 怎麼選注入那樣？」**要，而且它把 G0、G1、G2、G4、G7 收成同一個模型。**

- **分片**：每個部位的 profile 分固定幾片——邊界與上下游、權威在哪、已知病灶、驗法與量尺、層（熱修／主程式集）、規格狀態、讀路徑樣本。這是地圖的格子。
- **視角**（G1）：同一片可以用不同立場看。「理解視角」問這段在做什麼；「目標視角」拿著任務逐段評「是這裡、不是這段」；「數彎視角」數這條路拐幾個彎（G11）。
- **權重**：任務目的決定哪幾片先送到眼前、用哪個視角、先問哪題。修 bug 先病灶片與「幾份存法、有無訊號」；立案先權威片與「資料到底存哪」；查效能先量尺片；加功能先上下游與讀路徑。
- **讀入範圍**：範圍變大，認知就該更新；地圖有缺塊就補讀，不設上限（G0）。
- **跟 atom 注入的關係**：注入選「哪幾張卡」，這裡選「卡裡哪幾片、用哪個視角、先問哪題」，同一套排序邏輯多一層目的加權。根層給預設，專案可調。

## 三、每個目標：現在缺什麼 → 系統補什麼（是什麼類型）→ 怎麼知道補對了（用什麼驗）

> **補什麼的四種類型**：**閘**＝程式強控，hook 直接擋或放行，LLM 不參與判斷；**注入**＝程式把材料與問題送進 LLM 上下文，判斷由 LLM 做；**工具**＝AI 或人呼叫的腳本／MCP 指令，產出資料；**規矩**＝格式與範本，靠閘檢查格式、靠 LLM 填內容。
> **驗法的四種類型**：**題組**＝固定輸入＋預核答案，腳本比對命中與誤報；**機器數字**＝腳本從 log 算出來的過程量，只當代理；**第二家模型看**＝Codex 拿同材料獨立判；**人看**＝只有原設計者能判的（例如「你看得懂」）。

| G | 現在缺什麼 | 系統補什麼（類型） | 怎麼知道補對了（驗法） |
|---|---|---|---|
| G0 | 改前沒地圖；卡在但關鍵字沒對上就沒送到【試過】 | **注入**：分片＋目的加權，碰部位（含改文件、計畫）就送對的片與對的問題。**閘**：改前沒讀卡、沒交定位三行就擋 | **題組**：三個歷史案例回放修到根因，反例「格式全對但修錯層」要被抓。**機器數字**：首改前讀了卡與部位檔（代理）。**第二家模型看**：回放判分由 Codex 做 |
| G1、G9 | 第二意見手拼材料；材料沒附執行紀錄只能判「寫了沒」【試過】 | **工具**：第二意見指令，自動打包材料、兩種視角模式（獨立診斷／拿目標逐段評）、答案互不可見、回三段。**規矩**：設計類文件必附三段 | **題組**：材料雜湊相同、兩份答案時間戳證明互不可見。**機器數字**：分歧條數與採納率 |

## 四、角色分工：系統怎麼知道現在是哪一層、每層擁有什麼、入口在哪

> 原設計者問「CC 本身有辦法自主產生『現在是專案層』的認知？」——**有，而且已經是機制不是認知**：層由工作目錄與設定檔決定，hook 每次啟動都自己判，LLM 不參與。所以不需要新的 G，但要把「判層」當一條機制列出來（附錄 A 的 H9），讓後面每條機制都接它。

| 層 | 系統怎麼知道（已有機制） | 這層擁有的檔 | 這層的機制入口 | 這層若越界做了什麼，會出什麼危險 |
|---|---|---|---|---|
| 根層 | 工作目錄在 `~/.claude` 底下（realm 閘與寫入閘現在就這樣判） | hooks、MCP、tools、rules、`workflow/config.json` 預設值 | 所有閘、注入、工具的程式本體；每個機制出廠三件：verify 案、變量預設、「專案什麼情況該覆蓋」一句 | 根層若替專案填表或寫卡：內容隨根層 repo 同步到所有機器，別的專案會讀到不屬於它的部位與病灶，注入變成汙染；根層若在 hook 裡寫專案分支：第三個專案接上就壞，變量機制等於沒做 |
| 公司層 | `workflow/config.json` 的 `org_memory` 指到的公司 repo 根（`org_memory_root()` 已有） | 公司 repo 下 `<專案>/.claude/overview-hub.json`（要加）、公司工具卡 | 變量合併的中間層：根層預設 < 公司層 < 專案層（改 `_cfg` 一處） | 公司層若放專案專屬值（某專案的路徑、門檻）：全公司每個專案都被蓋上那個值，別的專案的閘會用錯尺擋錯人 |
| 專案層 | 工作目錄不在 `~/.claude` 底下、也不是公司 repo，就是專案層；再往上找 `<專案>/.claude/overview-map.md`（OverviewHub 的 `find_map` 已有）分兩個**狀態**：找到＝有表，找不到＝無表（新專案或還沒建表的舊專案） | `<專案>/.claude/overview-map.md`、`<專案>/.claude/overview-hub.json`、導讀卡、病灶文件、題組、驗收規格；無表狀態時這些檔還沒有 | 有表：填表、填卡、填門檻，機制自動讀。無表：從零掃表工具產表與骨架，閘在那之前只要求讀過部位檔；表一產生就是有表狀態，不是另一層 | 專案若改 hook／MCP：改的是 `~/.claude` 本體，同機其他專案 session 立刻受影響，而且根層 repo 下次同步會把它覆蓋掉，改動消失；需求要寫成 prompt 交根層（既有閘會擋並附替代做法） |

**專案 AI 每次改碼的自然流程（全部由上表的機制推著走）**：碰部位 → 判層 → 目的加權送片 → 定位三行放工具參數 → 改（產物路徑擋）→ 寫驗證 case、跑量法 → 哨兵自動進帳本 → 收尾帶證據級、持久路徑、追蹤項。

**根層 session 的日常**：看量尺與回路、調預設、修閘；自己改記憶系統也走同一套流程。

**自我批判（寫在這裡讓接手 AI 也看得到）**
- 最大風險是**軌 A 的順序問題**：現在提示詞管線先注入導讀卡再判意圖，目的加權若硬塞會變成「注入了再算權重」，等於沒做。對策：軌 A 第一步就把意圖判斷移前，verify 加「注入時已有意圖」一案，沒過不往下。
- **閘一律擋**會讓根層自己第一個被擋（根層也是專案）。對策：軌 0 先把根層自己的 `<專案>/.claude/overview-map.md` 補齊到能過閘；擋住自己是驗證，不是意外。
- **js 端改動要開新 session**：軌 C 的驗證必須在新 session 做，監工排程時留這一步。
- **三 session 同機共用 live 檔**：多 agent 並行時 log、帳本以專案根分檔，verify 一律 monkeypatch 路徑；這是上一波真摔過的。
- **題組反例先寫再實作**：每軌先把題組（含反例）寫進 `<專案>/.claude/verify/cases/`，實作後跑；避免做完才找驗法、又回到只有正例。
- **不用 scorecard 獎勵**：過程數字只當代理、不設上限；驗收以題組為準，否則會獎勵「讀更多檔、填存在的卡名、印 PASS」的表面合格。
- **效率**：五軌並行可同時開 4 個 agent；軌 0 約一個 session，A 最長；監工每軌合併前審一次，不逐步 ack（高速推進、每步跨大）。
- **退避檢查**：每軌交付前自問三句——有沒有把任何一條改成「提醒」而原本該「擋」；有沒有留「之後」；有沒有「—」。

## 三、舊總控台流程文件裡沒進 /console skill 的段落（逐字）
換手、開工句、派工、交付、裁定帳的做法已寫成 `skills/console/`。下面是三份舊文件（本機信箱 `_console/` 的 `換手協定.md`、`開工句模板.md`、`工作session用agent加速.md`）裡 skill 沒有涵蓋的段落，原文照錄；路徑是當時的。

### 換手協定
- 原設計者原話：「若 session 的 token 量快達壓縮上限(95%?)，你就可以直接(讓track-e或你自己)換成該待命的。但當然，務必確保 朝著目標、高品質執行。」
- context 用到約 85%（原設計者看得到百分比，會告知；工作 session 自己察覺也要先跟總控台說）就換，不等到自動壓縮。壓縮會丟細節，換手前寫清楚比壓縮後補救穩。
- 總控台 SendMessage 待命 session「派工 NNN：接手 track-<名>」＋派工單路徑（**派工訊息正文第一行固定以「派工」開頭**，或首行同時含「派工」與 to-track-<軌>/<檔>.md；hook 只看首行決定同伴訊息算不算開回合，內文引用派工單路徑不開回合）；待命 session 第一步 EnterWorktree 切進 `C:\Users\holylight\.claude-wt\track-<名>`（已存在），讀派工單照做。
- 舊 session 收到「收工」後停；原設計者關分頁。checklist 記新 session 名稱。（後半句已被 skill「不寫死 claude-xx」取代。）
- 現任總控台寫續接單 `C:\Users\holylight\.claude\memory\_staging\next-phase-v6.0-寫程式碼的進化.md`（六區塊：現狀、改動清單、驗證、下一步、危險、規則連結；每條決策附原話或理由；未解問題獨立成區），主追蹤表 checklist 先更新到最新。

### 開工句模板
- 原設計者固定在根層 `C:\Users\holylight\.claude` 開 Claude Code（Bypass permissions），不另開 worktree 資料夾。
- 總控台用 SendMessage 派工時，正文**第一行**固定「派工 NNN：…」（或首行同時含「派工」與 to-track-<軌>/<檔>.md）：hook 只看首行決定這則同伴訊息算不算開一個回合（DISPATCH_OPENS_TURN）；一般回報、交付信在內文引用派工單路徑不開回合，派工訊息也不是口令。
- 若由總控台自己貼：PowerShell `Set-Clipboard -Value <全文>` 放剪貼簿 → MCPControl 點分頁 → 點輸入框 → ctrl+v → 截圖核對 → 點右下角送出鈕（Enter 只換行）。
- （範本句尾）只跑目標 verify（直接在 worktree 根跑 pytest，不加 cd）、不跑全量、不重掛 Monitor、不輪詢。

### 工作 session 用 agent 加速
- 原設計者原話：「可以提醒所有session都能多開agent，看是要 codex cli agent 幫忙初步審查、或者是 幫忙寫 code 的 opus agent。」以下取代各派工單裡「不叫 codex」那一條（只限下面第 2 種用法）。
- **寫程式**：工作可以切成互不相干的幾塊時，派 `general-purpose` 子代理各做一塊。每個子代理的 prompt 要自足：目標（對應哪條 G、原話）、它擁有哪幾個檔（彼此不重疊）、不准動的檔、要跑的驗證、回報格式。同一個訊息裡一次派多個才會並行。
- 子代理沿用你的規矩：不碰 live、不 atom_write、不 commit main、不 push、不跑全量。它改的檔算你的成果，你要親自 review diff、親自跑目標 verify，交付信照實寫哪些是子代理做的。
- 子代理的 prompt 若要求它先寫預告，記得接一句「然後立刻繼續呼叫工具，中途不要停」，否則它會送完預告就結束。
- 指令（PowerShell，背景跑；路徑寫字面絕對路徑）：`Get-Content '<你 scratchpad 裡的 prompt 檔>' -Raw | codex exec -m gpt-6-astra -s read-only -C '<你的 worktree>' --ephemeral --skip-git-repo-check -c 'windows.sandbox="unelevated"' -c 'mcp_servers.unityMCP.enabled=false' -o '<你 scratchpad 裡的回覆檔>' -`
- prompt 要寫明對應的原話目標、你的 diff 範圍（`git diff <起> <迄>`），並要求兩向都審：能不能被繞過、誠實流程能不能通過。
- 總控台在 live 跑全量時會先廣播，那段時間不要跑 codex 或大批 pytest。
- 自己的 context 用到約 85%，先 SendMessage 總控台一句；總控台會叫你交接手備忘，再讓待命 session 接手。

## 四、留在本機、不進 repo 的工具
兩個資料夾都在 `workflow/inbox/` 底下（被 .gitignore 忽略），各有 `README.md` 寫每檔用途與跑法。
- `workflow/inbox/b5-kit/`：B5 驗收工具組——題目、開測流程、答案與觀察表、建置／自檢／收集／觀察輔助腳本，以及上次（2026-10-14）的原始材料。不進 repo 因為裡面有答案，放進公開 repo 等於洩題。
- `workflow/inbox/merge-scripts/`：合併驗證腳本——合併後補驗、live 全量五指令、快照腳本範本、合併前的查核閘探針組（`probe/`），與退回舊碼看紅、規則變異測、live 未動證明、衝突三方比等通用小工具。不進 repo 因為它們寫死了這台機器的路徑與快照樹位置，是總控台的工作工具，不是系統的一部分。

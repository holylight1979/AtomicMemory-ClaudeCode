**為什麼讀了還算沒讀（推論，證據鏈）**
1. 第 2 批那 4 個 Read 的工具後 hook 在同一秒（02:31:07）各跑約 310～330 毫秒，時間重疊（計時帳 `guard-hook_timing.jsonl`，4 筆 PostToolUse 都記在 02:31:07）。都沒有被判超時降級（degraded 0／165），讀檔記帳那段（導讀卡）每支都跑了 13～28 毫秒。
2. `write_state`（hooks/wg_core.py:1128）的鎖只包「寫檔」那一下，不包「讀 state → 改 → 寫回」整段。平行的幾支 hook 各自讀到同一份舊 state、各自加上自己那筆讀檔、各自寫回，最後寫的那支蓋掉其他人。
3. 結果跟這個機制對得上：4 個檔讀完，`reads_after_inject` 只剩 1，訂單結帳的 `part_files_read` 是 0。留下的那筆是表外的 shop.json 或 README，不在訂單結帳部位。
4. 旁證：同一個部位、同一次目標重置的「目標視角重看」送了 5 次（02:31:07 兩次、02:32:51 兩次、02:33:15 一次）。程式送過一次就記 `goal_view_turn` 不再送，記號一直沒留住。第 2 回合開頭（02:32:51）5 個平行讀檔之後，判定仍是 `part_files_read: 0`。直到 02:33:15 單獨再讀一次 pricing.py，才變成 3、放行。
5. 上一跑（作廢那份）同樣 3 個平行讀檔，讀檔數有記到。所以這是看時序的競態，不是每次都掉。

**對使用者的影響**：AI 照擋訊息做了、還是被擋；斷路器照規則停手，對人會跳出「連鎖中止」三選一。凡是平行讀檔後要靠讀檔紀錄放行的閘（定位閘的「讀過部位的檔」、需求目標的讀入範圍），都可能撞到同一個問題。
**建議（一條，給修補軌）**：工具後 hook 寫回 state 時，在同一把鎖裡重讀最新 state、把這次的增量（讀檔清單、記號）併進去再寫，不要整份覆蓋。或者讀檔紀錄改成每個 session 一份只追加的帳。要先寫一條「同一則回覆 4 個平行 Read、全部記到」的重現案證明它紅。

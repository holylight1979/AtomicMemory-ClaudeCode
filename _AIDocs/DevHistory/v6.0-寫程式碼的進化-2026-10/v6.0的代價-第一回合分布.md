# v6.0 的代價：改 code 題第一回合多出的 token 從哪來

> 這份在說什麼：改 code 題（題 B′）第一個使用者回合「加 by-product 子命令」，v6 守門全開比全關多出的輸入 token，拆到「為什麼多」與「哪道閘、哪段程式造成的」，給下一輪減量決定刀下在哪。
> 量測 2026-10-27。只讀既有實跑紀錄（2026-10-23 的現況 R1／R2 兩跑、全關三跑、004 現況三跑），沒有重跑、沒有改 hooks／lib／tools。
> 讀數標記：**實測**＝transcript 與回合 JSON 的 usage 直接加減得到。**推論**＝用估算式分配到段，或判斷「這次呼叫是閘造成的」。

## 結論
- **多出 111.7 萬 token、176 秒**（實測）：
  - token：全關平均 45.8 萬，現況 157.4 萬（R1 +102.7 萬、R2 +120.6 萬）。其中 80.6 萬（72%）是守門多出來的模型呼叫本身：每跑多 11.5 次呼叫，每次平均 7.0 萬。
  - 牆鐘：全關平均 139 秒，現況 R1 317、R2 313 秒。多出的 176 秒裡，額外呼叫從送出到回完共 124 秒（70%）；連同它們的工具執行與 hook，共 142 秒（81%）。
- **前三大來源**：
  - 定位閘 OverviewHub 48.8 萬（44%）、67 秒；
  - 需求目標樹 NeedGoal 17.7 萬（16%）、13 秒；兩跑分別 7.2 萬、28.2 萬，差在 need_goal 有沒有跟別的工具同一則送出；
  - 動資料檔閘 DataFileAsk 15.9 萬（14%）、7 秒。
  - 第 4、5 名是收尾的拐彎判斷 ReadingPath 9.0 萬（8%）、22 秒，和最該修 PickOne 8.5 萬（8%）、15 秒。
  - 前五名合計 99.9 萬（89%）；所有額外呼叫的秒數都落在這五個來源。
- **刀要下在「少一次呼叫」，不是「縮短文字」**：
  - 先前判讀的「被擋後重做」確實是大頭，a 類佔 48%；
  - 「擋訊息被重讀」不成立，b 類只佔 4%，擋訊息已經縮短了；
  - 第二大類是守門要求的額外動作，d 類佔 34%。

白話：模型每被叫一次，就要把到那一刻為止的整段對話（系統說明、工具清單、讀過的檔、之前每則回覆）從頭讀一遍。第一回合後半段每次約 6～9 萬 token。所以多被擋一次、多要一個動作，就是多付一整次 7 萬左右；把一段 2 千字的擋訊息砍一半，只省幾千。

## 用到的代號（第一次出現的白話）
- **第一回合**：受測任務的第一個使用者訊息（「sales 的 cli 加一個 by-product 子命令…」）到 AI 交出回覆，中間所有模型呼叫。
- **全關／現況**：全關＝hook 全部關掉（settings-guard-off.json）；現況＝live settings 全開、`WG_V6=1`。
- **輸入**：每次模型呼叫的 input＋cache_creation＋cache_read 相加，同 `v6.0的代價-減量後-重新判分.md` 的口徑。
- **額外呼叫**：沒有那道閘就不會發生的模型呼叫。**照常呼叫**：其餘的。
- **定位閘 OverviewHub**：改某個「部位」（部位表上的一塊程式，這題是 `sales/` 銷售報表）的檔之前，要先讀過那塊的檔，並交出「定位」四行（部位、根因層兩候選、前例、批判），不然擋。
  - **導讀卡**：第一次讀到那塊時 hook 注入的說明。
  - **判準卡**：附在擋訊息後面的判斷準則卡片。
- **NeedGoal**：需求目標樹。AI 用 `need_goal` 工具開工立樹（set）、宣告驗證範圍（verify_scope）、收尾對照（reconcile）。
- **DataFileAsk**：改使用者既有的資料檔、設定檔、README 這類共有文件前，要先宣告一行「動資料檔｜路徑：為什麼」。
- **ReadingPath／拐彎判斷**：收尾時量改到的函式有幾個彎、巢狀多深；到門檻就要回覆裡有「拐彎判斷｜」五欄行，沒有就擋收尾。
- **PickOne**：交付改了程式時，收尾附一段材料，要 AI 在回覆最後寫「順手看到最該修」。
- **Stop 續跑**：Stop hook（AI 要結束回覆時跑的 hook）擋下或附加文字時，Claude Code 會讓對話再跑一輪，AI 重寫收尾。

### 1. 定位閘：每跑 4 次額外呼叫走同一條路（我核過帳）
- **怎麼花掉的**（平均）：
  - a1 23.6 萬：每跑 4 次呼叫走「擋 → Read → 再擋 → 用 Bash 註解交定位 → 放行」。每一筆擋的理由見下一小節。
  - d1 14.1 萬：擋過後改用 Read 先讀才改，程式檔 3.3 萬（只有 R1）、README 7.5 萬（兩跑各 1 次，推論較弱，見限制）；另一次是只交宣告行，3.3 萬（只有 R1，交測試那塊的定位）。
  - a2 5.5 萬；b 3.6 萬（擋訊息本文 2.1 萬、附的判準卡 1.5 萬）；c 1.0 萬（導讀卡）；d2 0.9 萬。
- **記帳漏（只有 R1 踩到）**：
  - R1 第一條讀檔的 Bash 就一次讀完整個 `sales/`，這條指令觸發導讀卡注入。
  - 但 `on_read` 碰到第一個命中的檔就 `return _inject(...)`（:937）；`_record_read` 在注入前跑，那時這個部位還沒有紀錄。所以同一條指令讀到的檔一個都沒記。
  - 帳上：R1 `_overview-hub.log` 09:50:49 `inject via=bash`，09:51:41 第一次改檔 `part_files_read=0`；擋訊息寫「目前 0 個」。

- **第二筆擋是模型沒照做**：AI 把定位寫進 thinking。

- **改法 A 的取捨**：
  - 現行規則刻意只算「導讀卡之後」讀的（擋訊息原文「注入導讀卡後還沒讀過這個部位的檔」），用意是讀卡之後帶著卡的視角再讀。
  - 補記觸發那條指令的讀檔，等於放寬這條，要原設計者拍板。
  - 只改設定的替代是專案把 `part_files` 設 0（`lib/hub_config.py:43` 可設），但那等於整個不要求讀檔。
  - 省多少只看 R1 這一型：補 Read 那次（5.7 萬、7 秒）一定省；之後學來的「改測試檔前先 Read」（6.6 萬、4 秒）可望一起消失。R1 省 5.7～12.3 萬，R2 省 0，兩跑平均 3～6 萬（推論）。

  - (e1) 每跑約 6.0 萬、20 秒，是 AI 把定位只寫進 thinking 造成的第二次被擋。只能靠把擋訊息的管道說明改硬（例如「thinking 一律讀不到，四行要寫在回覆文字或 Bash 開頭的 # 註解」）去賭模型照做，屬推論。
  - 其餘約 11.9 萬、21 秒是交定位本身（被擋一次＋交宣告一次）。

### 2. NeedGoal：兩跑做的事一樣，差在送法
- 兩跑都呼叫 need_goal 3 次（set、verify_scope、reconcile）。
  - R1 三次都跟 Bash 或 ToolSearch 同一則送，呼叫本來就要發生，只算 d2 與 c，共 7.2 萬。
  - R2 三次都單獨送，多 3 次呼叫，共 28.2 萬。
- 真實的邊際成本落在兩者之間。
- 不論哪種送法都要付的固定成本：
  - need_goal 工具定義實測 3,625 token（4 次單獨載入 3,546～3,721），載入後每次呼叫都重讀，每跑約 3.5 萬；
  - set 回應送全樹加判準卡 E23 兩張，約 1.3 千字，被之後約 20 次呼叫重讀。

### 3. DataFileAsk：被擋一次就是 +2 次呼叫
- 擋訊息原文寫明「宣告行要比這次工具呼叫早一則訊息送出（跟工具呼叫同一則送出的文字，這裡還看不到）」，所以每次擋都是「被擋那次＋交宣告那次」兩次。
- `.md` 算資料檔是刻意的，檔頭寫「README、病灶清單這類團隊共有文件」。
- 兩跑 AI 在 Edit 前一則都寫了一句意圖，例如 R1「README 的「跑法」只寫了 monthly，補上新子命令」，只差沒照格式。
- 所以「事先告訴它格式」這刀命中率看起來高，但 AI 會不會照做是推論。

### 4＋5. 收尾兩輪續跑互相牽連
- **順序**：
  - 背景量測在第一次 Stop 才起跑（`wg_reading_path.py` 檔頭「Stop 只算出這一批輸入、交給背景行程量，不等它」），第一次收尾沒有數據、不擋。
  - 第一次收尾送 PickOne（Stop 的 additionalContext），對話續跑一輪，AI 重寫整則收尾加上最該修。
  - 第二次收尾數據到了，拐彎判斷擋下，AI 再重寫一次。
- **連帶後果**：
  - 拐彎判斷那次額外呼叫，是 PickOne 先多跑一輪才出現的。
  - 只把 PickOne 提前、不讓它續跑，第一回合會同時少掉兩次（約 17.5 萬），但拐彎判斷的擋延到下一個使用者回合，這題就是交材料那回合。
  - 兩件一起改（量測提早起跑、第一次收尾一起問）才是真的省。
  - 量測預算最長 300 秒（`WORKER_BUDGET_S`），不能改成在 Stop 裡等結果。
- PickOne 自稱「只提醒、不擋」，但代價是一整次呼叫（約 8.5 萬）。

### 建議刀序（推論）
1. 定位閘補記觸發注入那條指令的讀檔：改動最小，根因有帳可證，先拍板再改。只對 R1 型有用。
2. DataFileAsk 事先送格式提示。
3. PickOne 與拐彎判斷一起提前，併成一輪：省得最多秒（約 37 秒）。
4. need_goal 工具定義減半。

前四刀都照預期生效，估每跑省 37～40 萬、約 48～50 秒，第一回合從 157 萬降到約 117～120 萬，對全關仍是 2.6 倍。

剩下的大頭：
- 定位閘交定位本身（被擋一次＋交宣告一次，約 12 萬、21 秒）；
- AI 把定位寫進 thinking 的那次重擋（約 6 萬、20 秒，只能改說明去賭）；
- need_goal 的單獨呼叫。

## 方法
1. **模型呼叫與輸入**（實測）：
   - transcript 的 assistant 列依 `message.id` 合併成一次呼叫，讀 usage 得到輸入 T 與輸出 O。
   - 第一回合＝回合 JSON `_meta` 起訖時間內的呼叫。
   - 8 跑的逐呼叫加總都跟回合 JSON 的 usage 逐位相同；全關平均 45.8 萬、R1 148.5 萬、R2 166.4 萬，與重新判分報告一致。
2. **相鄰呼叫的差拆成兩半**：
   - 輸入差 D_k＝T_k−T_{k−1}，等於上一次的輸出 O_{k−1}（實測），加上中間新進 context 的東西 R_k＝D_k−O_{k−1}（實測總量）。
   - O 含 thinking token。thinking 會被送回（`clear_thinking keep: all`），R_k 全部為正、跟新進段的估算吻合，可佐證。
3. **R_k 分到各段**（推論）：
   - 新進的段＝工具結果（被 PreToolUse 擋的另標擋訊息，並在「判準卡（」處切開）、hook 注入（依行首標籤切塊）、Stop 擋訊息、Claude Code 自己的提醒。
   - 估算式：R_k ≈ 1.321×中日韓字＋0.534×其他字−8.8×段數，係數用 8 跑全部 149 個差額迴歸，平均絕對誤差 5.0%。每個 R_k 按估算比例分，總和不變。
   - ToolSearch 載入的工具定義看不到字，改用單獨載入那幾次的殘差當定值：need_goal 3,625、anti_evasion_report 2,218。
4. **開場注入**（實測差）：現況第一次呼叫 T_0 減全關 T_0 平均（37,064），R1 1,961、R2 1,962；估算式算出 1,985，差 1.2%，作為估算式的獨立驗證。
5. **呼叫分類**（推論，規則寫死在腳本 `classify`）。照順序判，先中先算：
   - Stop 擋（hook_blocking_error）之後的那次 → a；Stop 注入之後的那次 → d。
   - 所有工具都被 PreToolUse 擋 → a，開一個「補件窗」。窗內只做讀檔、Grep、need_goal、ToolSearch、交宣告行的呼叫 → a。碰到第一次做別的事（通常是寫檔成功）就關窗，那次算照常。
   - 只呼叫 need_goal（或只載入它）→ d；只交宣告行（Bash 的 `# 定位｜`、`# 動資料檔｜`、`# 改舊測試｜`）→ d；本回合定位閘擋過之後只用 Read 讀檔 → d（全關三跑第一回合 Read 0 次）。
   - 其餘照常。逐次分類表見 `v6.0的代價-第一回合分布-實測/first_turn_breakdown-輸出.md` 末段。
6. **記帳，不重複**：每一格「呼叫 × context 裡的一段」只進一類。
   - a、d 呼叫：整次輸入記 a1、d1，不再看裡面有什麼。所以「被擋後重做的呼叫也在重讀擋訊息」那部分算在 a1，不進 b。
   - 照常呼叫：把當時 context 每一段記到段的類別。擋訊息 → b；注入 → c；a、d 呼叫留下的輸出與工具結果 → a2、d2；照常呼叫裡 need_goal 的那幾塊與 need_goal 工具定義 → d2；其餘 → 照常。
   - 腳本核對每次照常呼叫各段加總＝T（最大差 <1 token），所以 a＋b＋c＋d＋e＝多出，恆等。
7. **e**＝照常合計−全關平均，可正可負，是 AI 自己走法的差，不歸任何閘。
8. **秒數**（實測）：
   - 每次呼叫的送出＝transcript 的 `api-request` 列時間（每次呼叫一列，8 跑數量都對得上，照順序配）；回完＝這次回應最後一個區塊寫入的時間。
   - 另算「送出到下一次送出」，含工具執行與 hook。
   - 回合牆鐘＝回合 JSON `_meta` 起訖（004 口徑），8 跑都和 `_fm/measure.json` 的同一回合 `wall_s` 相同。
   - 來源的秒＝它的額外呼叫加總。

## 限制（哪些數不可靠）
- **「這次呼叫是閘造成的」是反事實判斷**：規則保守，混合呼叫（例如 need_goal＋Bash 同一則）一律算照常，所以 a、d 偏低估、e 偏高估。
  - 最明顯是 NeedGoal：同樣 3 次 need_goal，R1 7.2 萬、R2 28.2 萬。
- **README 那兩次 Read 歸給定位閘是弱推論**（7.5 萬）：
  - README 不在 `sales/` 部位裡，定位閘不會擋它。
  - 判成「擋過學來的先 Read」，依據是全關三跑改 README 前都沒 Read。
  - 若改歸 e，定位閘降到 41.3 萬（37%），e 升到 15.8 萬。
- **e 的 8.3 萬在雜訊內**：全關三跑自己就是 39.8／52.1／45.4 萬（±6 萬），e 不拿來下結論。
- **b、c、a2、d2 的段內分配是推論**：估算式平均誤差 5%，兩項獨立驗證差 1.2% 與 0.2%（Stop 擋訊息兩份對實測 3,677）；各類合計誤差估在 ±5% 內。
- **兩跑樣本**：R1 與 R2 多出差 16%。前五名裡定位閘、DataFileAsk、ReadingPath、PickOne 兩跑幾乎一樣，NeedGoal 差 4 倍（送法不同）。
- **秒數的邊界**：
  - 「回完」取最後一個回應區塊寫入 transcript 的時間，Claude Code 邊串流邊寫區塊、平行工具可能已在跑，誤差在 1 秒級。
  - 多出的 176 秒裡，額外呼叫連同工具與 hook 只解釋 142 秒。其餘 34 秒是照常呼叫變慢（輸入變長、照常呼叫裡的 hook 時間），加上開場 hook 多 3 秒、全關三跑之間的差距（126～160 秒），沒有再拆。
- **token 不等於錢**：現況第一回合輸入 95% 是 cache_read（全關 91～93%）。額外呼叫讀的多半是快取，美金多出的比例比 token 小；這份照 001 的成本線口徑只算 token。
- **只量第一回合**：交材料那回合的同步提醒擋、第二段新 session 都不在內。
- **004 交叉對照的分類偏低**：004 的定位閘擋次上限照工具呼叫算，同一則常是「部分被擋、部分放行」。這種呼叫被規則算成照常，a 偏低、e 偏高；CCon-3 紅測閘擋下之後的兩次續跑只算第一次。

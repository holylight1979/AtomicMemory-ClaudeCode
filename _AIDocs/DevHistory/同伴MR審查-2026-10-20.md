## 合進 main 的，各自為什麼

**!4、!5**：純測試修正，產品碼一行沒動。重點不是「讓測試過」，而是這些紅和程式對不對無關：日期漂移、機器設定差異。多機共用時，一台紅一台綠的測試等於沒有測試。

**!6**：`normalize-eol` 在記憶樹被上層 `.gitignore` 整個排除時（例如忽略整個 `.claude/` 的系統 repo），仍會往 `.gitattributes` 寫規則。規則對被忽略的檔沒有作用，只是每開一次 session 多一個髒檔讓人去看。3 行判斷加 1 個案例。

**!7**：四件事放一起，因為都是「寫的時候只有一台機器、一個人」留下的洞——
1. 程式裡寫死 `"holylight"` 當路徑噪音詞與預設使用者。同事機器上 personal atom 會歸到錯的帳號下、PersonalSync 指到錯的目錄，而且不報錯。改成問當前使用者。
2. 子目錄自己是 SVN 工作副本時，「最近標記」會停在子目錄，記憶被切成第二棵殘缺的樹，症狀只是「atom 都讀不到」。改成強標記先掃滿整條鏈、裸 `.svn` 最後才算。
3. 收尾檢核交過之後、沒再改檔的純問答回合，不再被要求重交整份十一欄——這是省 token 的那一邊。
4. `knowledge_queue` 混進純字串時 SessionEnd 不炸：守衛本來就在，補測試釘住，重構時不會被當多餘的型別檢查拿掉。

**!9**：這批最大（30 檔、約 2500 行），但方向和本系統「多機共享記憶、靠版控同步」的目標完全一致，而且每一項都是把事情變少：
- 反向連結改由索引在注入時反轉，不再寫進被連的那顆檔。新增一顆連到 hub 的 atom 不必去改別人的檔，衝突源頭消失；SessionEnd 少起兩個背景子行程；atom-heal 的 L1 整級移除。
- 改名寫 `- Aka:`，舊連結照樣解析，改名者只動自己那一顆。
- 專案記憶索引可從磁碟重建（`--rebuild`、SessionStart 缺檔或過期自動重建），所以能退出專案版控；`lib/vcs_ignore` 自動設 svn:ignore／.gitignore，已版控的只告警附確切指令、絕不自動刪。
- 待辦清單型內容第一次寫入就擋（≥3 個 `- [ ]`）：atom 隨 trigger 整顆注入、知識段約 200 tok 就截斷，長清單放進去等於記了但送不到。
- 順手修掉的真 bug：Related 空值會把下一行標題吃掉、寫入 funnel 不拒含衝突標記的內容、v4 佈局漏掃 `failures/`、git 疊 svn 時 svn 側衝突被略過、MCP 子行程 cp950 亂碼。
- 相容：索引 schema 不升版只加欄位，舊版工具可讀新格式。全隊更新後才算根治（舊版 `--fix-refs` 仍會寫反向連結）。

**!12**：/upgrade skill 加一段「先判斷兩台機器的 git 歷史是否相通，相通就 fetch／merge-tree 試算／merge，不相通才逐維度比對」。只在有人跑 /upgrade 時載入。

## !11 暫不合：為什麼、想請原作者做什麼

- 129 檔、約 1700 行的全面改寫，加 `memory_names.json`（332 行）＋`memory_names.py`（238 行）＋`verify_name_single_source.py`（314 行）三支新機制，目的只是把檔名／資料夾名集中。它防的問題（改名時漏改某處）發生頻率很低——這些名字幾乎不會改。

**想請原作者回答**：這次重構是不是因為實際踩到了「改一處壞別處」？是哪一次、哪個名稱？

**建議的輕量版**：只把最常被引用的索引檔名與衍生資料夾名（約 10 個）集中到既有的 `lib/atom_spec.py`，不另開 JSON、不加拼路徑方法；守衛測試只擋「同一組索引檔名在別處再寫一份清單」這一種。JS 側（MCP paths.js）真要共用再談 JSON。

- 使用者拍板（10-20）：走小改版，最終目標寫清楚貼到 MR 上請作者協助調整；關閉重開或在原分支上合 main 再改，由作者自己決定。已貼（走網頁）。小改版的邊界：**做**——會被多處引用的索引檔名、衍生資料夾名、記憶結構資料夾名集中成扁平字串常數放進既有 `lib/atom_spec.py`，各工具跳過名單從常數組、內容各自維持，每個名字一句說明，守衛只擋「atom_spec 之外再寫一份同組名字清單」；**不做**——位置元組與拼路徑方法、`memory_names.json` 與 JS 讀 JSON、守衛擋單獨字面與路徑字面、設定／狀態／工具／文件檔名集中。

## 怎麼驗的

- 每個 MR 先對 main 做 `git merge-tree` 試算：!4～!9、!12 零衝突，!10／!11／!12 只有 `_CHANGELOG.md` 兩側各加條目（用 union 合併，兩側都留）。
- 先對 main 跑了一輪整組 pytest 當基準（這一步是多餘的，使用者裁定全量已從流程拔掉；記一筆）：51 個紅，集中在 verify_install、verify_merge_atom_index、verify_vcs_sync_worker、verify_project_root_claim 等 7 檔，全是這台機器在隔離假家目錄下的環境問題。
- 合併樹只跑「相關測試」33 檔（MR 自帶的案例檔＋被改模組的既有案例檔）：1083 過；紅的三類——verify_project_root_claim 6 個與基準相同（環境）；verify_stop_reconcile 86 個與 verify_normalize_eol 1 個是 git 錄製檔（cassette）過期：!5 改了測試裡 git 的參數、!6 多了一次 check-ignore，重播比對不上。重錄這兩檔的錄製檔後全綠，錄製檔一併進 commit（MR 作者沒附）。
- !9 改了 merge-atom-index.py（git 合併驅動會叫它），merge_atom_index／merge_driver_gate／vcs_sync_worker 三組錄製檔被測試框架判過期自動重錄；這三檔在基準就有環境紅，重錄結果不進版控（會把這台機器的環境固化給別人），由各機器下次跑時自己重錄。

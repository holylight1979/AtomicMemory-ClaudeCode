## 1. 起因與使用者原則

### 1.1 問題
- `memory/MEMORY.md` 被 `CLAUDE.md` `@import`，**每個專案每個 session 必載**，實測 2,833 tokens；內容是 49 顆 core atom 一行一列的平鋪明細，「說明」欄與名稱重複。`INDEX_MAX_LINES` 一路從 40 調到 80 只是在遷就膨脹。
- 本地範疇 `_AIDocs/_atoms/<domain>/` 早已階層化（`_local_catalog.md` 只列 Lv1 根＋計數＋drill）；core 平鋪不是決策，是「realm sweep 沒搬走的就是 core」的副作用（舊 SPEC §2.3「寫入落點永遠扁平」）。當初把分類記憶硬拆到 `_AIDocs/` 就是為了躲根下散檔，結果核心層自己還是平鋪。
- 失敗家族（feedback-*）物理住在 `_AIDocs/Failures/`，與 `memory/` 分家；dashboard 世界看不到 `_AIDocs/**` 任何 atom。

### 1.2 使用者原則（原文要點，本案所有裁決的上位依據）
- 記憶系統要**主動建立層次索引**。
- 根層與專案層寫入一律**先分類再落地**。
- **`memory/` 下分類資料夾必備**（強調三次以上），不得不經分類往 MEMORY.md 堆。
- 使用者拍板五點：① 分類落實體子目錄、分類由 index path 推導 ② Failures 整家族搬到 `memory/Failures/<主題>/`（Lv1 家族保留、底下按主題）③ 寫入閘：AI 必給分類；程式寫入走詞庫→本地 LLM；仍分不出就**拒寫**（core 不設 Else）④ `_AIDocs/_atoms/` 只留「只在 ~/.claude 有用」的（記憶系統開發／腦內世界／願景／本機特定）；Continuity／OS／Tools 逐顆看內容，與流程運作、產出品質相關的搬進 `memory/<範疇>/` ⑤ 記憶系統內部知識分「使用面（留 core）vs 開發面（去 local MemDev）」。
- 附帶澄清：專案層 AI 對 `_AIDocs` 轉折的「不理解」不是問題——路由是機制層（`atom_io._resolve_target`），任何 cwd 一致；專案層 AI 只看 MCP schema。真正缺口＝寫入時沒被要求分類，這才是 S4 寫入閘要補的。

## 2. 目標形狀

### 2.1 兩根
```
memory/                        ← 核心：全專案注入；根下零散檔
  MEMORY.md                    ← | 範疇 | atom 數 | 深入 |：Lv1 各一列 + Failures 一列 + local 指標行
  _meta/taxonomy.json          ← 分類法單一真相（fail-closed：檔缺／壞 → 閘拒寫並 stderr）
  <範疇>/[<子範疇>/]            ← 實體資料夾；_INDEX.md 由 sync-memory-index 生成
  Failures/<主題>/feedback-*.md ← 失敗家族 Lv1，主題 Lv2 同核心範疇名
  Failures/_reference/         ← 舊 V3 非 atom 參考文件；`_reference` ∈ SKIP_DIRS
_AIDocs/_atoms/<domain>/       ← 本地範疇（只在 ~/.claude 注入）：MemDev／World／Vision＋本機特定 Tools／OS；機制不變
<proj>/.claude/memory/shared/<範疇>/  ← 專案層同規則
```
分類唯一真相＝index `path`（`memory/<Cat>/…`、`memory/Failures/<Topic>/…`、`shared/<Cat>/…`），不加欄位、不寫 frontmatter；realm 仍由 `_AIDocs/_atoms/` 前綴推導，`is_local_realm_path` 與 SessionStart 注入閘**零改動**。

### 2.2 分類法（Lv1 閉合清單，11 個；資料夾＝中文正名，英文 slug／別名只做輸入對映）

| Lv1 資料夾 | slug | 涵蓋 | Lv2（≥2 顆才建） |
|---|---|---|---|
| `版控` | VCS | git／svn 操作紀律 | `Git`、`SVN` |
| `工作流` | Workflow | 任務節奏、收尾、協作、handoff | `協作與並行`、`節奏與收尾` |
| `思考與決策` | Thinking | 推理偏誤、歸因、取捨 | — |
| `驗證與實證` | Verify | 測試、實機取證、判準 | — |
| `dotnet` | dotnet | WinForms／ASP.NET／建置 | `WinForms`、`ASPNET`、`建置` |
| `OS-Windows` | Windows | Windows 系統層踩坑、UIA | — |
| `文字與格式` | Text | shell 跳脫／換行、解析器、辨識、資料格式 | — |
| `設計通則` | Design | 跨語言設計與重構安全 | — |
| `行為契約` | Conduct | AI 自主行為守則 | — |
| `CC與原子記憶契約` | CC-Memory | Claude Code／記憶系統**使用面**契約 | — |
| `Failures` | Failures | 使用者糾正／失敗模式；Lv2 = 上列主題名 | 同上 |

使用者原清單 → 正名對映：版控-SVN／GIT → `版控/SVN`、`版控/Git`；思考與智慧 → `思考與決策`；文字-辨識解析與格式 → `文字與格式`；VisualStudio → `dotnet`（內容過半是 server/build）；workflow → `工作流`；OS-windows → `OS-Windows`；CC與原子記憶契約法則 → `CC與原子記憶契約`（使用面）＋開發面留 local `MemDev`；直面失敗與錯誤 → `Failures`；驗證 → `驗證與實證`。

**禁用資料夾名**（casefold；撞 skip 名單／funnel 白名單／dashboard 層名）：`_*`、`.*`、`_archive*`、templates、personal、episodic、wisdom、roles、shared、projects、failures（小寫舊址）、unity、memory。`Failures`（大寫）是唯一例外：由 taxonomy 明列。

### 2.3 使用面 vs 開發面判準（決定每顆 atom 住哪根）
**使用面／流程運作與產出品質**（任何專案的 AI 會碰到）→ `memory/`；**開發面／本機特定**（改記憶系統本身、或只在這台機器成立）→ local `_AIDocs/_atoms/`。依此：
- 49 顆 core → 47 顆進 `memory/<範疇>/`、2 顆開發面（decisions-architecture、toolchain-ollama）→ `MemDev`。
- 21 顆 Failures → 19 顆進 `memory/Failures/<主題>/`、2 顆開發面（memory-pipeline-silent-failure-2026-05、feedback-memory-system-doc-sync）→ `MemDev`；7 份非 atom 參考文件 + `_INDEX.md` `git mv` 到 `memory/Failures/_reference/`。
- `_AIDocs/_atoms/` 現役 Continuity／OS／Tools 16 顆 → 11 顆使用面搬進 `memory/`（handoff／跨 session 失真／a執p／vscode-reload／git 已 push 勿改寫／dotnet-run 單檔／msbuild dash 參數／write_text CRLF／pythonw stdout／electron-uia／mcp.json 雙開），5 顆本機特定留 local（gdoc-harvester、cc 反編譯實跑、codex-log-bloat、WSL 0x80070569、hook 閃 console）。Continuity 根清空後 `CROSS_PROJECT_LOCAL_DOMAINS` 留空集合、機制保留。
- 遷移總量：77 move + 4 realm（進 MemDev）+ 8 份參考文件 git mv。範疇尺寸：最大 工作流 14、dotnet 9、Failures 19；最小 設計通則 2、行為契約 2、SVN 1（Lv2 允許單顆）。

## 7. 協作方式：總管模式

本案是「總管 ↔ 主力」雙 Claude 協作的首次五階段實跑：一個總管 session（Fable）全程只讀 repo、只寫 `.ai-inbox` 信件裁決，五個主力 session（S1–S5）逐階段接槽；每階段主力先寄「坑點清單」（改動面／已知坑對策／驗證對應），總管回「無異議＋補證項」才准接線；交付信附驗證末行，總管**獨立重跑**（run_verify、`--check`、audit、隔離埠 MCP 實測）而非只讀信。S3 apply 的前置硬閘（同機無其他活躍 session，避免舊 SessionStart 快取靜默不注入已搬 atom）由總管用 `claude.exe` 行程清單核實後放行；放行條件分兩封寄、主力已按第一封動手（提早 2 分鐘 apply，事後驗證無害）是本案唯一流程瑕疵。

手感與教訓已寫入 atom [`雙claude協作實戰認知-fable監工opus主力的分工手感`](../../memory/工作流/協作與並行/雙claude協作實戰認知-fable監工opus主力的分工手感.md)（總管模式段），本檔不重抄。

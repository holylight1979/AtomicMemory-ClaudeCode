# 派工單範本與信箱擺法

> 給誰：調度總控台寫派工單時照填。派工單只寫四樣：做什麼、怎麼驗、不准碰什麼，加一句原始目標（規則 DISPATCH_FOUR_PARTS）。開工、交付、git 啟動器、codex 這些每軌都一樣的做法在開工句與工作軌守則裡，不再抄進每張單；工作軌開工不讀歷史快照（接續單、交接備忘、舊交付信）。

## 信箱擺法

```
<專案根>/workflow/inbox/          ← 路徑可換；本機用，不進版控（換機要另外帶）
├── to-track-<軌>/NNN-<題>.md        ← 派工單（調度寫）
├── from-track-<軌>/NNN-<題>.md      ← 交付信（調度收到後存檔）
└── _console/                        ← 總控台自己的：裁定帳、交接備忘、驗證 log、腳本原稿
```

- 編號 NNN 每軌自己往上加；退件單接著編（例 002 退件 → 003）。
- 腳本、素材不要以 `.py`／`.sh` 放進信箱（程式會當成改碼記欠帳），存成 `.py.txt` 讓工作軌自己複製去用。
- 看現況：`python ~/.claude/skills/console/scripts/console-status.py`（印各軌最新來信與 `_console/verify*.log` 的結果）。

## 開新軌

1. 軌名望文生義（`track-login-fix`）。小幅改動不開軌，直接在 main 改、驗、推。
2. 建 worktree 與分支：`git worktree add <worktree 路徑> -b <分支> main`。
3. 寫派工單到 `to-track-<軌>/000-prompt.md`。
4. `/console 開工句 <軌名> <派工單路徑>`，交對人轉給人貼。

## 派工單範本

```markdown
---
to: <軌名>
seq: <NNN>
type: 派工（<一句話這件要做成什麼>）
from: 調度總控台 <調度名>
原始目標：<使用者原話或原設計者定的目標，一句；判準以原文為準>
---
## 做什麼
1. <每件一句：改哪裡、改成怎樣；不准自由發揮的寫死（放哪支檔、規則名、判定只看什麼）>

## 怎麼驗
- <紅案例：情境 → 該擋／該收；舊碼跑是紅、改完轉綠>
- <目標 verify 清單與跑法；pytest 跟直接跑都要綠，收 0 案不算綠>

## 不准碰什麼
- <不准動的檔、不准放寬的閘、不准跑的東西（全量、live）>
- 需要判斷的事不寫成固定規則（固定清單、檔名對應、門檻數字）：留給工作軌宣告＋理由、程式只核對。
```

## 交付信的「該誰解」只有兩種寫法（原設計者 2026-10-20 定）

- 審查、codex、交付時挖出來的問題：判為飄移（跟手上目標無關、或是設計取捨）→ 寫「飄移，不做，因為…」；判為相關且確實有問題 → 在同一分支立即修（先紅後綠）再交付，欄位寫「已修」。
- 不准寫「下一個寫碼 session」「合併後由總控台排」「要總控台同意」——要同意就當場問，不當成不做的理由。總控台收到這種字樣當場派回原軌補件，不記追蹤項。

## 退件單多寫三件

- 退件原因附「怎麼重現」（讀碼或指令），讓工作軌不必猜。
- 原話目標照抄，不只寫症狀。
- 同一面退第二次：不再列症狀，把規則定死或改設計。

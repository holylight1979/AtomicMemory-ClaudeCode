# 交付信範本（工作軌 → 調度）

> 給誰：工作軌交付時照填，用 SendMessage 送全文（worktree 裡寫不到信箱，所以不寫檔）。調度收到後存成 `from-track-<軌>/<NNN>-<題>.md`，在信尾加「調度對帳」段。

## 寫法

交付信就是收尾那一份報告（`anti_evasion_report` 的 `report`），原文照貼進 SendMessage，不另寫一份。唯一標準是白話易懂：讀者是沒看執行過程的隊友，看完要知道能不能合、要不要他做什麼。不預設欄位，照下面四段的順序寫，但以讀者看得懂為先：

- **做了什麼**：一句話總結（commit 短 hash、分支、未推），再每個改動一句白話——改前怎樣、改後怎樣。
- **驗了什麼**：跑了哪些目標 verify、幾個 passed、哪個案例在舊碼是紅的；codex 收了哪幾條、為什麼；live 未動的證明；這次有沒有把需要判斷的事寫成固定規則（固定清單、檔名對應、門檻數字），有就寫在哪、為什麼合理。只有讀碼或推論的寫「推論」，不寫「通過」。
- **沒做什麼**：跳過的、不准碰的、拿不準要裁的，照實寫；不准寫「之後再」「另外處理」「延後」。
- **追蹤項**：還沒做完、之後要追的事（同一份也進 `k_followups`）。

結尾一行「我在等：<調度對帳合併／對人裁定 X／無>」。

## 調度對帳段（調度收件後加在信尾）

```markdown
---
調度對帳（<名字>）：改檔集＝自述／禁字無／CR 無／merge-tree 無衝突／live 未動；
基底 <hash> 對 main <hash>：<含最新 main 可快轉 → 直接推、不補驗｜落後 → 合後補驗一次｜跟別軌碰同一大檔 → 該軌在分支合 main、解衝突、驗完再交，可快轉直接推>；閘本體改動：<有 → 快照｜無 → 信收據>。
```

## 寫交付信的三個坑

- 「完成」要有沒紅的收據；只有讀碼或推論的寫成「推論」，不寫「通過」。
- 子代理寫的部分照實標出來，你自己 review 過 diff、自己跑過 verify。
- 結尾沒有「我在等」＝調度看不出你卡在誰身上。
- 「順手看到最該修」與「已知限制」裡的問題，該誰解只有兩種：「已修」（相關且確實有問題 → 同分支立即修完再交）或「飄移，不做，因為…」；寫「下一個寫碼 session」「合併後再排」會被當場派回來補件（原設計者 2026-10-20 定，細節見 dispatch.md）。
